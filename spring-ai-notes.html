    01

    What is Spring AI?

    00:00 — 09:50

    Spring AI is just another Spring project / module — exactly like Spring Data, Spring Security or Spring Cloud. Whenever your Spring Boot application needs AI, you pull in Spring AI. That's the whole mental model the instructor starts with.

    The problem it solves

    Suppose you have a Spring Boot app and you want it to talk to ChatGPT-5, DeepSeek, or any other model. Every provider (OpenAI, Anthropic, Google, Meta) hosts its models on its own cloud and exposes them as REST APIs. So technically you could just fire a RestTemplate call from your controller and be done.

    Spring Boot App→ REST call→ OpenAI API→ GPT model→ response

    The instructor's analogy: "If you eat a plain dosa versus a masala dosa, there will be a difference." A raw REST call is the plain dosa. It works, but you lose everything that makes building a real AI feature bearable.

    What Spring AI actually is

    Spring AI sits between your app and the model as an abstraction layer. It gives you a Fluent Java API — plain classes and interfaces — and behind the scenes it makes the HTTP calls, builds the JSON, parses the response, and handles the tokens.

    Your Controller / Service→ Spring AI (abstraction)→ Any AI Model
    Key benefit

    You can swap providers without changing a single line of business code. Move from OpenAI to Azure to Hugging Face to Ollama by changing the dependency and a few properties — because your code only ever touched the Spring AI API.

    What you get on top of "just calling an API"

    • Prompt management — prompts stored in external files, dynamic placeholders, role-based (system / user / assistant) prompts instead of hard-coded strings.
    • Embeddings & vector stores — chunk a document, generate embeddings, push them into PostgreSQL / Redis / MariaDB, all through one API.
    • RAG — because an LLM is stateless and knows nothing about your data, you must send context. Sending the whole document blows up your token bill, so RAG retrieves only the meaningful bits.
    • Chat history & memory — "remember the last 20 messages", stored in memory or in a DB.
    • Streaming — chunk-by-chunk responses, the way ChatGPT types.
    • Ecosystem integration — works naturally with Spring Data JPA/JDBC, Spring Security, Spring Cloud Config (for centrally managing AI keys).
    Video example

    The real-world case used throughout: a customer-support chatbot. A user asks "What's your refund policy?" — the model has no idea, so the app pulls the answer from a vector DB where the company's policies are stored, and hands it to the LLM as context.

    02

    Features of Spring AI

    09:50 — 20:55

    1. Multi-model & multi-provider support

    Azure OpenAI, OpenAI, Hugging Face, Ollama, Amazon Bedrock, Anthropic, DeepSeek, Mistral, Google Vertex AI — Spring AI supports nearly every popular provider. Switching = changing configuration.

    2. Spring-friendly API

    If you know Spring beans and injection, you already know how to use it. You inject a bean, call methods on it, chain them. The star of the show is ChatClient.

    Important nuance

    Saying "Spring gives you a ChatClient bean" is technically incorrect. What you actually get injected is ChatClient.Builder. You then call .build() on it to get your ChatClient. This distinction is repeated many times in the course.

    3. Prompt management

    Prompts get big and dynamic. Spring AI lets you keep them in external .st files (String Template) with placeholders, instead of concatenating strings in Java.

    At runtime, {name} is replaced with whatever you pass — "Durgesh", "Sahil", anything. Same template, reusable forever.

    4. Embeddings & vector store support

    You don't split documents into chunks yourself, you don't write insert statements. The VectorStore API chunks the text, represents it as Documents, generates embeddings and persists them — into PostgreSQL, Redis, MariaDB, Qdrant, Pinecone, and more.

    5. RAG (Retrieval Augmented Generation)

    Stated plainly in the video: the LLM is stateless and knows nothing about your private data. You could stuff the entire context into the prompt — but a large prompt burns tokens, costs money, and eventually breaks the context window. RAG stores everything in a vector DB, retrieves only the relevant slice, and adds that to the prompt.

    Store data in Vector DB→ Retrieve relevant chunks→ Augment prompt→ LLM generates

    6. Chat history & memory

    Automatic. You just declare "remember the last 20 conversations" and where to keep them — temporary memory or a database.

    7. Streaming responses

    The model does not produce the full answer at once. It emits tokens progressively. Spring AI exposes that as a reactive stream so your UI can type it out live.

    8. Spring ecosystem integration

    REST APIs, Spring Security, Spring Data JPA / JDBC, Spring Cloud Config for centrally managing AI keys — all still yours.

    ChatClient API

    1:22:45 — 1:31:32

    ChatClient is described as "a helper class that makes it super easy to talk to the AI". Technically it's an interface; you always work with its implementation (DefaultChatClient), which Spring AI builds for you.

    What it hides

    • Building the raw HTTP request and choosing the base API URL
    • Serialising your prompt into the provider's JSON format
    • Parsing the JSON response back
    • Token handling and formatting

    You just call methods, like any normal Spring service, and get a response back.

    Feature 1 — Fluent API

    The instructor's phrase: "calling it is like butter" — one method, then another, then another.

    SystemYou, the developerRules that steer behaviour — "You are a helpful assistant"
    AssistantThe LLMThe reply that comes back

    07

    Core AI Concepts

    1:52:19 — 2:21:55

    Models

    Tools trained on huge amounts of data that generate text, images, speech or embeddings. Spring AI supports text, image, audio and embedding models. The models you'll use (GPT, DeepSeek, Llama) are pre-trained — you query, they answer.

    ChatGPT ≠ the model

    An important clarification made in the video: the ChatGPT website is a wrapper around the model. It pre-processes your input, calls tools, runs web search, post-processes the reply, and manages memory. The model itself does none of that.

    Prompts

    Everything you send to the model. In Spring AI a prompt can carry placeholders — like ? in a JDBC prepared statement — filled at runtime, making the prompt reusable.

    Tokens — the concept everything else depends on

    A token is the smallest piece of text an AI model understands. Before anything happens, your prompt is tokenized.

    Prompt→ Tokens (each with an ID)→ Vectors→ Neural network→ Predict next token→ Output

    A token can be a whole word, a part of a word, or punctuation. Example from the video: "unbelievable" may become one token, or split into un / believe / able — it depends on the algorithm. On the OpenAI Tokenizer demo, "what is java?" = 4 tokens, 13 characters.

    Rule of thumb

    ~4 characters ≈ 1 token in common English. ~75 words ≈ 100 tokens.

    Why tokens matter — two reasons

    1. Cost. Billing is per million input tokens and per million output tokens. More text → more tokens → more money. Cost is directly proportional.
    2. Limit. Every model has a context window — the max tokens it can process at once. Newer models: ~400K context / 128K max output. Older ones were far smaller. You cannot send more context than the window allows.

    Embeddings

    Embeddings turn text, images or video into vectors — arrays of numbers. Critically, these vectors capture meaning, not just exact words.

    The king / queen example

    Think of Google Maps in 3D. "King" and "queen" land close together because they're related. "King" and "car" land far apart. Closeness is what lets the model predict the next token, and what lets a vector DB do similarity search.

    Used for: semantic search (meaningful, not keyword matching) and RAG. Similarity is measured mathematically — cosine similarity or Euclidean distance.

    Structured Output

    By default an AI returns plain text. Even when it looks like JSON it's a String — you can see the surrounding double quotes. That's a problem inside a real program, where you need a Java object to validate and pass around. And the model might produce invalid JSON, or drop a field entirely.

    Spring AI's structured output converters fix this. They:

    • Inject special instructions into the prompt describing the exact keys and types you want
    • Validate the returned JSON
    • Convert it into a real Java object / DTO / POJO
    • Retry if the output is invalid

    Ask for "a user object with name and email" — plain text gives you a String; structured output gives you a User object. Implementation is in Chapter 09.

    Prompt Templates & Message Roles

    3:26:24 — 4:24:09

    The four roles

    RoleWho sends itWhat it does
    userEnd userThe actual query — "What is a JS Promise?"
    systemDeveloperRules, behaviour, identity — "You are an expert JS assistant"
    assistantThe LLMEvery reply you receive is of this role
    tool / functionTool callingNot supported by every model — check yours
    Model support varies

    Almost every model supports user. GPT supports all four. Gemini and others vary. Always verify which roles your chosen model accepts.

    Why you can't send the raw user prompt

    The user types "In what logic should I write a program for prime numbers?" — but you're building a Java-only assistant, and the model happily answers in Python. So you must modify the prompt before sending it, adding context and constraints.

    Don't concatenate strings

    You can do systemText + query + "Now reply for this question" — but with several variables it becomes unreadable and error-prone. That's what templates are for.

    Approach A — Fluent API (easiest, use this most of the time)

    Multiple parameters — either chain .param() calls or pass a Map:

    Bug fixed live

    "Attribute techName is not defined" — the placeholder name in the template and the key in .param() must match exactly, including spelling.

    Approach B — Step-by-step with PromptTemplate

    Four explicit steps: create template → render → build message → build prompt.

    render() vs createMessage()

    render() returns a String. createMessage() returns a proper Message object. If you're combining several role-specific messages inside one Prompt, you need createMessage() — a Prompt cannot take multiple raw Strings.

    Role-specific templates

    There is a SystemPromptTemplate (and Assistant / Function variants) but no UserPromptTemplate — the plain PromptTemplate is the user template.

    Template renderers

    Rendering is done by a TemplateRenderer. The default is StTemplateRenderer, which uses the StringTemplate (ST4) library and { } delimiters. Implementations available: StTemplateRenderer and NoOpTemplateRenderer. You can supply your own if you want different delimiters — say angle brackets instead of curly braces.

    Reading prompts from files

    Hard-coding big prompts inside Java is bad. Put them in src/main/resources/prompts/ as .st files.

    Import trap

    IntelliJ will happily import jakarta.annotation.Resource. You need org.springframework.core.io.Resource. Always check your imports here.

    Test failing with "incorrect API key"

    When running JUnit tests, the run configuration is separate from your application's. The OPENAI_API_KEY environment variable must be added to the test run configuration too, otherwise you get an invalid-API-key error.

    12

    Advisors — Interceptors for AI Calls

    4:24:09 — 4:44:56

    Advisors are middleware / interceptors. They sit between the ChatClient and the LLM and run on the way out and on the way back.

    User→ ChatClient→ Advisors (pre)→ LLM→ Advisors (post)→ User
    Golden rule

    You may add to a prompt inside an advisor, but the meaning must not change. Enriching a simple prompt to produce a better answer is good. Mangling it until it's meaningless defeats the point.

    Two interfaces, and why there are two

    InterfaceMethod to overrideUsed when
    CallAdvisoradviseCall(...)Blocking .call()
    StreamAdvisoradviseStream(...)Reactive .stream()

    Because ChatClient works both ways, an advisor that should support both must implement both.

    Built-in advisors

    AdvisorPurpose
    SimpleLoggerAdvisorLogs the full request and response
    SafeGuardAdvisorBlocks the call if the input contains sensitive words
    MessageChatMemoryAdvisorInjects conversation history as role-based messages
    PromptChatMemoryAdvisorInjects history as plain text
    VectorStoreChatMemoryAdvisorMemory backed by a vector store
    QuestionAnswerAdvisorAutomatic RAG — Chapter 19
    RetrievalAugmentationAdvisorModular / advanced RAG — Chapter 20

    Registering advisors — two scopes

    Logs won't appear unless you enable them

    SimpleLoggerAdvisor logs at DEBUG level. You must turn it on:

    What the logs actually show you

    This is the payoff — you finally see exactly what leaves your app:

    • The system message, fully resolved from your .st file
    • The user message with placeholders already substituted
    • Model options — model name, temperature 0.3, max tokens 200, streamUsage false
    • The response with messageType: ASSISTANT, finish reason, content filters

    SafeGuardAdvisor in action

    Configured with the word "games", sending "card games" never reaches the LLM. You get the default refusal message instead — "I'm unable to respond to that due to sensitive content, could we rephrase and discuss…". Practical use: block a keyword list for your chatbot.

    Advisor ordering

    Each advisor has an order (SimpleLoggerAdvisor is 0). Higher order = higher priority = runs first. If two advisors share the same order there is no guarantee which runs first. Advisors chain via advisorChain.nextCall(request) — when the chain is exhausted, the request finally goes to the LLM.

    Custom Advisor — Token Counter

    4:44:56 — 5:06:54

    Use case: you're building an app where users pay by token. You need to know how many tokens every request consumed so you can debit their balance.

    The three token types

    TokenWhat it counts
    Prompt tokens Everything you send: system messages + user messages + chat history + tool/function definitions + JSON mode instructions
    Completion tokens Everything the model generates. ~150 words ≈ ~200 tokens
    Total tokens prompt + completion — this is what you're billed on

    Writing the advisor

    Implement both CallAdvisor and StreamAdvisor, override getName() and getOrder(), then forward the request down the chain.

    Bug from a later chapter — worth knowing now

    When streaming was added, the app broke. Cause: adviseStream had been left returning null, so nothing came back. The fix is exactly the line above — always forward with streamAdvisorChain.nextStream(...).

    Real output

    Query "Java new features" → prompt tokens 43, completion tokens 200 (capped by max-tokens), total 243. Input tokens are billed at the input rate, output tokens at the output rate — add both to get the cost.

    Execution order observed

    With SimpleLoggerAdvisor and TokenPrintAdvisor registered, the logger ran first on the way out — and last on the way back. Advisors unwind in reverse order, like a stack.

    14

    Streaming Responses

    5:06:54 — 5:24:56

    Blocking vs streaming

    Blocking: the user sends a request, your app waits for the entire answer (maybe minutes), and only then responds. Both the app and the user are blocked. Demonstrated in Postman and in the browser — the tab just spins.

    User→ App→ LLM (5 min…)→ full answer→ User

    Streaming: the model emits chunks as it generates them; you forward each chunk immediately. That's the ChatGPT typing effect.

    User→ App→ chunk · chunk · chunk→ User sees it live

    Controller — return a Flux

    Service — swap .call() for .stream()

    What .stream() can give you

    .content() → Flux<String> · .chatResponse() → Flux<ChatResponse> · .chatClientResponse() → Flux<ChatClientResponse>. Pick based on how much detail you need.

    The exception you'll hit

    Streaming threw an error because the custom TokenPrintAdvisor implemented adviseStream as return null;. Any custom advisor must forward the stream properly (Chapter 13). Advisors sit in both paths.

    Side-by-side demo

    Two URLs on port 8082: /chat waits and dumps everything at once; /stream-chat paints text progressively. Removing the max-token cap makes the difference obvious. Postman shows a "Receiving response…" indicator; the browser renders live.

    Verdict from the video: streaming is the better default. A blocked user leaves your site.

    Chat Memory

    5:24:56 — 6:09:20

    LLMs are stateless

    Request 1: "My name is John" → the model uses it, because it's in that request. Request 2: "What's my name?" → "I don't know your name." Every interaction is treated as brand new.

    So how does ChatGPT remember?

    It doesn't — the ChatGPT application does. It's a wrapper that stores your conversation and re-sends it as context on every request. Spring AI gives you the same capability.

    Examples of concernsLast N messages, token limit, time windowMemory, database, vector store
    TypeInterfaceInterface
    Default implMessageWindowChatMemoryInMemoryChatMemoryRepository

    MessageWindowChatMemory keeps a rolling window — default 20 messages. When new messages arrive, the oldest are evicted. It holds a reference to a repository and delegates all actual persistence to it.

    InMemoryChatMemoryRepository stores everything in a ConcurrentHashMap<String, List<Message>> — key = conversation ID, value = the message list. Close the app and it's gone.

    Don't crank the window up

    Every remembered message is re-sent with each request, so it lands in your prompt tokens. Bigger window → bigger bill. Keep it tight.

    Wiring it up

    Use the builder, not new

    MessageChatMemoryAdvisor's constructor is private — MessageChatMemoryAdvisor.builder(chatMemory).build() is the only way. ChatMemory itself is auto-configured, so you can just inject it.

    What memory actually does to your request

    Turn on SimpleLoggerAdvisor and the mechanism is completely visible. Say "My name is Amit", then ask "What is my name?". The second request contains:

    1. The system message
    2. "My name is Amit" — the earlier user message, replayed automatically
    3. The earlier assistant message (the model's previous reply)
    4. Finally, the new user message "What is my name?"

    Nothing magical — the whole history is simply prepended to the prompt.

    The hidden cost, measured

    Asking a two-word question after some history consumed ~1300 total tokens — 874 of them prompt tokens, purely from replayed history. Memory is convenient and expensive. RAG (Chapter 18) exists partly to solve this.

    RAG — Concepts, Vectors & Vector Databases

    6:54:41 — 7:20:23

    Why chat memory isn't enough

    Storing conversations in a DB works for limited context. But imagine a chatbot for "Substring Technologies" that must answer questions about company policies. That data is huge. You can't send it all with every prompt because:

    • More context → more tokens → higher bill
    • Every model has a hard context window — you physically cannot exceed it

    What RAG stands for

    LetterStands forWhat happens
    RRetrievalFetch the most relevant chunks from the database
    AAugmentedAttach those chunks to the prompt as context
    GGenerationThe LLM generates an answer grounded in that context

    The full flow

    1. User query→ 2. App→ 3. Similarity search in Vector DB→ 4. Context + query → LLM→ 5. Answer→ 6. User
    The prerequisite step

    Before any of this, you must load your data into the vector DB — chunk it, embed it, store it. That's the ETL pipeline (Chapter 21).

    What problems RAG solves

    • Limited memory — models are trained on public data, never on your private data
    • Training cutoff — they can't know anything recent
    • Context limit — you can't paste a whole book into a prompt
    • Hallucination — grounding in retrieved facts improves accuracy and trust

    Vectors

    In ML terms, a vector is simply an array of numbers (an n-dimensional matrix) that represents some piece of information — text, image, audio, video. Those numbers are the embeddings.

    Vector databases

    Regular databases (MySQL, Postgres) store structured rows and search by exact property. Vector databases store embeddings and search by similarity.

    The 3D-space analogy

    Picture objects plotted on x/y/z axes. Similar items cluster together; unrelated items sit far apart. Search for one embedding and the DB returns its nearest neighbours — ranked by similarity, e.g. the top 5. Under the hood it's maths: cosine similarity or Euclidean distance.

    Supported vector stores in Spring AI: Azure AI Search, Chroma, MariaDB, Neo4j, Oracle, PgVector, Pinecone, Qdrant, Redis, and more.

    How a query is answered

    1. The user's query is converted into an embedding vector
    2. That vector is searched against the vector DB
    3. The top-K most similar chunks come back (the "knowledge")
    4. Knowledge + original query are sent to the LLM
    5. The LLM answers from that knowledge

    Advanced RAG — Modular Pipeline

    8:31:42 — 9:43:25

    Spring AI implements a modular RAG architecture (inspired by the "Modular RAG" paper). Instead of one search, the flow is broken into four phases, each pluggable.

    Pre-Retrieval→ Retrieval→ Post-Retrieval→ Generation

    Phase 1 — Pre-Retrieval (process the query before searching)

    ComponentImplementationWhat it does
    Query TransformerRewriteQueryTransformer Rewrites a verbose/ambiguous query into a clean one
    TranslationQueryTransformerTranslates the query into a target language
    CompressionQueryTransformerCompresses conversation history into one standalone query
    Query ExpanderMultiQueryExpander Turns 1 query into N variations to cast a wider net
    Rewrite example

    User types "I'm studying ML, what is an LLM?" → rewritten to "Large Language Model definition". In the live demo "what is java" became "what is java programming language" — more context, better vector matches.

    Phase 2 — Retrieval

    • DocumentRetriever → VectorStoreDocumentRetriever does the similarity search with optional metadata filtering and threshold.
    • DocumentJoiner → ConcatenationDocumentJoiner merges results from multiple queries / multiple sources and removes duplicates.

    Phase 3 — Post-Retrieval

    DocumentPostProcessor — clean, re-rank, compress or drop irrelevant chunks before they reach the LLM. No built-in implementation ships; write your own process() method.

    Phase 4 — Generation

    QueryAugmenter → ContextualQueryAugmenter merges the retrieved documents into the query and hands the final prompt to the model.

    Putting it together

    Two errors hit live

    1. "vectorStore cannot be null" — VectorStoreDocumentRetriever needs .vectorStore(...) explicitly.
    2. The query expander also calls the LLM, so it needs a chatClientBuilder too — obtained via chatClient.mutate().clone().

    What the debugger showed, step by step

    Breakpoint inside RetrievalAugmentationAdvisor.before():

    1. Original query created: "what is java"
    2. Transformed by RewriteQueryTransformer → "what is java programming language"
    3. Expanded by MultiQueryExpander into 4 queries — including "What are the key features and uses of the Java programming language?" and "How does Java compare to other programming languages?"
    4. Each expanded query hit the vector DB → ~3 documents each
    5. ConcatenationDocumentJoiner merged them into one deduplicated list
    6. ContextualQueryAugmenter built the final prompt: context + rules + user query
    Translation demo

    With TranslationQueryTransformer set to "hindi", the log showed the instruction "Given a user query, translate it into Hindi. If the query is already in Hindi, return it unchanged. Do not add explanations." — then three expanded queries in Hindi. Very useful when your vector data is in one language and users type in another.

    Beyond vector stores

    Want documents from the web instead of a DB? Implement DocumentRetriever and override retrieve(). Everything upstream and downstream is unchanged — the pipeline has no idea where the documents came from.

    ETL Pipeline — Getting Real Documents In

    9:43:25 — 10:26:23

    Everything in Chapter 19 loaded hard-coded Strings. Real data lives in PDFs, JSON, DOCX and HTML. The ETL pipeline is how you move raw files into a vector store.

    Source
    (PDF/JSON/DOCX)    → DocumentReader
    (Extract)    → DocumentTransformer
    (Transform / chunk)    → DocumentWriter
    (Load)    → Vector DB

    What a Document is

    A Document is not just text. It holds content, metadata, and optionally media references. Every stage of the pipeline passes around a List<Document>.

    E — DocumentReader

    ReaderReadsExtra dependency
    JsonReaderJSON filesnone
    TextReaderPlain textnone
    PagePdfDocumentReaderPDF — one document per pagespring-ai-pdf-document-reader
    ParagraphPdfDocumentReaderPDF — one document per paragraphspring-ai-pdf-document-reader
    TikaDocumentReaderDOCX, PPTX, HTML and morespring-ai-tika-document-reader
    Result

    A 2-page PDF read with withPagesPerDocument(1) produced exactly 2 Documents, each with its own ID and the page's extracted text. PagePdfDocumentReader uses Apache PDFBox under the hood.

    T — DocumentTransformer (chunking)

    You never insert a huge document as one chunk — it won't fit the model's context and matches poorly. TokenTextSplitter splits by token count.

    Chunk size matters

    Same PDF: default config → 3 chunks. Chunk size 300 → 6 chunks. Smaller chunks are more specific, so similarity search returns more relevant matches — at the cost of more rows.

    Other transformers: ContentFormatTransformer, KeywordMetadataEnricher, SummaryMetadataEnricher.

    L — DocumentWriter

    VectorStore extends DocumentWriter — it acts as the sink. Implementations include MariaDBVectorStore, SimpleVectorStore and FileDocumentWriter.

    Error you'll see

    The write failed until the API key was added to the test run configuration. Reason: before a chunk can be stored it must be converted into an embedding, and that calls the embedding model over the network.

    Tool Calling — Giving the LLM Superpowers

    10:26:23 — 11:27:38

    The limitation being solved

    Ask a plain LLM "What is today's date?" and it answers with its training cutoff — in the video, October 3, 2023, when the real date was 2025. It has no real-time access. Ask "Set an alarm" and it can't act at all.

    Two kinds of tools

    TypePurposeExamples
    InformationRetrieve dataCurrent date, weather, DB query, stock price
    ActionDo somethingSet an alarm, send an email, insert a row, add to cart

    How tool calling actually works

    1. Request arrives at your Spring AI backend
    2. Your query plus the tool descriptions (name, description, parameter schema) go to the LLM
    3. The LLM decides a tool is needed and replies with the tool name + parameters
    4. Your application executes the tool — the LLM never runs code
    5. The result is sent back to the LLM, which generates the final natural-language answer
    6. That answer is returned to the user
    Where the tool runs

    Inside your Spring Boot app. The LLM only decides which tool and with what arguments. Setting returnDirect = true on @Tool skips step 5 and returns the raw result straight to the user.

    Example 1 — Date/time tool (information + action)

    What the model can now do

    "What is today's date?" → correct date. "What is the date tomorrow?" → correct. "What was the date last Sunday?" → correct. "My DOB is 1998, what's my current age?" → 27. "What will my age be in 2050?" → 52. One small tool, and the LLM reasons on top of it.

    Ask something unrelated — "top five programming languages" — and the logs show no tool call at all. It only calls a tool when it needs one.

    Example 2 — A real external API (weather)

    Sign up at weatherapi.com for a free key, store it in properties, and expose it as a tool.

    The impressive bit

    "Compare the weather in Delhi and Lucknow today" → the logs show the weather tool called twice, once per city, then the LLM compared the two results itself: "Delhi is significantly cooler than Lucknow today…". Nobody wrote comparison logic.

    @Tool attributes

    AttributeMeaning
    nameTool name. Defaults to the method name
    descriptionWhat the LLM reads. Defaults to the method name — always write one
    returnDirecttrue = send the result straight to the client, skip the second LLM round-trip. Default false
    resultConverterCustom class to convert the tool result into a String for the model
    Two approaches

    Declarative — @Tool / @ToolParam (what's shown here) and Programmatic — low-level ToolCallback implementations. The declarative style covers almost everything.

    Where tool calling shines

    • Data queries — "What are today's sales?" → the LLM builds the query, the tool runs it
    • Data actions — "Create an expense for today" → row inserted automatically
    • E-commerce — "Find the cheapest iPhone", "Add it to my cart"
    • Customer support — send an email, create an invoice

    Combine RAG (context) + chat memory (conversation) + tool calling (actions) and you have a genuine AI agent.
