1. SQL Basics

Foundation

Every SQL interview starts here. Make sure these are second nature:

  • Database, Table, Row, Column — the basic building blocks of a relational database.
  • Primary Key — uniquely identifies a row, cannot be NULL, one per table.
  • Foreign Key — a column referencing another table's primary key, enforcing referential integrity.
  • DDL (structure): CREATE, ALTER, DROP, TRUNCATE
  • DML (data): INSERT, UPDATE, DELETE, SELECT
  • Filtering: WHERE, DISTINCT, AND/OR/NOT, IN, BETWEEN, LIKE, IS NULL
  • Sorting/limiting: ORDER BY, LIMIT
SELECT name, salary
FROM employee
WHERE salary > 50000
ORDER BY salary DESC;
⭐ Logical execution order (a favorite interview question):
FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT

2. Aggregate Functions & GROUP BY

Core

Master COUNT(), SUM(), AVG(), MIN(), MAX() — and remember that all of them (except COUNT(*)) ignore NULLs.

SELECT department, AVG(salary)
FROM employee
GROUP BY department
HAVING AVG(salary) > 50000;
⭐ WHERE vs HAVING
WHERE filters rows before grouping.
HAVING filters groups after GROUP BY — this is why aggregate functions can't go in WHERE.

3. JOINs

Most Important

One of the most heavily tested topics. Master INNER, LEFT, RIGHT, FULL OUTER, SELF, and CROSS joins.

SELECT e.name, d.department_name
FROM employee e
INNER JOIN department d
ON e.department_id = d.id;

Classic problem — employees with no department:

SELECT e.*
FROM employee e
LEFT JOIN department d
ON e.department_id = d.id
WHERE d.id IS NULL;
⭐ Gotcha: filtering the right-hand table of a LEFT JOIN in WHERE silently turns it into an INNER JOIN. Put that condition in the ON clause instead if you want to keep unmatched rows.

4. Subqueries

Core
  • Scalar subquery — returns exactly one value.
  • IN — matches against a list from a subquery.
  • EXISTS — tests for existence; usually faster and NULL-safe compared to NOT IN.
  • Correlated subquery — references the outer query, re-runs per row.
SELECT *
FROM employee
WHERE salary > (SELECT AVG(salary) FROM employee);

SELECT *
FROM employee e
WHERE EXISTS (
  SELECT 1 FROM department d WHERE d.id = e.department_id
);
⭐ Gotcha: NOT IN (subquery) returns zero rows if the subquery result contains any NULL. Use NOT EXISTS instead.

5. Constraints

Core

PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL, CHECK, DEFAULT.

Know the classic distinctions: Primary Key vs Unique Key, Primary Key vs Foreign Key, and that a table can have only one primary key (though it can be composite).

6. Keys

Core

Primary, Foreign, Candidate, Super, Composite, Alternate keys.

Super Key ⊇ Candidate Key (minimal super key) → one candidate key becomes the Primary Key, the rest are Alternate Keys. A Composite Key spans multiple columns.

7. SQL Functions

Practical

String: UPPER(), LOWER(), LENGTH(), CONCAT(), SUBSTRING(), TRIM(), REPLACE()

Date: CURRENT_DATE, CURRENT_TIMESTAMP, EXTRACT(), DATE_TRUNC()

Numeric: ROUND(), CEIL(), FLOOR(), ABS()

Exact syntax varies between PostgreSQL / MySQL / Oracle — always confirm the dialect in an interview before writing date functions.

8. CASE Expressions

Practical 
SELECT name, salary,
       CASE
           WHEN salary >= 100000 THEN 'High'
           WHEN salary >= 50000 THEN 'Medium'
           ELSE 'Low'
       END AS salary_category
FROM employee;

Also useful inside aggregates for conditional aggregation / pivoting:

SELECT department_id,
  SUM(CASE WHEN gender='F' THEN 1 ELSE 0 END) AS female_count
FROM employee GROUP BY department_id;

9. Set Operations

Core

UNION, UNION ALL, INTERSECT, EXCEPT

⭐ UNION vs UNION ALL: UNION removes duplicates (sorts/dedupes → slower). UNION ALL keeps everything and is faster.

10. CTE (Common Table Expressions)

Modern SQL 
WITH high_salary AS (
    SELECT * FROM employee WHERE salary > 100000
)
SELECT * FROM high_salary;

Recursive CTE for hierarchical data (org charts, category trees):

WITH RECURSIVE org_chart AS (
  SELECT id, name, manager_id, 1 AS level
  FROM employee WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, e.manager_id, oc.level + 1
  FROM employee e JOIN org_chart oc ON e.manager_id = oc.id
)
SELECT * FROM org_chart;

11. Window Functions

⭐ Interview-level

This is where preparation becomes interview-level. Master ROW_NUMBER(), RANK(), DENSE_RANK(), PARTITION BY, LAG(), LEAD(), FIRST_VALUE(), LAST_VALUE(), and running SUM()/AVG().

SELECT name, department, salary,
       RANK() OVER (
           PARTITION BY department
           ORDER BY salary DESC
       ) AS rank
FROM employee;
⭐ Classic: "Find the second-highest salary in each department" is almost always solved with DENSE_RANK() + PARTITION BY — see Q42 in the practice set.
FunctionBehavior on ties
ROW_NUMBER()Always unique (1,2,3,4)
RANK()Ties share rank, gaps after (1,2,2,4)
DENSE_RANK()Ties share rank, no gaps (1,2,2,3)

12. Normalization

Design

1NF → 2NF → 3NF → BCNF → Denormalization. Don't memorize definitions blindly — understand why normalization exists: eliminating redundancy and update/insert/delete anomalies.

Example: instead of storing department_name and department_manager directly on every Employee row (a transitive dependency), split into separate Employee and Department tables.

13. Transactions

⭐ Backend-critical

ACID: Atomicity, Consistency, Isolation, Durability.

Control: COMMIT, ROLLBACK, SAVEPOINT

Isolation levels (weakest → strongest): Read Uncommitted → Read Committed → Repeatable Read → Serializable

AnomalyDescriptionPrevented from
Dirty ReadReads uncommitted dataRead Committed+
Non-repeatable ReadSame row changes between readsRepeatable Read+
Phantom ReadNew rows appear on re-querySerializable

This connects directly to Spring:

@Transactional(isolation = Isolation.READ_COMMITTED)
public void transferFunds(...) { ... }

14. Indexes

⭐ Backend-critical

Extremely important for backend interviews.

  • An index is a B-Tree (usually) mapping values → row locations for fast lookups.
  • Speeds up SELECT, but slows down INSERT/UPDATE/DELETE (index maintenance overhead).
  • Clustered index defines physical row order (one per table); non-clustered is a separate lookup structure (many per table).
  • Composite index — order matters! Only a leftmost prefix is usable.
  • Covering index — contains every column the query needs → index-only scan.
  • Selectivity — high-selectivity columns benefit most from indexing.
CREATE INDEX idx_employee_email
ON employee(email);

15. Views

Practical 
CREATE VIEW employee_details AS
SELECT e.name, d.department_name
FROM employee e JOIN department d ON e.department_id = d.id;

View — virtual, recomputed each query. Materialized View — physically stored, faster reads, needs refreshing.

16. Stored Procedures / Functions / Triggers

Lower priority

Lower priority for Java backend interviews, but know the basics: Stored Procedure, SQL Function, Trigger, Cursor.

CREATE TRIGGER trg_audit_salary
AFTER UPDATE OF salary ON employee
FOR EACH ROW
EXECUTE FUNCTION log_salary_change();

17. Query Optimization

⭐ Backend-critical

Especially useful since you work with PostgreSQL.

  • EXPLAIN / EXPLAIN ANALYZE — shows the planned (or actual) execution strategy.
  • Sequential Scan vs Index Scan — full table read vs targeted lookup.
  • Nested Loop vs Hash Join — row-by-row lookup vs in-memory hash probing.
  • Cost and Cardinality — the optimizer's internal estimate of resource usage and row counts, used to choose the cheapest plan.

18. Database Design

Design

One-to-One, One-to-Many, Many-to-Many relationships. Many-to-Many always needs a junction/bridge table.

Student ──Many-to-Many── Course

  →  student
     course
     student_course   (junction table)

Also know: foreign keys, cascading (ON DELETE CASCADE / SET NULL / RESTRICT), and referential integrity.

SQL Basics

Q1 What is the difference between a Primary Key and a Unique Key?

Answer: A Primary Key uniquely identifies each row and does not allow NULLs; a table can have only one. A Unique Key also enforces uniqueness but allows one NULL (in most RDBMS) and a table can have multiple Unique Keys.

Why / details: Primary Key = uniqueness + NOT NULL + one per table (usually clustered index). Unique Key = uniqueness only, multiple allowed, can accept a NULL.

Q2 What is the difference between DELETE, TRUNCATE and DROP?

Answer: DELETE removes rows (can use WHERE, is logged, can be rolled back), TRUNCATE removes all rows quickly (minimal logging, resets identity, hard/impossible to roll back in some DBs), DROP removes the entire table structure and data.

Why / details: Interviewers want you to mention: DDL vs DML, rollback behavior, triggers (DELETE fires them, TRUNCATE usually doesn't), and speed (TRUNCATE is fastest since it deallocates data pages instead of logging row by row).

Q3 Difference between WHERE and HAVING?

Answer: WHERE filters individual rows before grouping/aggregation; HAVING filters groups after GROUP BY has been applied.

Why / details: You cannot use an aggregate function like AVG(salary) inside WHERE because grouping hasn't happened yet — that's exactly why HAVING exists.

SELECT department, AVG(salary)
FROM employee
GROUP BY department
HAVING AVG(salary) > 50000;
Q4 What does the DISTINCT keyword do, and what is its performance cost?

Answer: DISTINCT removes duplicate rows from the result set. It typically requires a sort or hash operation internally, which adds CPU/memory cost, especially on large unindexed columns.

Why / details: In interviews, mention that DISTINCT across many columns can be expensive and sometimes GROUP BY or EXISTS achieves the same result more efficiently.

Q5 What is the difference between CHAR and VARCHAR?

Answer: CHAR is fixed-length and pads with spaces to the declared length; VARCHAR is variable-length and only stores the actual characters (plus a small length prefix).

Why / details: CHAR can be marginally faster for fixed-size data (like a 2-letter state code) because rows are predictable in size; VARCHAR saves space when lengths vary a lot.

Q6 What is a NULL value and how does it behave in comparisons?

Answer: NULL represents an unknown/missing value. Any comparison with NULL using =, <>, etc. returns UNKNOWN (not TRUE or FALSE), so you must use IS NULL / IS NOT NULL.

Why / details: A common trap: `WHERE column <> NULL` never matches anything — this is a classic interview gotcha question.

Q7 What is the order of execution of a SQL query (logical query processing order)?

Answer: FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT/OFFSET.

Why / details: This is one of the most asked conceptual questions — it explains why you can't use a SELECT alias in WHERE, but you can in ORDER BY.

Q8 What is the difference between UNION and JOIN?

Answer: JOIN combines columns from two or more tables horizontally based on a related column. UNION stacks the result sets of two queries vertically, requiring the same number and compatible types of columns.

Why / details: JOIN increases the number of columns per row; UNION increases the number of rows.

Q9 What is an alias and why is it used?

Answer: An alias is a temporary name given to a table or column (using AS) to make queries more readable or to disambiguate columns from multiple tables, especially in self-joins.

SELECT e.name AS employee_name, m.name AS manager_name
FROM employee e
JOIN employee m ON e.manager_id = m.id;
Q10 What's the difference between LIKE '%abc%' and LIKE 'abc%'?

Answer: '%abc%' matches 'abc' anywhere in the string (leading wildcard, cannot use an index efficiently). 'abc%' matches strings starting with 'abc' and CAN use a B-Tree index (index seek).

Why / details: This is an important index-usage question — leading wildcards force a full scan in most databases.

Aggregate Functions

Q11 Do aggregate functions ignore NULLs?

Answer: Yes. COUNT(column), SUM, AVG, MIN, MAX all ignore NULL values, except COUNT(*) which counts all rows regardless of NULLs.

Why / details: COUNT(column) vs COUNT(*) is a very common trick question.

Q12 Find departments having more than 5 employees.

Answer: Group employees by department and filter groups with HAVING COUNT(*) > 5.

SELECT department_id, COUNT(*) AS emp_count
FROM employee
GROUP BY department_id
HAVING COUNT(*) > 5;
Q13 Find the second-highest salary (without window functions).

Answer: Use a subquery that excludes the maximum salary and take the max of the remainder, or use LIMIT/OFFSET.

Why / details: This classic works everywhere, including MySQL/PostgreSQL/Oracle without window function support.

SELECT MAX(salary) AS second_highest
FROM employee
WHERE salary < (SELECT MAX(salary) FROM employee);

-- Alternative (Postgres/MySQL):
SELECT DISTINCT salary
FROM employee
ORDER BY salary DESC
LIMIT 1 OFFSET 1;
Q14 Find the Nth-highest salary generically.

Answer: Use DISTINCT + ORDER BY DESC + LIMIT 1 OFFSET (N-1), or DENSE_RANK() for a version that handles ties correctly.

Why / details: OFFSET-based solutions don't handle salary ties well (two people with the same top salary count as one rank) — mention DENSE_RANK as the more correct interview answer.

SELECT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employee
) t
WHERE rnk = :N;
Q15 Find the highest salary in each department.

Answer: GROUP BY department_id and take MAX(salary) per group.

SELECT department_id, MAX(salary)
FROM employee
GROUP BY department_id;
Q16 Find employees whose salary is above the company average.

Answer: Compare each employee's salary to a scalar subquery computing the overall AVG(salary).

SELECT * FROM employee
WHERE salary > (SELECT AVG(salary) FROM employee);
Q17 Why can't you filter on an aggregate result using WHERE?

Answer: Because WHERE is evaluated before GROUP BY/aggregation happens in the logical execution order, so the aggregate value doesn't exist yet at that stage — you must use HAVING.

Why / details: Ties back to the logical query-processing order question.

Q18 Find customers who placed more than 3 orders.

Answer: Group orders by customer_id and filter with HAVING COUNT(*) > 3.

SELECT customer_id, COUNT(*) AS order_count
FROM orders
GROUP BY customer_id
HAVING COUNT(*) > 3;

Joins

Q19 Explain INNER JOIN vs LEFT JOIN vs RIGHT JOIN vs FULL OUTER JOIN.

Answer: INNER JOIN returns only matching rows from both tables. LEFT JOIN returns all rows from the left table plus matches from the right (NULLs where no match). RIGHT JOIN is the mirror of LEFT. FULL OUTER JOIN returns all rows from both sides, matched where possible, NULLs elsewhere.

Why / details: Draw this as a Venn diagram mentally when explaining in an interview — it shows you understand the visual intuition.

Q20 What is a self join and when would you use one?

Answer: A self join joins a table to itself, typically to compare rows within the same table — e.g., finding employees and their managers who live in the same 'employee' table.

SELECT e.name AS employee, m.name AS manager
FROM employee e
JOIN employee m ON e.manager_id = m.id;
Q21 Find employees who don't belong to any department.

Answer: LEFT JOIN employee to department and filter where the department's key is NULL.

SELECT e.*
FROM employee e
LEFT JOIN department d ON e.department_id = d.id
WHERE d.id IS NULL;
Q22 Find employees earning more than their manager.

Answer: Self-join employee to itself on manager_id, then compare the two salary columns.

SELECT e.name AS employee, e.salary, m.name AS manager, m.salary AS manager_salary
FROM employee e
JOIN employee m ON e.manager_id = m.id
WHERE e.salary > m.salary;
Q23 What is a CROSS JOIN?

Answer: A CROSS JOIN produces the Cartesian product of two tables — every row from table A paired with every row from table B, with no join condition.

Why / details: Useful for generating combinations (e.g., all product/size pairs), but dangerous if used accidentally since it can explode row counts.

Q24 What is the difference between an implicit join (comma syntax) and explicit JOIN syntax?

Answer: Implicit joins list tables in FROM separated by commas and put the join condition in WHERE; explicit joins use the JOIN...ON syntax. They're logically equivalent but explicit JOIN is preferred for readability and to avoid accidentally forgetting the WHERE condition (which creates a CROSS JOIN).

Q25 Can you JOIN on a condition other than equality?

Answer: Yes — a non-equi join uses operators like <, >, BETWEEN instead of =, e.g., joining a sales table to a tax-bracket table where sale_amount BETWEEN low AND high.

Q26 How does a LEFT JOIN with a WHERE clause on the right table behave differently from a WHERE clause vs. putting the condition in the ON clause?

Answer: Putting a filter on the right table in WHERE effectively turns the LEFT JOIN into an INNER JOIN (because NULL rows fail the WHERE condition), whereas putting the same filter in ON preserves the LEFT JOIN's unmatched rows.

Why / details: This is a very common 'gotcha' interview question testing deep JOIN understanding.

Q27 What is the difference between JOIN and subquery-based filtering (e.g., IN vs JOIN)?

Answer: A JOIN combines and returns columns from both tables and can produce duplicate rows if the relationship is one-to-many; a subquery with IN/EXISTS just filters rows from one table and never duplicates rows. Optimizers often rewrite IN/EXISTS into semi-joins internally, so performance can be similar.

Q28 How would you find duplicate records in a table?

Answer: Group by the columns that define a duplicate and filter groups with HAVING COUNT(*) > 1.

SELECT email, COUNT(*)
FROM employee
GROUP BY email
HAVING COUNT(*) > 1;
Q29 How would you delete duplicate records, keeping only one copy?

Answer: Use a window function to rank duplicates and delete all but rank 1, or use a CTE with ROW_NUMBER().

WITH ranked AS (
  SELECT ctid, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn
  FROM employee
)
DELETE FROM employee
WHERE ctid IN (SELECT ctid FROM ranked WHERE rn > 1);
Q30 Find duplicate emails in a users table.

Answer: Group by email and filter for counts greater than one.

SELECT email, COUNT(*) AS cnt
FROM users
GROUP BY email
HAVING COUNT(*) > 1;
Q31 What happens if you JOIN two tables and forget the ON condition?

Answer: Without an ON condition, most databases either throw a syntax error (for explicit JOIN) or, with implicit comma-syntax, silently produce a CROSS JOIN — a Cartesian product of every row combination, which can be extremely large and slow.

Subqueries

Q32 What is a correlated subquery, and how is it different from a regular subquery?

Answer: A correlated subquery references a column from the outer query, so it re-executes once per outer row. A regular (non-correlated) subquery runs independently, once, and its result is reused.

Why / details: Correlated subqueries can be slow on large tables because of repeated execution — window functions or JOINs are often a faster alternative.

SELECT e.name FROM employee e
WHERE salary > (
  SELECT AVG(salary) FROM employee e2 WHERE e2.department_id = e.department_id
);
Q33 Difference between EXISTS and IN?

Answer: EXISTS checks whether a subquery returns any rows and stops at the first match (often faster with correlated subqueries and handles NULLs safely); IN compares a value against a list of subquery results and can behave unexpectedly if the subquery returns NULLs.

Why / details: A key gotcha: `WHERE x NOT IN (subquery)` returns no rows at all if the subquery result contains a NULL — NOT EXISTS doesn't have this problem.

Q34 What is a scalar subquery?

Answer: A subquery that returns exactly one row and one column, usable anywhere a single value is expected (e.g., in SELECT, WHERE, or comparisons).

SELECT name, salary,
  (SELECT AVG(salary) FROM employee) AS company_avg
FROM employee;
Q35 Can a subquery be used in the SELECT clause?

Answer: Yes — a scalar subquery can appear in SELECT to compute a per-row derived value, though it runs once per outer row unless the optimizer caches it, so it can be slower than an equivalent JOIN.

Q36 What's the difference between a subquery and a CTE?

Answer: Functionally they can be equivalent, but a CTE (WITH clause) is named and more readable, can be referenced multiple times in the same query without repeating the SQL, and (in some databases) can be recursive. A subquery is inline and single-use.

Q37 Find employees who earn the maximum salary in their department using a correlated subquery.

Answer: Compare each employee's salary to the MAX(salary) of employees in the same department.

SELECT * FROM employee e
WHERE salary = (
  SELECT MAX(salary) FROM employee e2 WHERE e2.department_id = e.department_id
);
Q38 What is a derived table (inline view)?

Answer: A subquery used in the FROM clause, treated as a temporary, unnamed (or aliased) table for the duration of the query.

SELECT dept_avg.department_id, dept_avg.avg_sal
FROM (
  SELECT department_id, AVG(salary) AS avg_sal
  FROM employee GROUP BY department_id
) dept_avg
WHERE dept_avg.avg_sal > 50000;
Q39 When would you prefer a JOIN over a subquery, or vice versa?

Answer: Prefer a JOIN when you need columns from both tables in the result and the optimizer can use indexes efficiently on the join keys. Prefer EXISTS/subqueries when you only need to test for existence and don't need columns from the second table — it avoids row duplication and can be clearer.

Constraints & Keys

Q40 What is a Foreign Key and what does it enforce?

Answer: A Foreign Key is a column (or set of columns) that references the Primary Key of another table, enforcing referential integrity so you can't insert a value that doesn't exist in the parent table (or, depending on rules, delete a parent row that's still referenced).

Q41 Can a table have multiple primary keys?

Answer: No — a table can have only one PRIMARY KEY constraint, but that key can be composite (made up of multiple columns).

Q42 What is a composite key?

Answer: A key made up of two or more columns that together uniquely identify a row, used when no single column is unique on its own — common in junction/bridge tables for many-to-many relationships.

CREATE TABLE student_course (
  student_id INT,
  course_id INT,
  PRIMARY KEY (student_id, course_id)
);
Q43 What is a candidate key vs a super key?

Answer: A super key is any set of columns that uniquely identifies a row (may include extra, redundant columns). A candidate key is a minimal super key — no column can be removed without losing uniqueness. One candidate key is chosen as the primary key; the rest become alternate keys.

Q44 What does the CHECK constraint do?

Answer: It enforces a boolean condition on column values at insert/update time, rejecting rows that violate it — e.g., ensuring salary > 0.

ALTER TABLE employee ADD CONSTRAINT chk_salary CHECK (salary > 0);
Q45 What is the difference between ON DELETE CASCADE, SET NULL, and RESTRICT?

Answer: CASCADE automatically deletes child rows when the parent is deleted. SET NULL sets the foreign key column to NULL on the children instead of deleting them. RESTRICT (or NO ACTION) blocks the delete of the parent entirely if children still reference it.

Q46 What is referential integrity?

Answer: A guarantee that relationships between tables remain consistent — every foreign key value must correspond to an existing primary key value in the referenced table (or be NULL, if allowed).

Q47 What's the difference between NOT NULL and DEFAULT constraints?

Answer: NOT NULL simply forbids storing a NULL value in the column. DEFAULT supplies an automatic value when no value is explicitly provided on INSERT — a column can have both.

SQL Functions

Q48 How do you extract the year from a date column?

Answer: Use EXTRACT(YEAR FROM date_column) in PostgreSQL/Oracle, or YEAR(date_column) in MySQL.

Why / details: Dialect differences are a common practical question — always mention which database you're referring to.

Q49 How do you concatenate strings in SQL?

Answer: Use the CONCAT() function, or the || operator in PostgreSQL/Oracle/SQLite (MySQL supports CONCAT() but not || by default).

SELECT CONCAT(first_name, ' ', last_name) AS full_name FROM employee;
Q50 Difference between CAST and CONVERT?

Answer: CAST is ANSI-standard SQL and works across most databases; CONVERT is more feature-rich in SQL Server (supports style codes for formatting) but is less portable.

Q51 What does COALESCE() do?

Answer: It returns the first non-NULL value from a list of expressions — commonly used to substitute a default value when a column might be NULL.

SELECT COALESCE(phone, 'N/A') FROM employee;
Q52 Find employees who joined in the last 6 months.

Answer: Filter join_date against the current date minus a 6-month interval.

SELECT * FROM employee
WHERE join_date >= CURRENT_DATE - INTERVAL '6 months';
Q53 What's the difference between ROUND(), FLOOR(), and CEIL()?

Answer: ROUND rounds to the nearest specified decimal place (standard rounding rules). FLOOR always rounds down to the nearest integer. CEIL always rounds up to the nearest integer.

CASE Expressions

Q54 How does a CASE expression work in SQL?

Answer: CASE evaluates conditions in order and returns the value tied to the first TRUE condition, falling back to ELSE (or NULL if no ELSE is given) if none match. It works in SELECT, WHERE, ORDER BY, and GROUP BY.

SELECT name,
  CASE WHEN salary >= 100000 THEN 'High'
       WHEN salary >= 50000 THEN 'Medium'
       ELSE 'Low' END AS salary_band
FROM employee;
Q55 Can CASE be used inside an aggregate function? Give an example.

Answer: Yes — this is a common technique called conditional aggregation, useful for pivoting data.

SELECT department_id,
  SUM(CASE WHEN gender = 'F' THEN 1 ELSE 0 END) AS female_count,
  SUM(CASE WHEN gender = 'M' THEN 1 ELSE 0 END) AS male_count
FROM employee
GROUP BY department_id;
Q56 What's the difference between simple CASE and searched CASE syntax?

Answer: Simple CASE compares one expression against multiple values (CASE column WHEN val1 THEN...). Searched CASE evaluates independent boolean conditions (CASE WHEN condition1 THEN...), giving more flexibility (e.g., ranges, multiple columns).

Set Operations

Q57 Difference between UNION and UNION ALL?

Answer: UNION merges two result sets and removes duplicate rows (requires a sort/dedup step); UNION ALL merges them and keeps all rows including duplicates, so it's generally faster.

Q58 What is INTERSECT and how does it differ from an INNER JOIN?

Answer: INTERSECT returns rows that appear in both result sets (matching on entire rows, not just a key column), whereas an INNER JOIN combines columns from two tables based on a join key. INTERSECT is a set operation; JOIN is a relational combination.

Q59 What rules must both queries follow to use UNION?

Answer: Both SELECT statements must return the same number of columns, in a compatible order, with compatible (implicitly convertible) data types.

Q60 What does EXCEPT (or MINUS in Oracle) do?

Answer: It returns rows present in the first query's result but not in the second — essentially a set difference.

SELECT customer_id FROM customers
EXCEPT
SELECT customer_id FROM churned_customers;

CTE

Q61 What is a CTE and why use it over a subquery?

Answer: A Common Table Expression (WITH clause) is a named, temporary result set scoped to a single query. It improves readability, allows reuse of the same result multiple times within the query, and supports recursion — subqueries can't be reused by name.

WITH high_earners AS (
  SELECT * FROM employee WHERE salary > 100000
)
SELECT department_id, COUNT(*) FROM high_earners GROUP BY department_id;
Q62 What is a recursive CTE and when would you use one?

Answer: A CTE that references itself to process hierarchical or graph-like data, such as an org chart or category tree, by starting with a base case and repeatedly joining to build up results.

WITH RECURSIVE org_chart AS (
  SELECT id, name, manager_id, 1 AS level
  FROM employee WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, e.manager_id, oc.level + 1
  FROM employee e
  JOIN org_chart oc ON e.manager_id = oc.id
)
SELECT * FROM org_chart;
Q63 Are CTEs materialized (computed once) or inlined by the optimizer?

Answer: It depends on the database: PostgreSQL (pre-12) always materialized CTEs, PostgreSQL 12+ can inline them like subqueries unless marked MATERIALIZED, while SQL Server typically inlines/optimizes CTEs like views. Always check your specific engine's behavior for performance-critical queries.

Q64 Can you use multiple CTEs in a single query?

Answer: Yes, by separating them with commas in a single WITH clause; later CTEs can even reference earlier ones.

WITH dept_avg AS (
  SELECT department_id, AVG(salary) avg_sal FROM employee GROUP BY department_id
), high_dept AS (
  SELECT * FROM dept_avg WHERE avg_sal > 60000
)
SELECT * FROM high_dept;
Q65 What is the main limitation of a CTE compared to a temporary table or a view?

Answer: A CTE only exists for the duration of the single statement it's attached to — it can't be indexed, and it's re-evaluated each time it's referenced (unless the engine materializes and caches it), unlike a temp table which persists and can be indexed for the session.

Window Functions

Q66 Difference between ROW_NUMBER(), RANK(), and DENSE_RANK()?

Answer: ROW_NUMBER() assigns a unique sequential number to every row, even for ties. RANK() gives the same rank to ties but skips subsequent numbers (1,2,2,4). DENSE_RANK() gives the same rank to ties without skipping (1,2,2,3).

SELECT name, salary,
  RANK() OVER (ORDER BY salary DESC) AS rnk
FROM employee;
Q67 Find the second-highest salary in each department using window functions.

Answer: Use DENSE_RANK() partitioned by department, ordered by salary descending, then filter for rank = 2.

SELECT * FROM (
  SELECT name, department_id, salary,
    DENSE_RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rnk
  FROM employee
) t
WHERE rnk = 2;
Q68 What does PARTITION BY do inside an OVER() clause?

Answer: It divides the result set into groups (partitions), and the window function is computed independently within each partition, resetting for each new group — analogous to GROUP BY but without collapsing rows.

Q69 What is the difference between a window function and GROUP BY?

Answer: GROUP BY collapses multiple rows into one row per group, losing row-level detail. A window function computes an aggregate/ranking value per row while still returning every individual row, letting you see both detail and aggregate together.

Q70 Explain LAG() and LEAD() with an example use case.

Answer: LAG() accesses a value from a previous row and LEAD() from a following row within the same result set/partition, without a self-join — useful for computing differences between consecutive rows, like month-over-month change.

SELECT name, salary,
  salary - LAG(salary) OVER (ORDER BY review_date) AS salary_change
FROM salary_history;
Q71 How do you calculate a running total using window functions?

Answer: Use SUM() as a window function ordered by the relevant column, without a PARTITION BY (or with one, for a per-group running total) — the default frame accumulates all preceding rows.

SELECT order_date, amount,
  SUM(amount) OVER (ORDER BY order_date) AS running_total
FROM orders;
Q72 Find the top 3 salaries in each department.

Answer: Partition by department, rank by salary descending using DENSE_RANK or ROW_NUMBER, and keep rows with rank <= 3.

SELECT * FROM (
  SELECT name, department_id, salary,
    DENSE_RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rnk
  FROM employee
) t
WHERE rnk <= 3;
Q73 What is a window frame, and what does 'ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW' mean?

Answer: A window frame defines which rows within a partition are included in the calculation for the current row. That specific clause means: include every row from the start of the partition up to and including the current row — the classic definition for a running total.

Q74 What do FIRST_VALUE() and LAST_VALUE() do?

Answer: FIRST_VALUE() returns the value of an expression from the first row of the window frame; LAST_VALUE() returns it from the last row of the frame. Note LAST_VALUE often needs an explicit frame clause (ROWS BETWEEN ... AND UNBOUNDED FOLLOWING) to behave as expected, since the default frame ends at the current row.

Q75 Can you use a window function's result directly in a WHERE clause?

Answer: No — window functions are evaluated after WHERE and GROUP BY in the logical processing order, so you must wrap the query in a subquery or CTE and filter in the outer query.

Q76 Find the highest salary in each department using RANK().

Answer: Rank employees by salary within each department partition and keep rank = 1 (note: RANK can return ties for the top spot, unlike ROW_NUMBER).

SELECT * FROM (
  SELECT name, department_id, salary,
    RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rnk
  FROM employee
) t
WHERE rnk = 1;
Q77 What is the practical difference between using ROW_NUMBER() vs RANK() to find 'the top earner per department' when there's a tie?

Answer: ROW_NUMBER() arbitrarily picks just one employee as rank 1 even if two people tie on salary, potentially hiding a tie. RANK() correctly returns both tied employees as rank 1, which is usually the more business-correct answer.

Normalization

Q78 What problem does normalization solve?

Answer: It reduces data redundancy and prevents update/insert/delete anomalies by organizing columns and tables so each fact is stored in only one place.

Q79 Briefly explain 1NF, 2NF, and 3NF.

Answer: 1NF: each column holds atomic (indivisible) values, no repeating groups. 2NF: 1NF plus every non-key column depends on the whole primary key (no partial dependency on part of a composite key). 3NF: 2NF plus no transitive dependency — non-key columns depend only on the key, not on other non-key columns.

Q80 What is denormalization and when would you use it?

Answer: Denormalization intentionally introduces redundancy (e.g., duplicating a column across tables) to reduce the number of joins needed, trading some write complexity/storage for faster reads — common in reporting/analytics or read-heavy systems.

Q81 What is BCNF (Boyce-Codd Normal Form) and how does it differ from 3NF?

Answer: BCNF is a stricter version of 3NF: for every functional dependency X → Y, X must be a super key. It resolves rare anomalies that can still exist in 3NF when a table has multiple overlapping candidate keys.

Q82 Give a practical example of removing a transitive dependency to reach 3NF.

Answer: If an Employee table stores department_name and department_manager directly (which depend on department_id, not on employee_id), that's a transitive dependency — split it into a separate Department table and reference it via a foreign key.

Transactions

Q83 Explain ACID properties.

Answer: Atomicity: a transaction is all-or-nothing. Consistency: a transaction moves the database from one valid state to another, respecting constraints. Isolation: concurrent transactions don't interfere with each other's intermediate state. Durability: once committed, changes survive crashes.

Q84 What's the difference between COMMIT and ROLLBACK?

Answer: COMMIT permanently saves all changes made in the current transaction. ROLLBACK undoes all changes made since the last COMMIT (or since the transaction began), restoring the prior state.

Q85 What is a SAVEPOINT?

Answer: A named point within a transaction that you can roll back to without undoing the entire transaction — useful for partial recovery from an error mid-transaction.

BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
SAVEPOINT sp1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
-- if something goes wrong:
ROLLBACK TO sp1;
Q86 Explain the four transaction isolation levels.

Answer: Read Uncommitted: can see other transactions' uncommitted changes (dirty reads possible). Read Committed: only sees committed data, but repeated reads can differ (non-repeatable reads). Repeatable Read: same rows return the same values across the transaction, but new rows can appear (phantom reads). Serializable: fully isolated, transactions behave as if executed one after another — safest but slowest.

Q87 What is a dirty read, a non-repeatable read, and a phantom read?

Answer: Dirty read: reading uncommitted data from another transaction that might later be rolled back. Non-repeatable read: re-reading the same row within a transaction and getting a different value because another transaction committed a change in between. Phantom read: re-running the same query and getting a different set of rows because another transaction inserted/deleted matching rows.

Q88 How does @Transactional in Spring relate to SQL transactions?

Answer: It wraps a method's database operations in a single transaction managed by Spring's PlatformTransactionManager — commits automatically if the method completes normally and rolls back on an unchecked exception (by default), letting you control isolation level and propagation declaratively instead of manually issuing BEGIN/COMMIT/ROLLBACK.

@Transactional(isolation = Isolation.READ_COMMITTED, propagation = Propagation.REQUIRED)
public void transferFunds(Long fromId, Long toId, BigDecimal amount) { ... }
Q89 What is a deadlock and how can it be avoided?

Answer: A deadlock occurs when two or more transactions each hold a lock the other needs, so neither can proceed. It can be mitigated by always acquiring locks in a consistent order across transactions, keeping transactions short, and using appropriate timeouts so the database can detect and abort one transaction.

Q90 What is optimistic locking vs pessimistic locking?

Answer: Pessimistic locking acquires a lock on a row up front (e.g., SELECT ... FOR UPDATE) and blocks other transactions from touching it until released. Optimistic locking assumes conflicts are rare — it doesn't lock, but checks a version/timestamp column at commit time and fails the update if the row changed since it was read.

Indexes

Q91 What is an index and why does it speed up SELECT queries?

Answer: An index is a separate, ordered data structure (usually a B-Tree) that maps column values to row locations, letting the database jump directly to matching rows instead of scanning the entire table sequentially.

Q92 Why can indexes slow down INSERT/UPDATE/DELETE?

Answer: Every write that touches an indexed column must also update the index structure(s), so more indexes on a table mean more work per write operation — it's a classic read-speed vs write-speed tradeoff.

Q93 Difference between a clustered and non-clustered index?

Answer: A clustered index determines the physical order in which data rows are stored on disk — a table can have only one. A non-clustered index is a separate structure that stores pointers back to the actual rows, and a table can have several.

Q94 What is a composite (multi-column) index and how does column order matter?

Answer: A composite index is built on multiple columns together. Column order matters because the index can only be used efficiently (as a seek) for queries filtering on a leftmost prefix of those columns — an index on (a, b, c) helps queries filtering on 'a', 'a,b', or 'a,b,c', but not on 'b' alone.

Q95 What is a covering index?

Answer: An index that contains all the columns a query needs (in its key or included columns), so the database can answer the query entirely from the index without touching the actual table rows — this is called an index-only scan.

Q96 What is index selectivity, and why does it matter?

Answer: Selectivity is the ratio of distinct values to total rows in a column. High-selectivity columns (like email) benefit greatly from indexing since an index seek narrows results to very few rows; low-selectivity columns (like a boolean 'is_active' flag) benefit little, since the index still returns a large fraction of the table.

Q97 When would you NOT want to create an index?

Answer: On small tables (a full scan is already fast), on columns rarely used in WHERE/JOIN/ORDER BY, on low-selectivity columns, or on tables with very heavy write traffic where the write overhead of maintaining the index outweighs the read benefit.

Q98 How would an index on department_id help this query: WHERE department_id = ?

Answer: Instead of scanning every row in the table (sequential scan), the database can navigate the B-Tree index directly to the matching department_id value and retrieve only those row pointers — an index scan/seek, which is much faster on large tables.

Views

Q99 What is a View and how is it different from a Table?

Answer: A View is a stored, named SELECT query that behaves like a virtual table — it has no data of its own (except materialized views) and is recomputed each time it's queried. A Table physically stores data on disk.

CREATE VIEW employee_details AS
SELECT e.name, d.department_name
FROM employee e JOIN department d ON e.department_id = d.id;
Q100 What is a Materialized View and how does it differ from a regular View?

Answer: A Materialized View physically stores (caches) the query result on disk and must be periodically refreshed, trading storage and staleness for much faster read performance compared to a regular view, which re-runs its query every time.

Q101 Give a scenario where you'd use a View.

Answer: To simplify a complex, frequently reused JOIN/aggregation for reporting, or to restrict which columns/rows certain users can see (security through column/row-level abstraction) without exposing the underlying table structure directly.

Procedures & Triggers

Q102 What is the difference between a Stored Procedure and a Function in SQL?

Answer: A Function must return a value and can be used inline within a SELECT statement (typically can't modify data in most databases); a Stored Procedure may or may not return a value, can perform DML/DDL, and is invoked with CALL/EXEC rather than embedded in a query.

Q103 What is a Trigger, and give an example use case?

Answer: A Trigger is a piece of code that automatically executes in response to an INSERT/UPDATE/DELETE event on a table — e.g., automatically logging changes to an audit table whenever a row in 'employee' is updated.

CREATE TRIGGER trg_audit_salary
AFTER UPDATE OF salary ON employee
FOR EACH ROW
EXECUTE FUNCTION log_salary_change();

Query Optimization

Q104 What does EXPLAIN (or EXPLAIN ANALYZE) show you?

Answer: EXPLAIN shows the database's planned execution strategy for a query — which scans, joins, and sorts it will use and their estimated cost — without running it. EXPLAIN ANALYZE actually executes the query and shows real timing/row counts alongside the plan, letting you compare estimates to reality.

Q105 Difference between a Sequential Scan and an Index Scan in an execution plan?

Answer: A Sequential Scan reads every row in the table in physical order — O(n), used when there's no useful index or the optimizer expects to need most of the rows. An Index Scan uses an index to jump directly to matching rows, much faster when selectivity is high (few matching rows relative to table size).

Q106 What is a Nested Loop Join vs a Hash Join?

Answer: A Nested Loop Join iterates the outer table row by row and, for each row, searches the inner table (efficient with a good index on the inner table and a small outer set). A Hash Join builds an in-memory hash table from one input and probes it with the other — generally faster for large, unindexed equi-joins but requires more memory.

Q107 What do 'cost' and 'cardinality' mean in a query execution plan?

Answer: Cardinality is the estimated (or actual) number of rows a step will produce/process. Cost is the optimizer's internal unit measuring the estimated resources (I/O + CPU) a step will take — the optimizer picks the plan with the lowest total estimated cost, which depends heavily on accurate cardinality estimates from table statistics.

Q108 Why might a query be slow even though the right index exists?

Answer: Common reasons: outdated table statistics leading the optimizer to pick a bad plan, a function applied to the indexed column in WHERE (e.g., UPPER(email) = ...) which prevents index usage, low selectivity making a scan cheaper anyway, implicit type conversion, or the query fetching so many rows that an index scan is no faster than a sequential scan.

Database Design

Q109 How do you model a One-to-Many relationship?

Answer: Put a foreign key on the 'many' side referencing the primary key of the 'one' side — e.g., each employee row has a department_id pointing to one department, but a department can have many employees.

Q110 How do you model a Many-to-Many relationship?

Answer: Introduce a junction/bridge table containing foreign keys to both related tables (often with a composite primary key), since neither table can directly hold a variable-length list of the other's keys.

CREATE TABLE student_course (
  student_id INT REFERENCES student(id),
  course_id INT REFERENCES course(id),
  PRIMARY KEY (student_id, course_id)
);
Q111 What is a One-to-One relationship and when is it used?

Answer: Each row in table A corresponds to exactly one row in table B, usually implemented with a foreign key that is also unique (or shares the same primary key). Used to split a table for security (isolating sensitive columns) or to keep rarely-used columns out of a hot table.

Q112 Find departments with no employees.

Answer: LEFT JOIN department to employee and filter where the employee side is NULL.

SELECT d.*
FROM department d
LEFT JOIN employee e ON d.id = e.department_id
WHERE e.id IS NULL;
Q113 What does 'cascading' mean in database design, and what's a risk of ON DELETE CASCADE?

Answer: Cascading means an action on a parent row automatically propagates to related child rows (e.g., deleting a customer also deletes their orders). The risk is unintended data loss — a single delete can silently ripple through many related tables if the cascade chain isn't well understood.
