Section 01

JVM — The Big Picture

The Java Virtual Machine (JVM) is an abstract computing machine — a software layer that provides a runtime environment in which Java bytecode can be executed. Because it is virtual, it isn't tied to any physical hardware; rather, it is a specification. The actual implementation of that specification is delivered by JRE (Java Runtime Environment).

🔷 JVM

Abstract specification. Defines the rules for loading, verifying, and executing bytecode.

🟢 JRE

JVM implementation + standard libraries. What you install to run Java programs.

🟣 JDK

JRE + compiler (javac) + dev tools. What you install to develop Java programs.

Three Pillars of JVM

1. Class Loader

Loads .class files (bytecode) into JVM memory from disk, network, or other sources. Handles loading → linking → initialization.

2. Memory Areas (Runtime Data Areas)

Organized memory regions: Heap, Stack, Method Area, PC Registers, Native Method Stack.

3. Execution Engine

Reads bytecode and executes it using Interpreter, JIT Compiler, Garbage Collector, and JNI.

Section 03

Class Loader Subsystem

The Class Loader is the gatekeeper of the JVM. Its job is to find .class files and load the bytecode into JVM memory. Think of it as the security checkpoint at the JVM's entrance.

Three Types of Class Loaders

Class Loader Hierarchy (Parent Delegation Model)
Class Loader Java < 9 Java 9+ What it loads
Bootstrap Loads rt.jar Loads java.base module Core JDK classes: java.lang.*, java.util.*
Platform Extension CL — loads $JAVA_HOME/lib/ext Platform CL — replaces Extension CL Platform-specific modules (java.sql, java.desktop…)
Application System CL Same, also reads module path Your application's .class files, 3rd-party jars

Parent Delegation Model

When a class needs to be loaded, the request is always delegated to the parent first. Only if the parent cannot find the class does the child try to load it. This ensures that core JDK classes can never be overridden by malicious user code.

// Custom Class Loader example
public class MyClassLoader extends ClassLoader {

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        // 1. Parent (AppCL) is asked first — automatically via loadClass()
        // 2. Only if parent fails, findClass() here is called
        byte[] bytecode = loadBytesFromCustomLocation(name);
        return defineClass(name, bytecode, 0, bytecode.length);
    }
}
Interview Trap: Bootstrap ClassLoader is implemented in native code (C/C++), not Java. So String.class.getClassLoader() returns null — because Bootstrap has no Java representation.

Class Loading Lifecycle

After loading, a class goes through Linking then Initialization before it can be used.

1️⃣ Loading

The ClassLoader reads the .class file's bytecode into memory. A Class<?> object is created in the heap to represent the loaded class.

2️⃣ Verification

The Bytecode Verifier checks that the bytecode is structurally valid and follows JVM spec. Prevents malicious / malformed bytecode from crashing the JVM. Throws VerifyError on failure.

3️⃣ Preparation

Memory for static variables is allocated and set to default values (0, null, false). No actual code runs yet — just memory reservation.

4️⃣ Resolution

Symbolic references (e.g., class names as strings in the constant pool) are replaced with direct references (actual memory pointers). This is sometimes done lazily.

5️⃣ Initialization

Static variables are assigned their actual values. static {} blocks are executed. This is the first time user code runs during class loading.

public class Demo {
    // Preparation: x = 0 (default)
    // Initialization: x = 42 (actual value)
    static int x = 42;

    static {
        // This static block runs during Initialization phase
        System.out.println("Class initialized! x = " + x);
    }
}

Runtime Memory Areas

The JVM divides its memory into distinct regions, each serving a specific purpose. Understanding which data lives where is critical for debugging memory issues and acing interviews.

⚙️

JVM Memory Layout

Method Area / Metaspace (Detailed)

Java < 8 — PermGen

Fixed-size region inside the JVM heap

Stored: class metadata, method bytecode, interned strings, static variables

Problem: could not grow dynamically → frequent OutOfMemoryError: PermGen space

Java 8+ — Metaspace

Lives in native memory (outside JVM heap)

Stores: class metadata, method bytecode, annotations — but NOT static variables

Grows dynamically. Capped with -XX:MaxMetaspaceSize

Java 8 Key Change: Static variables moved from PermGen/Metaspace to the Heap — stored inside the Class<T> object that lives in the heap. This is a very common interview question!

Heap Memory — Generational Structure

The heap is divided into generations to optimize garbage collection performance:

  • Eden Space — New objects are born here. Minor GC happens here frequently and is fast.
  • Survivor S0 / S1 — Objects that survive Minor GC get moved here. Objects alternate between S0 and S1 across GC cycles.
  • TLAB (Thread-Local Allocation Buffer) — Each thread has a private slice of Eden for lock-free allocation.
  • Old Generation (Tenured) — Long-lived objects promoted from Young Gen. Major GC (slower) cleans this.

Stack Memory

Each thread has its own private stack. The stack holds frames — one per method call. Each frame contains:

  • Local Variable Array — holds this, method parameters, and local primitives/references
  • Operand Stack — a working area for the bytecode instruction execution
  • Reference to Constant Pool — links back to the Method Area
StackOverflowError happens when recursion is too deep and the thread's stack runs out of space. This is a per-thread error, not a heap issue. 
// Where does each variable live?
public class MemoryExample {
    static int counter = 0;        // Heap (inside Class<MemoryExample> object) — Java 8+
    int id;                           // Heap (instance variable, part of each object)

    void compute(int x) {
        int result = x * 2;            // Stack (local variable in this frame)
        String msg = "hello";          // msg reference: Stack | "hello" object: Heap (String Pool)
        Object obj = new Object();    // obj reference: Stack | Object instance: Heap
    }
}

JIT Compiler — Deep Dive

The Just-In-Time compiler is the performance heart of the JVM. Without it, Java would be perpetually slow. Here's exactly how it works:

The Problem with Pure Interpretation

// This loop runs 1,000,000 times
for (int i = 0; i < 1_000_000; i++) {
    result += computeSomething(i);  // Without JIT: bytecode retranslated EVERY iteration
}                                        // With JIT: compiled once to machine code, runs native

How JIT Works — The Pipeline

🏃
Interpret
JVM starts interpreting bytecode. All methods initially run interpreted.
📊
Profile
JVM counts invocations. Tracks branch decisions, types, call sites.
🔥
Detect Hot Spot
Method exceeds invocation threshold (~10,000). Flagged for compilation.
⚙️
Compile (C1/C2)
Background compiler thread compiles method to optimized native code.
💾
Cache
Compiled machine code stored in Code Cache. Future calls skip compilation.
🚀
Execute Native
Method now runs as native code — near C++ performance.

JIT Optimization Techniques

🔗 Method Inlining

Small frequently-called methods are copied directly into the caller — eliminating method call overhead entirely. Most impactful JIT optimization.

// Before inlining:
result = add(a, b);

// After inlining (JIT):
result = a + b; // no call overhead!

🏃 Escape Analysis

JIT detects if an object "escapes" the method scope. If not, it can allocate the object on the stack instead of the heap — zero GC pressure.

void doWork() {
    Point p = new Point(1, 2); // Doesn't escape!
    use(p.x + p.y);
    // JIT may allocate p on stack
}

🔄 Loop Unrolling

The JIT expands loop iterations to reduce branch check overhead and enable CPU pipeline optimization.

// Before:
for(int i=0; i<4; i++) a[i]++;

// After unrolling:
a[0]++; a[1]++; a[2]++; a[3]++;

🎯 Monomorphic Dispatch

If JIT sees a virtual method always called on the same type, it replaces the virtual dispatch with a direct call (or even inline it).

💀 Dead Code Elimination

Code that provably never executes (based on profiling data) is removed, shrinking the hot path.

↩️ Deoptimization

If JIT made an assumption that turns out to be wrong (e.g., new subclass loaded), it deoptimizes — falls back to interpreter. Safe and transparent.

Code Cache

Compiled native code is stored in the Code Cache — a fixed-size memory region. If it fills up, JIT stops compiling and performance degrades silently.

# Check code cache size
java -XX:+PrintCodeCache -version

# Increase code cache (default ~240MB in Java 8+)
java -XX:ReservedCodeCacheSize=512m MyApp

# Disable JIT (run pure interpreter — for debugging only)
java -Xint MyApp

# Force compilation threshold
java -XX:CompileThreshold=1000 MyApp  # compile after 1000 invocations

Section 08

Garbage Collector

The GC automatically manages heap memory by reclaiming space from objects that are no longer reachable — no manual free() needed.

GC Roots — How Reachability Works

An object is live if it is reachable from a GC Root. GC Roots are:

  • Local variables and parameters in active stack frames
  • Static variables (Class objects in heap)
  • JNI references from native code
  • Active thread objects

Anything not reachable from a root → eligible for garbage collection.

GC Algorithms in HotSpot JVM

CollectorJava VersionStrategyBest For
Serial GCAllSingle-threaded, stop-the-worldSingle-core, small heaps
Parallel GCAll (default pre-9)Multi-threaded, stop-the-worldThroughput-focused batch apps
G1 GCJava 9+ defaultRegion-based, concurrent markingBalanced latency + throughput
ZGCJava 11+Concurrent, scalable, <1ms pausesLow-latency, large heaps (>100GB)
ShenandoahJava 12+Concurrent evacuationLow pause time, any heap size
Tip for interviews: G1 GC is the default since Java 9. ZGC is the choice for latency-sensitive applications (trading systems, real-time APIs). Always mention that GC pause = Stop-The-World (STW) pause.
Section 09

JNI — Java Native Interface

JNI is the bridge between Java bytecode and native code written in C/C++. It allows Java to call OS-specific features and use native libraries.

Why JNI?

Access hardware directly, use legacy C libraries, call OS APIs not exposed in Java, maximize performance-critical code with native routines.

How it works

Java method declared native → compiled normally → at runtime, JNI looks up the matching C function in a loaded .dll / .so and calls it.

// Java side
public class NativeExample {
    static { System.loadLibrary("mylib"); }  // Load mylib.dll / libmylib.so
    public native int add(int a, int b);         // Declared, implemented in C
}

// C side (mylib.c)
JNIEXPORT jint JNICALL Java_NativeExample_add(JNIEnv *env, jobject obj, jint a, jint b) {
    return a + b;  // C implementation
}
Section 10

Top 20 Interview Questions

Q01 What is the JVM and why is Java called "platform-independent"? +

JVM (Java Virtual Machine) is an abstract computing machine that provides a runtime environment for executing Java bytecode. Java is platform-independent at the source/bytecode level — the same .class file runs on any OS that has a JVM installed. However, the JVM itself is platform-dependent (you install a different JVM for Windows vs Linux). So the phrase is "Write Once, Run Anywhere" because the bytecode is universal, and the JVM translates it to platform-specific machine code at runtime.

Q02 Explain the three main components of the JVM. +

1. Class Loader Subsystem — Loads .class files into memory. Performs Loading → Linking (Verification, Preparation, Resolution) → Initialization.

2. Runtime Memory Areas — Organizes JVM memory: Method Area (Metaspace), Heap, Java Stack, PC Register, Native Method Stack.

3. Execution Engine — Executes bytecode via Interpreter (line-by-line) and JIT Compiler (hot-path native compilation). Also includes Garbage Collector and JNI.

Q03 What is the Parent Delegation Model in class loading? +

When a class loader is asked to load a class, it first delegates the request to its parent class loader. Only if the parent fails (class not found) does the child try to load it itself. The hierarchy is: Application CL → Platform CL → Bootstrap CL → (null — can't go higher).

This prevents user code from replacing core Java classes like java.lang.String with malicious versions — Bootstrap always loads them first and the request never reaches the Application CL.

// Bootstrap is "parent" of all, has no Java parent → returns null
System.out.println(String.class.getClassLoader()); // null
System.out.println(MyClass.class.getClassLoader()); // jdk.internal.loader.ClassLoaders$AppClassLoader
Q04 What is the difference between JVM, JRE, and JDK? +

JVM — The specification and engine that executes bytecode. Abstract; the same spec is implemented differently on each platform.

JRE (Java Runtime Environment) — JVM implementation + standard class libraries. Required to run Java programs. End-users install this.

JDK (Java Development Kit) — JRE + compiler (javac) + debugger + javadoc + other tools. Developers install this. JDK ⊃ JRE ⊃ JVM.

Q05 Where are static variables stored in Java 8 vs earlier versions? +

Before Java 8 (PermGen era): Static variables were stored in the PermGen (Permanent Generation), which was a fixed-size region inside the JVM heap.

Java 8+ (Metaspace era): Static variables are stored in the Heap — specifically inside the Class<T> object that represents the class. Since this Class object lives on the heap, static variables live on the heap too.

Method bytecode and class metadata still go into Metaspace (native memory). This change eliminated most OutOfMemoryError: PermGen space issues.

Q06 What is PermGen and why was it replaced by Metaspace? +

PermGen (Permanent Generation) was a fixed-size region of the JVM heap used to store class metadata, method bytecode, interned strings, and static variables. Its critical flaw: the size was fixed at JVM startup (-XX:MaxPermSize) and could not dynamically shrink or grow. Applications deploying many classes (e.g., app servers with hot-deploy) would frequently hit OutOfMemoryError: PermGen space.

Metaspace (Java 8+) allocates class metadata in native OS memory (outside the JVM heap). It auto-grows by default and is bounded only by available system memory. You can cap it with -XX:MaxMetaspaceSize. This massively reduces OOM errors related to class loading.

Q08 What is the difference between Interpreter and JIT Compiler? +

Interpreter translates and executes bytecode one instruction at a time. It starts immediately with no warm-up, but is slow for repeated code because the same bytecode gets re-translated on every execution.

JIT Compiler monitors which methods are called frequently (hot spots), compiles them entirely to native machine code, and stores the result in the Code Cache. Future calls execute the native code directly — no translation overhead. JIT has a warm-up period but delivers near-native speed at peak.

Modern JVMs use both: interpret first, JIT-compile hot methods in the background (tiered compilation). This gives fast startup AND fast peak throughput.

Q09 What is a Stack Frame? What does it contain? +

A stack frame is a data structure pushed onto a thread's stack for each method invocation. It contains:

  • Local Variable Array — this, method parameters, local variables (primitives stored directly; objects stored as references)
  • Operand Stack — working memory for the bytecode engine (like a calculator's scratch pad)
  • Frame Data / Constant Pool Reference — link to the class's runtime constant pool for symbolic resolution
  • Return Address — where to resume execution in the calling method after this method returns

When a method returns, its frame is popped from the stack and all its local data is gone.

Q10 What is the PC Register? Why does each thread have its own? +

The Program Counter (PC) Register holds the address (pointer) to the currently executing bytecode instruction for a thread. It always knows: "which instruction am I executing right now?" and "which instruction comes next?"

Each thread must have its own PC register because threads execute independently and concurrently. Thread 1 may be at instruction 42 of methodA() while Thread 2 is at instruction 7 of methodB(). If they shared a PC, they'd corrupt each other's execution state.

Special case: For native methods, the PC register is undefined (the native code manages its own instruction pointer at the OS level).

Q11 What is bytecode verification and why is it important? +

Bytecode verification is the process during the Linking → Verification phase where the JVM's Bytecode Verifier checks that the loaded .class file is structurally valid and safe before executing it.

It checks that:

  • The bytecode was produced by a valid Java compiler and follows the JVM specification
  • No stack underflow/overflow occurs
  • Type safety is not violated (no int passed where object expected)
  • No illegal memory access attempts exist

This is the JVM's primary defense against malicious or corrupted bytecode. Without it, a crafted .class file could crash the JVM or access arbitrary memory. On failure, a VerifyError is thrown and the class is rejected.

Q12 What is the difference between Minor GC and Major GC? +

Minor GC collects the Young Generation (Eden + Survivor spaces). It is triggered when Eden fills up. Minor GC is fast because most objects die young (weak generational hypothesis). It causes a stop-the-world pause but usually a short one (milliseconds).

Major GC (Full GC) collects the Old Generation. Triggered when Old Gen fills up or is fragmented. Much slower because old gen is larger and objects there are long-lived (more to scan/compact). Full GC pauses the entire application and can take seconds in poorly tuned apps.

The goal of GC tuning is to keep objects in Young Gen as long as possible (die young) and minimize Full GC frequency.

Q13 How does JIT method inlining work and why is it important? +

Method inlining is the most impactful JIT optimization. When a small method is called frequently, JIT replaces the method call with the actual body of the method at the call site — eliminating the overhead of:

  • Stack frame creation and destruction
  • Jump instruction to method code
  • Argument passing
  • Return value handling

After inlining, the JIT can apply further optimizations across the merged code (e.g., constant folding, dead code elimination) that would be impossible across method boundaries. Getters/setters are classic inlining candidates. Methods larger than ~35 bytecodes are typically not inlined.

// Getter inlining example
int val = obj.getValue(); // interpreted

// After JIT inlining (no method call at all):
int val = obj.internalField; // direct field access
Q14 What is Escape Analysis in JIT? How does it help? +

Escape Analysis is a JIT optimization where the compiler determines whether an object can "escape" the scope in which it was created — i.e., whether a reference to it can be accessed from outside that method or thread.

If an object does NOT escape (it's used only locally within the method), JIT can:

  • Stack allocate it instead of heap-allocating — zero GC pressure, auto-freed when method returns
  • Scalar replace it — break the object into individual fields stored directly in registers/stack
  • Eliminate synchronization — if the object never escapes to another thread, locks on it are useless and can be removed
void process() {
    StringBuilder sb = new StringBuilder();
    sb.append("hello");
    String result = sb.toString();
    use(result);
    // sb does NOT escape → JIT may stack-allocate or scalar-replace it
}
Q15 What is the difference between Bootstrap, Platform, and Application class loaders? +

Bootstrap ClassLoader: The top of the hierarchy. Written in native code (C/C++), not Java. Loads core JDK classes from java.base module (Java 9+) or rt.jar (Java 8-). Has the highest priority. Returns null when queried for its parent (String.class.getClassLoader() == null).

Platform ClassLoader (formerly Extension CL): Loads platform-specific modules like java.sql, java.desktop, java.xml. Before Java 9, this was called Extension ClassLoader and loaded $JAVA_HOME/lib/ext JARs.

Application ClassLoader: Loads your application's code from the classpath or module path. This is the default ClassLoader for all user classes. When you call Thread.currentThread().getContextClassLoader(), this is typically what you get.

Q16 What happens when you do new Object() in Java at the JVM level? +

When new Object() is executed:

  1. JVM checks if Object class is already loaded. If not, it triggers class loading.
  2. JVM allocates memory for the object in the Eden space of the Young Generation heap. For multi-threaded allocation, each thread uses its own TLAB (Thread-Local Allocation Buffer) for lock-free fast allocation.
  3. The allocated memory is zero-initialized (all instance variable fields set to default values: 0, null, false).
  4. JVM sets the object's header — contains mark word (GC info, hash code, lock state) and klass pointer (points to Class<Object> in Metaspace).
  5. The constructor (Object()) runs — initializing fields to their actual values.
  6. A reference to the object is placed on the operand stack (returned to the caller).
Q17 What is the String Pool (String Intern Pool) and where does it live? +

The String Pool (also called String Intern Pool or String Literal Pool) is a special cache that stores unique string literals. When you write "hello" as a literal, the JVM checks the pool first. If "hello" already exists, it reuses the same object reference instead of creating a new one.

Location:

  • Java 7 and earlier: Lived inside PermGen (heap). Could cause OOM if too many unique strings were interned.
  • Java 7+ (and 8+): Moved to the main Heap. Can now be GC'd if no references remain.
String a = "hello";          // pool lookup → stored in pool
String b = "hello";          // pool hit → same reference as a
String c = new String("hello"); // always new heap object
System.out.println(a == b);    // true (same pool reference)
System.out.println(a == c);    // false (c is a new object)
System.out.println(a == c.intern()); // true (intern returns pool ref)
Q18 What is JNI? When would you use it in production? +

JNI (Java Native Interface) is a programming framework that allows Java code to call and be called by native applications and libraries written in C, C++, or assembly. The Execution Engine uses JNI to bridge Java and native code.

Production use cases:

  • Hardware I/O — accessing serial ports, USB devices, GPU computing (CUDA)
  • Legacy systems — wrapping decades-old COBOL/C financial libraries
  • OS-specific APIs — Windows Registry access, POSIX file locking
  • Performance-critical routines — BLAS libraries for matrix math (used in ML frameworks)
  • Security — calling hardware security modules (HSMs) for cryptographic operations

Risks: JNI bypasses Java's memory safety. A crash in native code brings down the entire JVM. Use with extreme care and thorough testing.

Q19 Explain tiered compilation in HotSpot JVM. +

HotSpot uses 5 compilation levels (Tier 0–4):

  • Tier 0 — Interpreter: Pure interpretation. All methods start here.
  • Tier 1 — C1 (no profiling): Fast compilation, no optimization data collected. For trivial/rarely-called methods.
  • Tier 2 — C1 (limited profiling): Invocation and backedge counters only.
  • Tier 3 — C1 (full profiling): Collects branch probabilities, type profiles, call site information. Feeds data to C2.
  • Tier 4 — C2 (optimizing compiler): Uses all profiling data for aggressive optimizations: inlining, escape analysis, loop unrolling, vectorization. This is peak performance.

The JVM dynamically moves methods between tiers based on how hot they are and how busy the compiler threads are. Tiered compilation is on by default since Java 7 and gives both fast startup (C1 quickly) and high peak throughput (C2 eventually).

Q20 What is deoptimization in JIT and when does it happen? +

Deoptimization is the process where the JIT compiler throws away a previously compiled (optimized) version of a method and reverts to interpreting it. This happens when an assumption JIT made during compilation turns out to be wrong at runtime.

Common triggers:

  • New class loaded: JIT assumed a virtual call always went to class A (monomorphic). A new class B is loaded that overrides the method → deoptimize, recompile with new type profile.
  • Uncommon trap: JIT excluded a rare branch as dead code. At runtime that branch is actually taken → deoptimize.
  • Object escaped: JIT stack-allocated an object that later escapes to another thread → deoptimize to heap-allocate it.
  • Class redefinition: Hot-redeployment or JVMTI agents redefine a class.

Deoptimization is completely transparent to the developer. The JVM collects new profiling data and recompiles with updated information. It's safe but causes a temporary performance dip.
