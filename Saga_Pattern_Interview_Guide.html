1. The problem, quickly recapped

In a monolith, a multi-step business operation sits inside one @Transactional boundary — if any statement fails, the database rolls everything back atomically. Once you split into microservices, each with its own database, that single ACID transaction is gone: Order Service, Payment Service, Inventory Service, and Shipping Service each commit to their own local database. If Order and Payment succeed but Inventory fails, you're left with a paid, unfulfillable order — the system is in an inconsistent state, and there's no distributed rollback to fall back on (2PC/XA transactions don't scale and most modern datastores don't even support them well).

The Saga pattern solves this by replacing one big atomic transaction with a sequence of local transactions, one per service, where every step that changed something also defines an explicit compensating transaction to undo it if a later step fails. There's no "rollback" — there's "run the opposite operation."

2. Sample project — the scenario

Four Spring Boot microservices, each with its own DB, communicating over Kafka:

ServiceLocal transactionCompensating transaction
order-serviceCreate order (status=CREATED)Cancel order (status=CANCELLED)
payment-serviceDeduct customer's moneyRefund money
inventory-serviceReserve stock for the productRelease reserved stock
shipping-serviceCreate a shipmentCancel shipment (rarely fails — last step)

We'll build the same business flow two ways so you can compare them directly in an interview.

3. Type 1: Choreography-based Saga

Concept

No central controller. Each service publishes an event when its local transaction completes, and listens for events from other services to know when to act — like dancers who each know their own steps and react to their partner's moves, with no conductor.

Internal working
order-service: create order→ publish OrderCreated
payment-service listens OrderCreated→ deduct money→ publish PaymentCompleted (or PaymentFailed)
inventory-service listens PaymentCompleted→ reserve stock→ publish InventoryReserved (or InventoryFailed)
shipping-service listens InventoryReserved→ create shipment→ publish ShipmentCreated

Failure path: if InventoryFailed is published, payment-service (which is listening for it) triggers its own compensating action and publishes PaymentRefunded; order-service listens for that and cancels the order. Each service only needs to know which events to react to — never who else exists.

// ---- Shared event contracts (common module) ----
public record OrderCreatedEvent(String orderId, String productId, int qty, double amount) {}
public record PaymentCompletedEvent(String orderId, double amount) {}
public record PaymentFailedEvent(String orderId, String reason) {}
public record InventoryReservedEvent(String orderId, String productId) {}
public record InventoryFailedEvent(String orderId, String reason) {}
public record PaymentRefundedEvent(String orderId) {}

// ---- order-service ----
@Service
class OrderService {
    private final OrderRepository repo;
    private final KafkaTemplate<String, Object> kafka;

    void createOrder(CreateOrderRequest req) {
        Order order = repo.save(new Order(req.productId(), req.qty(), req.amount(), "CREATED"));
        kafka.send("order-created", new OrderCreatedEvent(order.getId(), req.productId(), req.qty(), req.amount()));
    }

    @KafkaListener(topics = "payment-refunded")
    void onPaymentRefunded(PaymentRefundedEvent event) {
        repo.updateStatus(event.orderId(), "CANCELLED");   // compensating action
    }
}

// ---- payment-service ----
@Service
class PaymentService {
    private final PaymentRepository repo;
    private final KafkaTemplate<String, Object> kafka;

    @KafkaListener(topics = "order-created")
    void onOrderCreated(OrderCreatedEvent event) {
        try {
            repo.deduct(event.orderId(), event.amount());   // local transaction
            kafka.send("payment-completed", new PaymentCompletedEvent(event.orderId(), event.amount()));
        } catch (InsufficientBalanceException e) {
            kafka.send("payment-failed", new PaymentFailedEvent(event.orderId(), e.getMessage()));
        }
    }

    @KafkaListener(topics = "inventory-failed")
    void onInventoryFailed(InventoryFailedEvent event) {
        repo.refund(event.orderId());                        // compensating transaction
        kafka.send("payment-refunded", new PaymentRefundedEvent(event.orderId()));
    }
}

// ---- inventory-service ----
@Service
class InventoryService {
    private final InventoryRepository repo;
    private final KafkaTemplate<String, Object> kafka;

    @KafkaListener(topics = "payment-completed")
    void onPaymentCompleted(PaymentCompletedEvent event) {
        boolean reserved = repo.reserveStock(event.orderId());
        if (reserved) {
            kafka.send("inventory-reserved", new InventoryReservedEvent(event.orderId(), null));
        } else {
            kafka.send("inventory-failed", new InventoryFailedEvent(event.orderId(), "Out of stock"));
        }
    }
}

// ---- shipping-service ----
@Service
class ShippingService {
    @KafkaListener(topics = "inventory-reserved")
    void onInventoryReserved(InventoryReservedEvent event) {
        // create shipment - final happy-path step
    }
}

Notice: nobody orchestrates anybody. Every service only knows its own topics — add a fifth service (say, notification-service) and it just subscribes to whichever events it cares about, with zero changes to the existing four.

4. Type 2: Orchestration-based Saga

Concept

A dedicated Saga Orchestrator service owns the entire workflow as an explicit state machine. It issues commands to each participant one at a time and decides — based on each response — whether to move forward or trigger compensations backward. Participants become "dumb" — they just do what they're told and reply.

Internal working
OrderSagaOrchestrator→ command: CreateOrder→ order-service replies OrderCreated
Orchestrator→ command: DeductPayment→ payment-service replies Success/Failure
Orchestrator→ command: ReserveInventory→ inventory-service replies Success/Failure

If any reply is a failure, the orchestrator walks backward through the already-completed steps, issuing explicit compensating commands (RefundPayment, CancelOrder) in reverse order — it has full visibility of saga state at every point, usually persisted in its own DB so a crash mid-saga can resume where it left off.

enum SagaStep { ORDER_CREATED, PAYMENT_DONE, INVENTORY_DONE, SHIPPED, FAILED, COMPENSATED }

@Entity
class SagaState {
    @Id String sagaId;
    String orderId;
    @Enumerated(EnumType.STRING) SagaStep currentStep;
    // ... amount, productId etc for compensations
}

@Service
class OrderSagaOrchestrator {
    private final SagaStateRepository sagaRepo;
    private final KafkaTemplate<String, Object> kafka;

    void startSaga(CreateOrderRequest req) {
        String sagaId = UUID.randomUUID().toString();
        sagaRepo.save(new SagaState(sagaId, null, SagaStep.ORDER_CREATED));
        kafka.send("order.create.cmd", new CreateOrderCommand(sagaId, req));
    }

    @KafkaListener(topics = "order.create.reply")
    void onOrderCreated(OrderCreatedReply reply) {
        SagaState saga = sagaRepo.findById(reply.sagaId()).orElseThrow();
        if (reply.success()) {
            saga.setCurrentStep(SagaStep.ORDER_CREATED);
            sagaRepo.save(saga);
            kafka.send("payment.deduct.cmd", new DeductPaymentCommand(reply.sagaId(), reply.amount()));
        } else {
            failSaga(saga);   // nothing to compensate yet, first step
        }
    }

    @KafkaListener(topics = "payment.deduct.reply")
    void onPaymentReply(PaymentReply reply) {
        SagaState saga = sagaRepo.findById(reply.sagaId()).orElseThrow();
        if (reply.success()) {
            saga.setCurrentStep(SagaStep.PAYMENT_DONE);
            sagaRepo.save(saga);
            kafka.send("inventory.reserve.cmd", new ReserveInventoryCommand(reply.sagaId()));
        } else {
            compensate(saga, SagaStep.PAYMENT_DONE);   // walk backward: cancel order
        }
    }

    @KafkaListener(topics = "inventory.reserve.reply")
    void onInventoryReply(InventoryReply reply) {
        SagaState saga = sagaRepo.findById(reply.sagaId()).orElseThrow();
        if (reply.success()) {
            saga.setCurrentStep(SagaStep.INVENTORY_DONE);
            sagaRepo.save(saga);
            kafka.send("shipping.create.cmd", new CreateShipmentCommand(reply.sagaId()));
        } else {
            compensate(saga, SagaStep.INVENTORY_DONE);  // walk backward: refund + cancel order
        }
    }

    private void compensate(SagaState saga, SagaStep failedAt) {
        if (failedAt == SagaStep.INVENTORY_DONE) {
            kafka.send("payment.refund.cmd", new RefundPaymentCommand(saga.getSagaId()));
        }
        kafka.send("order.cancel.cmd", new CancelOrderCommand(saga.getSagaId()));
        saga.setCurrentStep(SagaStep.COMPENSATED);
        sagaRepo.save(saga);
    }

    private void failSaga(SagaState saga) {
        saga.setCurrentStep(SagaStep.FAILED);
        sagaRepo.save(saga);
    }
}

// participants become simple command-handlers, e.g.:
@Service
class PaymentCommandHandler {
    @KafkaListener(topics = "payment.deduct.cmd")
    void handle(DeductPaymentCommand cmd) {
        boolean ok = paymentRepo.tryDeduct(cmd.sagaId(), cmd.amount());
        kafka.send("payment.deduct.reply", new PaymentReply(cmd.sagaId(), ok));
    }

    @KafkaListener(topics = "payment.refund.cmd")
    void handleRefund(RefundPaymentCommand cmd) {
        paymentRepo.refund(cmd.sagaId());
    }
}

The orchestrator is the single source of truth for "where is this saga right now" — you can query SagaState at any time to see exactly which step an order is stuck at, which is much harder in choreography where the "state" is implicit, scattered across everyone's event logs.

5. Deep dive — compensations, idempotency, ordering, state

Compensating transactions aren't a mirror-image rollback

A compensating transaction is a new, independent business operation, not an automatic reversal — "refund payment" is its own transaction with its own audit trail, not SQL's ROLLBACK. This matters because some steps are genuinely not compensatable — you can't un-send an email. For steps like that, sagas either place them last in the sequence (so nothing after them can fail and force a compensation) or design a "best-effort" compensation (e.g. sending a follow-up "please ignore the previous email" notice).

Idempotency is non-negotiable

Kafka (and most brokers) guarantee at-least-once delivery — a consumer can receive the same event twice (retry after a crash, rebalance, etc). Every command/event handler in a saga must be idempotent: e.g. payment-service should track a processed sagaId/orderId and skip re-deducting money if it sees the same command twice. Without this, a network blip can silently double-charge a customer.

Event ordering

In choreography especially, you must guarantee a service processes events for the same orderId in order — otherwise InventoryFailed could theoretically be processed before PaymentCompleted if events race. Kafka gives ordering guarantees per-partition, so partitioning topics by orderId (as the message key) ensures all events for one order land on the same partition and are consumed in order.

Where does saga "state" live?

Choreography has no explicit saga state — the current status of an order is implicitly derivable only by replaying/aggregating events, which makes debugging "why is this order stuck" harder. Orchestration persists explicit state (like the SagaState entity above), so the orchestrator can resume a crashed saga from exactly where it left off, and ops teams can query "show me all sagas stuck at PAYMENT_DONE."

6. Choreography vs Orchestration — when to pick which

ChoreographyOrchestration
ControlDecentralized — no single ownerCentralized — one orchestrator owns the flow
CouplingLoosely coupled — services don't know each otherOrchestrator knows about every participant
Adding a new stepEasy — new service just subscribes to an eventRequires updating the orchestrator's logic
Debuggability / visibilityHard — must trace across many services' logsEasy — orchestrator's state machine shows exact status
Best forSimple flows, few steps (2-4), teams wanting max autonomyComplex flows, many steps, conditional branching, need for auditability
Common risk"Event soup" — implicit, undocumented coupling; cyclic event dependenciesOrchestrator becomes a god-service/single point of failure if not made highly available

A practical rule interviewers like: start with choreography for 2-3 step flows; move to orchestration once you have 4+ steps, branching logic, or need a clear operational view of "where is this transaction right now."

7. 10 Interview Questions & Answers — designed to impress

1.Why can't you just use a distributed transaction (2PC) across microservices instead of Saga?
Two-Phase Commit requires a coordinator to hold locks across all participating databases until every participant votes commit, which blocks resources for the duration and doesn't scale under microservice-style high concurrency; it also assumes all participants support XA transactions, which most modern NoSQL/cloud-managed databases and message brokers don't. Saga trades strict ACID atomicity for eventual consistency achieved via compensations, which fits distributed, independently-deployed services far better.
Impress factor: naming 2PC/XA explicitly and explaining *why* it doesn't scale (blocking locks) shows you understand the alternative being rejected, not just the pattern being used.
2.What exactly is a "compensating transaction," and how is it different from a rollback?
A rollback undoes a transaction before it commits, using the database's own log — it's automatic and free. A compensating transaction is a deliberate, separate business operation that semantically reverses an already-committed transaction's effect — e.g. "refund" instead of "un-deduct." It has its own transaction, its own audit trail, and must be explicitly written by the developer for every step that has side effects.
3.Why must every saga participant be idempotent?
Because message brokers like Kafka guarantee at-least-once delivery, not exactly-once, so a consumer can receive and process the same command/event twice (e.g. after a rebalance or a retry). Without idempotency — usually implemented by tracking a unique operation/saga ID and skipping already-processed ones — a duplicate delivery could double-deduct payment or double-reserve stock, silently corrupting state.
Impress factor: this is the #1 follow-up interviewers ask after "explain saga" — bringing it up unprompted signals production experience, not just textbook knowledge.
4.How do you guarantee event ordering in a choreography-based saga using Kafka?
Partition the topic by a key that groups all events for one business transaction together — typically orderId — since Kafka only guarantees ordering within a single partition, not across the whole topic. All events for the same order then land on the same partition and are consumed strictly in the order they were produced.
5.What happens if the orchestrator itself crashes mid-saga in the orchestration approach?
Because saga state is persisted (not held only in memory), the orchestrator can reload the last known SagaState for in-flight sagas on restart and resume issuing commands from that step — this is why orchestration typically requires its own durable state store, unlike choreography where "state" is implicit across event logs.
6.Is Saga strongly consistent or eventually consistent, and what does that mean practically for users?
Eventually consistent — there's a window where, say, an order shows as CREATED before payment/inventory steps resolve, and if a later step fails, the system briefly shows a state (like "paid") that later gets compensated (refunded). Practically, this means UX needs to communicate transient states honestly ("processing your order") rather than assuming an instant, all-or-nothing result like a monolithic transaction would give.
7.What's a scenario where a step genuinely cannot be compensated, and how do you design around it?
Sending a confirmation email or SMS can't be "un-sent." The standard mitigation is to sequence non-compensatable steps last in the saga, after all compensatable/reversible steps have already succeeded, so a later failure never needs to undo them — e.g. shipping notification goes out only after payment and inventory are both confirmed, minimizing the chance it needs to be walked back.
8.How would you monitor and debug a stuck saga in production?
With orchestration, query the persisted SagaState table directly for sagas stuck at a given step past some time threshold, and alert on them. With choreography, since there's no central state, you typically need distributed tracing (correlation/saga ID propagated through every event and log line) plus a saga "read model" built by consuming all the events into a dashboard, since there's no single source of truth to query.
Impress factor: contrasting the operational cost of choreography's lack of centralized visibility shows real-world judgment, not just pattern memorization.
9.Can you mix choreography and orchestration in the same system?
Yes — it's common in larger systems to orchestrate the high-level, critical multi-step business workflow (e.g. order fulfillment) explicitly, while individual services internally react to fine-grained events choreography-style for secondary concerns like analytics, notifications, or audit logging that don't need to affect the saga's success/failure path.
10.How does Saga relate to the Transactional Outbox pattern, and why are they often used together?
A service's local transaction (e.g. "create order" + "insert an OrderCreated row into an outbox table") happens atomically in the same DB transaction; a separate poller/CDC process then reliably publishes that outbox row to Kafka. This solves the "dual write" problem — without it, a service could commit its DB change but crash before publishing the event (or vice versa), silently breaking the saga. Transactional Outbox guarantees the event is published if and only if the local transaction committed, which is exactly the reliability guarantee a saga step depends on.
Impress factor: this is the single most senior-sounding answer you can give on Saga — it shows you know the pattern isn't safe in isolation without solving the dual-write problem underneath it, and directly matches what you've already rehearsed for your HealthWatch narrative.
