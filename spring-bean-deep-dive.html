Part A — Foundations
SPEC-01

What Is a Spring Bean?

A bean is just an ordinary Java object — but one whose creation, wiring, and lifecycle are handed over to the Spring IoC (Inversion of Control) container instead of being managed by your own new SomeClass() calls. "IoC" describes exactly this handover: control over object creation and dependency wiring is inverted — it moves from your code to the framework.

Concretely, the container (an ApplicationContext) reads a set of instructions — a bean definition — describing how to build an object, what it depends on, and how long it should live. It then instantiates, wires, and manages that object for you: that managed object is the bean.

  • Beans live in the ApplicationContext (a BeanFactory under the hood), which acts as a registry you can query by type or name.
  • The container also resolves each bean's dependencies automatically — this is Dependency Injection (DI), the practical mechanism that makes IoC useful day to day.
  • Not every object in a Spring app is a bean — a plain DTO you build with new inside a method is not container-managed and is not a bean.
Without Spring — you own the wiring
OrderRepository repo = new OrderRepositoryImpl(new DataSource(...));
OrderService service = new OrderService(repo); // manual, brittle, hard to test
With Spring — container owns the wiring
@Service
public class OrderService {
    private final OrderRepository repo;

    // Spring finds an OrderRepository bean and injects it — you never call new
    public OrderService(OrderRepository repo) {
        this.repo = repo;
    }
}
Say this: "A bean is any object whose lifecycle — creation, dependency wiring, and destruction — is managed by the Spring IoC container instead of my own code. IoC is the principle; Dependency Injection is the mechanism that implements it."
SPEC-02

Every Way to Create/Register a Bean

Prompt: "What are the different ways to create a bean in Spring?"

All roads lead to the same place — a bean definition registered in the container — but there are five distinct ways to get there:

  • Stereotype annotations + component scan — @Component and its specializations @Service, @Repository, @Controller/@RestController on classes you own. Discovered automatically by @ComponentScan.
  • @Bean methods inside @Configuration — explicit factory methods, most useful for classes you don't own or construction logic that needs code.
  • XML configuration — the legacy <bean> tag in an XML context file. Rare in new code, but still shows up in older enterprise codebases.
  • @Import — pull in another @Configuration class (or even @Component-annotated class) explicitly, without relying on component scanning to find it.
  • Programmatic registration — register a bean at runtime directly against the context, e.g. via ApplicationContextInitializer or GenericApplicationContext.registerBean() — used by frameworks and advanced bootstrapping, rarely in everyday app code.
1 — Stereotype annotation (component scan)
@Service
public class PricingService { }
2 — @Bean inside @Configuration
@Configuration
public class AppConfig {
    @Bean
    public RestTemplate restTemplate() {
        return new RestTemplate();
    }
}
3 — XML (legacy)
<bean id="restTemplate" class="org.springframework.web.client.RestTemplate"/>
4 — @Import
@Configuration
@Import({ SecurityConfig.class, CacheConfig.class })
public class AppConfig { }
5 — Programmatic registration
GenericApplicationContext ctx = new GenericApplicationContext();
ctx.registerBean(AuditLogger.class, () -> new AuditLogger("audit.log"));
ctx.refresh();
Say this: "In practice it's almost always stereotype annotations for my own classes, and @Bean methods in a @Configuration class for third-party or conditionally-built objects. XML and programmatic registration exist but are rare in modern Spring Boot code."
SPEC-03

@Component vs @Bean — The Real Difference

Prompt: "What's the difference between @Component and @Bean?"

They both end with "a bean in the container," but they operate at completely different levels: one is a class-level marker discovered by scanning; the other is a method-level factory you write by hand.

Aspect@Component@Bean
Applied toA class declarationA method inside a @Configuration class
How it's foundAuto-detected via @ComponentScanExplicitly written, not scanned for — the method itself is the registration
Who owns the classYou — you can put the annotation on itAnyone — perfect for third-party / library classes you can't annotate
Construction logicWhatever the constructor does; limited flexibilityFull Java method body — conditionals, builders, factory calls, external SDK setup
Multiple instances of same typeAwkward — one class, one componentTrivial — write two @Bean methods returning the same type with different config
Typical useYour own services, repositories, controllersSDK clients, DataSources, ObjectMapper customization, anything needing setup code
@Component — you own PricingService, so annotate it directly
@Service
public class PricingService {
    public PricingService() { }
}
@Bean — you DON'T own OkHttpClient, so wrap it in a factory method
@Configuration
public class HttpClientConfig {
    @Bean
    public OkHttpClient okHttpClient() {
        return new OkHttpClient.Builder()
                .connectTimeout(Duration.ofSeconds(5))
                .build(); // can't put @Component on a class you don't control
    }
}
Say this: "@Component is a class-level stereotype found by component scanning — for classes I own. @Bean is a method I write inside a @Configuration class that explicitly returns an object — the go-to when I need construction logic or I'm registering a class I don't control, like a third-party client."
SPEC-04

Why @Configuration + Manual @Bean, When @Component Exists?

Prompt: "If @Component already registers a bean automatically, why do we bother writing @Configuration classes and manually defining beans?"

Because @Component only works when three conditions all hold: you own the source, a single no-argument-ish constructor is enough, and one instance of that type is all you'll ever need. The moment any of those breaks, you need a hand-written factory — that's what @Bean inside @Configuration is for. Concretely:

  • Third-party classes — you cannot add @Component to a class from a JAR you don't own (e.g. ObjectMapper, RestTemplate, an AWS SDK client). A @Bean method is the only way to hand that object to the container.
  • Non-trivial construction logic — builder chains, conditional setup, reading values from multiple properties, try/catch around a resource — a constructor can't express this as cleanly as a plain Java method body can.
  • Multiple beans of the same type — e.g. two DataSources (primary + reporting replica). One class can't be annotated twice; two @Bean methods handle it naturally, disambiguated with names or @Qualifier.
  • Conditional / environment-specific beans — using @Profile or @ConditionalOnProperty on a @Bean method to swap implementations (mock vs real payment gateway) per environment.
  • Centralizing infra config — grouping every low-level bean (DataSource, security filter chain, cache manager) in dedicated @Configuration classes keeps that concern out of your business-logic classes, which stay pure @Components.
Two beans, same type, disambiguated
@Configuration
public class DataSourceConfig {

    @Bean @Primary
    public DataSource primaryDataSource() {
        return DataSourceBuilder.create().url("jdbc:postgresql://primary/db").build();
    }

    @Bean
    public DataSource reportingDataSource() {
        return DataSourceBuilder.create().url("jdbc:postgresql://replica/db").build();
    }
}

// consumer picks explicitly
public ReportService(@Qualifier("reportingDataSource") DataSource ds) { ... }
Say this: "@Component works when I own the class and need exactly one instance built a simple way. I reach for @Configuration + @Bean whenever any of that breaks — third-party classes, construction logic that needs real code, multiple instances of the same type, or environment-conditional beans."
Part B — Wiring & Behavior
SPEC-05

Dependency Injection Styles

Once a bean exists, Spring has to hand it its own dependencies. There are three mechanisms — and modern Spring guidance is clear about which one to default to:

  • Constructor injection (preferred) — dependencies passed via the constructor, stored in final fields. The object can never exist in a half-wired state, dependencies are visible at a glance, and it plays perfectly with immutability.
  • Setter injection — dependencies set via public setters after construction. Useful for genuinely optional dependencies, but the object can exist momentarily unwired.
  • Field injection — @Autowired directly on a field. Least boilerplate, but hides dependencies from the constructor signature, makes the class hard to unit test without Spring or reflection, and is explicitly discouraged by the Spring team.
Constructor injection — the default choice
@Service
public class OrderService {
    private final OrderRepository repo;
    private final PaymentClient paymentClient;

    // with a single constructor, @Autowired is optional (Spring 4.3+)
    public OrderService(OrderRepository repo, PaymentClient paymentClient) {
        this.repo = repo;
        this.paymentClient = paymentClient;
    }
}
Field injection — works, but avoid it
@Service
public class OrderService {
    @Autowired
    private OrderRepository repo; // can't be final, hard to test in isolation
}
Say this: "Constructor injection by default — it enables final fields, makes required dependencies explicit, and lets me construct the class in a plain unit test without a Spring context. Field injection I avoid; it hides dependencies and breaks easily-testable design."
SPEC-06

Bean Scopes

Prompt: "What bean scopes does Spring support?"

Scope determines how many instances the container creates and how long each lives.

ScopeLifetimeNotes
singleton (default)One instance per containerShared by every injection point — must be stateless/thread-safe
prototypeNew instance every time it's requestedContainer does not manage destruction after handing it out
requestOne instance per HTTP requestWeb-aware contexts only
sessionOne instance per HTTP sessionWeb-aware contexts only
applicationOne instance per ServletContextSimilar to singleton, but scoped to the web app
Injecting a prototype bean into a singleton — the classic trap
// naive version: the prototype is injected ONCE at singleton construction,
// so every call sees the SAME instance — defeats the purpose of "prototype"
@Component
public class ReportRunner {
    private final ReportBuilder builder; // prototype-scoped
    public ReportRunner(ReportBuilder builder) { this.builder = builder; }
}

// fix: inject an ObjectProvider (or use scoped-proxy) to get a FRESH instance per call
@Component
public class ReportRunner {
    private final ObjectProvider<ReportBuilder> builderProvider;
    public ReportRunner(ObjectProvider<ReportBuilder> builderProvider) {
        this.builderProvider = builderProvider;
    }
    public void run() {
        ReportBuilder fresh = builderProvider.getObject(); // new instance, every call
    }
}
Say this: "Singleton is the default and covers most services. Prototype gives a new instance per lookup — but injecting one directly into a singleton only wires it once, so I'd use ObjectProvider or a scoped-proxy to get a fresh instance on every call. Request/session/application only apply in web-aware contexts."
SPEC-07

Bean Lifecycle

Prompt: "Walk me through the lifecycle of a Spring bean."

From container startup to shutdown, a singleton bean passes through a well-defined sequence:

  • 1. Instantiation — constructor is called (or the @Bean factory method runs).
  • 2. Populate properties — dependencies are injected (constructor args already set at step 1; setter/field injection happens here).
  • 3. Aware interfaces — if implemented, callbacks like BeanNameAware, BeanFactoryAware, ApplicationContextAware fire, giving the bean access to container internals.
  • 4. BeanPostProcessor — before initialization — postProcessBeforeInitialization() runs for every registered post-processor (this is how @Autowired, @Value, and AOP proxies actually get applied under the hood).
  • 5. Initialization callbacks — in order: @PostConstruct method → InitializingBean.afterPropertiesSet() → custom init-method (if configured).
  • 6. BeanPostProcessor — after initialization — postProcessAfterInitialization(); this is also where proxying (e.g. for @Transactional) typically wraps the bean.
  • 7. Bean is ready — sits in the container, available for injection, until shutdown.
  • 8. Destruction — on container shutdown: @PreDestroy → DisposableBean.destroy() → custom destroy-method. Only singleton beans get this — prototypes are handed off and the container stops tracking them.
Lifecycle callbacks in one class
@Component
public class CacheWarmer implements InitializingBean, DisposableBean {

    @PostConstruct
    public void onPostConstruct() {
        System.out.println("1. @PostConstruct — warm the cache");
    }

    @Override
    public void afterPropertiesSet() {
        System.out.println("2. InitializingBean.afterPropertiesSet()");
    }

    @PreDestroy
    public void onPreDestroy() {
        System.out.println("flush cache before shutdown");
    }

    @Override
    public void destroy() {
        System.out.println("DisposableBean.destroy()");
    }
}
Say this: "Construct → inject dependencies → Aware callbacks → BeanPostProcessor before-init → @PostConstruct/InitializingBean/init-method → BeanPostProcessor after-init (this is where proxies get applied) → ready → on shutdown, @PreDestroy/DisposableBean/destroy-method, for singletons only."
SPEC-08

Resolving Multiple Candidates

Prompt: "You have two beans of the same type — how does Spring know which to inject?"

By default it doesn't — and that's a startup failure, not a silent guess (see Module 11 in the companion Spring Boot notes on BeanDefinitionOverrideException vs NoUniqueBeanDefinitionException). You resolve ambiguity explicitly:

  • @Primary on one candidate — makes it the default whenever a qualifier isn't specified.
  • @Qualifier("beanName") at the injection point — picks a specific bean by name, overriding @Primary if both are present.
  • Matching the parameter/field name to the bean name also works, since Spring falls back to by-name matching when there's a type conflict — but explicit @Qualifier is clearer.
@Primary + @Qualifier together
@Service @Primary
public class RazorpayGateway implements PaymentGateway { }

@Service
public class StripeGateway implements PaymentGateway { }

@Service
public class CheckoutService {
    public CheckoutService(@Qualifier("stripeGateway") PaymentGateway gateway) {
        // explicitly wants Stripe, overriding @Primary's default of Razorpay
    }
}
Say this: "@Primary marks the default candidate; @Qualifier at the injection point picks a specific one by name and wins over @Primary if both exist. With no disambiguation at all, Spring fails fast at startup rather than guessing."
SPEC-09

Full vs Lite @Configuration Mode

Prompt: "If a @Bean method calls another @Bean method directly, do you get two instances or one?"

One — and this is a genuinely sharp interview question, because the answer looks like it should be "two" if you think of @Bean methods as plain Java methods.

When a class is annotated @Configuration (not @Component), Spring generates a CGLIB subclass proxy of it at startup — this is "full" mode. Every call to another @Bean method on this is intercepted by the proxy, which checks the container first: if that bean already exists, the proxy returns the cached singleton instead of actually running the method body again.

  • @Configuration (full mode) — CGLIB-proxied; inter-bean method calls are intercepted and return the same singleton. This is what guarantees singleton semantics even when beans reference each other.
  • @Configuration(proxyBeanMethods = false) or plain @Component with @Bean methods (lite mode) — no proxy; calling another @Bean method directly really does re-run its body and create a second, separate object.
Full mode — same instance, guaranteed
@Configuration // CGLIB-proxied by default
public class AppConfig {

    @Bean
    public ObjectMapper objectMapper() {
        return new ObjectMapper();
    }

    @Bean
    public JsonExporter jsonExporter() {
        // intercepted by the proxy → returns the SAME ObjectMapper singleton
        return new JsonExporter(objectMapper());
    }
}
Say this: "@Configuration classes are CGLIB-proxied by default (full mode) — calling one @Bean method from another goes through the proxy and returns the existing singleton rather than re-running the constructor. With proxyBeanMethods=false, or plain @Component, you lose that guarantee and get two separate objects."
Part C — Advanced
SPEC-10

FactoryBean vs @Bean Factory Method

Prompt: "What's the difference between implementing FactoryBean and just writing a @Bean method?"

Both ultimately produce an object for the container, but they solve it at different layers:

  • @Bean method — a simple, imperative "build and return" step. The right tool 95% of the time.
  • FactoryBean<T> interface — a reusable, encapsulated factory component. You implement getObject(), getObjectType(), and isSingleton(); Spring detects the interface and registers the product of getObject() as the bean — not the factory itself. This is how libraries like MyBatis and early Hibernate integrations plugged complex object construction into Spring before Java config existed, and it's still useful when you want the construction logic packaged as its own reusable, testable unit.
FactoryBean implementation
public class SqlSessionFactoryBean implements FactoryBean<SqlSessionFactory> {

    @Override
    public SqlSessionFactory getObject() throws Exception {
        return new SqlSessionFactoryBuilder().build(configuration());
    }

    @Override
    public Class<?> getObjectType() { return SqlSessionFactory.class; }

    @Override
    public boolean isSingleton() { return true; }
}

// registering it yields a SqlSessionFactory bean, NOT a SqlSessionFactoryBean bean
// (prefix the name with '&' to get the factory itself: ctx.getBean("&mySessionFactory"))
Say this: "A @Bean method is the everyday, imperative way to register something. FactoryBean is a reusable component whose getObject() supplies the actual bean — Spring registers the product, not the factory — and it's the pattern libraries use to plug non-trivial construction logic into the container."
SPEC-11

Conditional Bean Registration

Prompt: "How would you register a bean only in certain environments, or only if another bean isn't already defined?"

Spring Boot's auto-configuration is built almost entirely on conditional @Bean definitions — the same annotations are just as usable in application code:

  • @Profile("dev") — only registered when that Spring profile is active.
  • @ConditionalOnProperty(...) — gated on an application property's presence/value.
  • @ConditionalOnMissingBean — registered only if the container doesn't already have one of that type — this is exactly how Boot's auto-configured beans "back off" when you supply your own.
  • @ConditionalOnClass — registered only if a given class is present on the classpath (how Boot decides whether to configure Redis support at all, for example).
Swap gateway implementation per environment
@Configuration
public class PaymentConfig {

    @Bean
    @Profile("dev")
    public PaymentGateway mockGateway() {
        return new MockPaymentGateway();
    }

    @Bean
    @Profile("prod")
    public PaymentGateway razorpayGateway() {
        return new RazorpayGateway();
    }

    // back off if the app already defines its own MeterRegistry
    @Bean
    @ConditionalOnMissingBean(MeterRegistry.class)
    public MeterRegistry defaultMeterRegistry() {
        return new SimpleMeterRegistry();
    }
}
Say this: "@Profile swaps implementations per environment, @ConditionalOnProperty gates on a config flag, and @ConditionalOnMissingBean lets my default back off if the app supplies its own — the exact mechanism Spring Boot's own auto-configuration uses."
SPEC-12

Circular Dependency Between Beans

Prompt: "Bean A depends on Bean B, and Bean B depends on Bean A. What happens?"

The outcome depends entirely on which injection style is used:

  • Setter/field injection — Spring can usually resolve it. It creates a bean's raw instance first, registers it in an "early reference" cache, then finishes wiring — so the circular reference can be satisfied with a not-yet-fully-initialized object.
  • Constructor injection on both sides — cannot be resolved. Neither object can finish constructing without the other already existing. Spring throws BeanCurrentlyInCreationException at startup.

Either way, a circular dependency is usually a design smell — the real fix is almost always to break the cycle: extract the shared behavior into a third bean both depend on, or use @Lazy on one side to defer resolution, rather than leaning on setter injection as a permanent workaround.

Fails — constructor injection, no escape
@Service
public class ServiceA {
    public ServiceA(ServiceB b) { } // needs a fully-built ServiceB
}
@Service
public class ServiceB {
    public ServiceB(ServiceA a) { } // needs a fully-built ServiceA — deadlock
}
Workaround (use sparingly) — @Lazy breaks the cycle
public ServiceA(@Lazy ServiceB b) { } // injects a proxy, resolved on first use
Say this: "With constructor injection on both sides it fails at startup with BeanCurrentlyInCreationException — neither bean can finish building first. Setter injection can resolve it via an early-reference cache, but I'd treat the cycle itself as a design smell and extract the shared logic into a third bean instead."
SPEC-13

@Lazy and @DependsOn

Two small annotations that control when and in what order beans get created, on top of the default (eager, dependency-order) behavior:

  • @Lazy on a bean — delays its creation until first use, and injects a proxy in the meantime. Useful for rarely-used or expensive-to-build beans, and as an escape hatch for circular dependencies (see Module 12).
  • @DependsOn("beanName") — forces one bean to be initialized after another, even when there's no direct field/constructor dependency between them — e.g. a cache warmer that must run only after a JDBC connection pool bean is fully up.
@DependsOn — no direct reference, but strict ordering needed
@Component
@DependsOn("connectionPoolInitializer")
public class CacheWarmer {
    // guaranteed to be constructed AFTER connectionPoolInitializer,
    // even though CacheWarmer never injects it directly
}
Say this: "@Lazy defers a bean's construction to first use — good for expensive or rarely-needed beans. @DependsOn enforces initialization order between beans that don't have a direct dependency relationship but still need one built before the other."
SPEC-14

Bean Definition vs Bean Instance

Worth separating clearly, because a lot of Spring's internal APIs (and questions about BeanDefinitionOverrideException) only make sense once this distinction is clear:

  • A BeanDefinition is metadata — the class name, scope, constructor args, property values, lazy flag, init/destroy method names. It's a blueprint, created when the container starts up and parses your annotations/config, before any actual object exists.
  • The bean instance is the real Java object, built later by following that blueprint — for a singleton, built once and cached; for a prototype, built fresh on every request.
  • This is why two conflicting @Bean definitions fail at the definition stage (before either object is ever constructed) — the container detects the metadata clash while assembling its registry, not at runtime when something is finally injected.
Inspecting definitions vs instances
ConfigurableApplicationContext ctx = ...;

// metadata — no object created yet
BeanDefinition def = ctx.getBeanFactory().getBeanDefinition("pricingService");
System.out.println(def.getScope()); // e.g. "singleton"

// actual object — created (or fetched from cache) on demand
PricingService instance = ctx.getBean(PricingService.class);
Say this: "A BeanDefinition is the blueprint the container parses at startup — class, scope, dependencies. The bean instance is the actual object built from that blueprint, later, on demand. Definition conflicts are caught before any object is even constructed."
Rapid Reference — Interview Q&A Bank
Tap to expand a clean, interview-ready answer for each.
Q01What is a Spring bean?

An object whose creation, dependency wiring, and lifecycle are managed by the Spring IoC container instead of your own code — registered against a bean definition and retrievable from the ApplicationContext.

Q02What are the different ways to create/register a bean?

Stereotype annotations (@Component and its specializations) with component scanning, @Bean factory methods inside @Configuration classes, legacy XML <bean> definitions, @Import to pull in configuration classes explicitly, and programmatic registration via GenericApplicationContext.registerBean() for advanced bootstrapping.

Q03What's the difference between @Component and @Bean?

@Component is a class-level annotation discovered automatically by component scanning — for classes you own. @Bean is a method-level annotation inside a @Configuration class that explicitly builds and returns an object — needed for third-party classes, non-trivial construction logic, or multiple instances of the same type.

Q04Why write @Configuration classes and manually define beans when @Component already does it automatically?

Because @Component only works when you own the class, need a single instance, and construction is trivial. @Bean methods are required for third-party/library classes, construction logic that needs real code, multiple beans of the same type, and environment-conditional beans.

Q05What's the difference between constructor, setter, and field injection?

Constructor injection (preferred) wires required dependencies at construction time via final fields — no half-wired state. Setter injection wires after construction, suited to optional dependencies. Field injection is the least boilerplate but hides dependencies and makes unit testing without a Spring context difficult — generally discouraged.

Q06What bean scopes does Spring support?

singleton (default, one instance per container), prototype (a new instance every lookup), and the web-aware scopes request, session, and application.

Q07What happens if you inject a prototype-scoped bean into a singleton?

The prototype is only resolved once, at singleton construction time, so every subsequent use sees the same instance — defeating the point of "prototype." Fix it by injecting an ObjectProvider (or a scoped-proxy) so a fresh instance is fetched on every call.

Q08Walk me through the full bean lifecycle.

Instantiate → populate dependencies → Aware interface callbacks → BeanPostProcessor before-init → @PostConstruct → InitializingBean.afterPropertiesSet() → custom init-method → BeanPostProcessor after-init (proxies applied here) → bean ready → on shutdown: @PreDestroy → DisposableBean.destroy() → custom destroy-method (singletons only).

Q09How do you resolve a conflict when two beans of the same type exist?

Mark one @Primary as the default, and use @Qualifier("beanName") at the injection point to pick a specific one explicitly — @Qualifier wins over @Primary when both are present. With no disambiguation, Spring fails at startup rather than guessing.

Q10If a @Bean method calls another @Bean method directly inside the same @Configuration class, do you get one instance or two?

One. @Configuration classes are CGLIB-proxied by default ("full" mode) — the proxy intercepts inter-bean method calls and returns the already-created singleton instead of re-running the method. With proxyBeanMethods=false, or on a plain @Component, that guarantee disappears and you get two separate objects.

Q11What's the difference between implementing FactoryBean and writing a @Bean method?

A @Bean method is a simple, direct "build and return" step — the default choice. FactoryBean<T> is a reusable component whose getObject() supplies the actual registered bean (not the factory itself) — useful when construction logic needs to be packaged as its own testable unit, as libraries like MyBatis do.

Q12How do you register a bean only for certain environments, or only if a property is set?

@Profile("dev"/"prod") gates a bean on the active Spring profile; @ConditionalOnProperty gates it on an application property; @ConditionalOnMissingBean registers a default only if the app hasn't already supplied its own — the same mechanism Spring Boot's auto-configuration uses internally.

Q13What happens with a circular dependency between two beans?

With setter/field injection, Spring can usually resolve it using an early-reference cache. With constructor injection on both sides, it cannot — neither bean can finish constructing without the other, and Spring throws BeanCurrentlyInCreationException at startup. The real fix is to break the cycle, e.g. by extracting shared logic into a third bean.

Q14What does @Lazy do, and when would you use it?

Defers a bean's construction until it's first actually used, injecting a proxy in the meantime — useful for expensive or rarely-used beans, and as a targeted fix for circular dependency deadlocks.

Q15What does @DependsOn do?

Forces one bean to be initialized only after another named bean, even when there's no direct injection relationship between them — useful for enforcing setup order (e.g. a cache warmer that must run after a connection pool is ready).

Q16What's the difference between a bean definition and a bean instance?

A BeanDefinition is metadata parsed at container startup — class, scope, dependencies, lifecycle method names. The bean instance is the actual object built from that metadata, later, on demand. Definition conflicts are caught while the registry is being assembled, before any instance is ever created.

Q17Are all Spring beans singletons?

Singleton is only the default scope, not a rule — a bean can be declared prototype, request, session, or application scoped depending on the annotation/config, so "one instance per container" only holds for the default case.

Q18Can a bean depend on itself, or reference an unfinished bean during construction?

Not with constructor injection — the object literally cannot exist until its constructor returns, so a self- or mutual-reference at that stage is unresolvable and fails fast. Setter/field injection can work around it via early references, but it's a sign the design should be restructured.
