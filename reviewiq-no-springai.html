    ReviewIQ — AI without Spring AI

    An e-commerce review analyser built as microservices. Every AI feature — chat, embeddings, RAG, streaming, memory, function calling — is written by hand against the OpenAI REST API using RestTemplate and WebClient.

    Java 21Spring Boot 3.5 EurekaSpring Cloud Gateway RestTemplateWebClient RedisPostgreSQL 4 services
    00

    What we are building, and why by hand

    The product

    An online store gets thousands of reviews per product. Nobody reads them all. ReviewIQ does three things:

    1. Summarises all reviews of a product into sentiment, top complaints and top praises.
    2. Answers questions about a product using only what real customers wrote — "how is the battery life?" — instead of the seller's marketing copy.
    3. Remembers the conversation, so the shopper can keep asking follow-ups.

    Why write the AI calls manually?

    Spring AI is a wrapper around the provider's REST API. Doing it yourself once teaches you what that wrapper is actually doing, and there are real situations where you have no choice:

    • The project is on an older Spring Boot version that Spring AI does not support.
    • Your company uses an internal LLM gateway with a custom API shape.
    • You need a provider feature that the abstraction has not exposed yet.
    • You are asked in an interview to explain how it works underneath.

    Why ai-service is separate

    The API key lives in exactly one service. If five services each called OpenAI directly you would have the key in five places, five different retry policies, and no single place to measure spend. Putting it behind one service means one config, one circuit breaker, one token counter.

    Honest note about the embedding column

    Storing a 1536-number vector as a comma-separated string and comparing in Java works fine up to a few thousand reviews. Beyond that you want the pgvector extension, which does the similarity search inside the database with a proper index. I kept it simple here so the maths is visible instead of hidden.

    discovery-server — Eureka

    Every service registers itself here with its name and address. Then review-service can call ai-service by name instead of hardcoding http://localhost:8081, and if we run three copies of ai-service the calls are load balanced automatically.

    Auth and rate limiting

    Why Redis and not a HashMap

    If the count lived in a Java map, running two gateway instances would let a user send double the limit, because each instance would have its own counter. Redis is shared, so the limit is correct however many gateways are running.

    07

    The OpenAI DTOs

    This is the part Spring AI normally hides. To call the API we have to build the exact JSON it expects and parse the exact JSON it returns.

    Two annotations that will save you a production incident
    • @JsonIgnoreProperties(ignoreUnknown = true) on every response class. Providers add fields without warning; without this your parsing breaks overnight.
    • @JsonInclude(NON_NULL) on the request. Sending "stream": null makes the API return 400.
    08

    The OpenAI client — RestTemplate

    This one class replaces ChatClient. It builds the headers, posts the body, and turns provider errors into something the rest of the app can handle.

    Why 4xx and 5xx are handled separately

    A 401 (bad key) or a 400 (bad request) will fail exactly the same way if you retry it — you are just wasting time. A 500 or a timeout is usually temporary and worth retrying. Treating them the same is a common mistake and it makes outages last longer than they should.

    09

    Streaming — WebClient and SSE

    RestTemplate cannot stream. When you set "stream": true, OpenAI keeps the connection open and sends lines like this:

    So we have to read line by line, strip the data: prefix, stop at [DONE], and pull the small piece of text out of each chunk.

    Why the stream ends with [DONE]

    OpenAI sends the literal text data: [DONE] as the last line. It is not JSON, so if you try to parse every line you get an exception at the very end of every request. takeUntil closes the stream cleanly instead.

    10

    Chat memory — by hand

    The model is stateless. It remembers nothing. So to make a conversation work we store the past messages ourselves and send them again with every request.

    load past messages→ system + history + new question→ OpenAI→ save question + answer
    Why the window is small

    Every message in the history is sent again on the next request, and you are billed for it every time. A window of 50 messages sounds generous until you see the prompt token count triple. Ten is usually plenty for a product Q&A.

    11

    ChatService — putting it together

    This service builds the message list (system, then history, then the new question), calls the client, and saves the result to memory.

    Why we expose our own DTO instead of OpenAI's

    AiChatRequest is our contract. If we ever swap OpenAI for Anthropic, only OpenAiClient changes — review-service does not notice. This is exactly the same idea as Spring AI's abstraction, just written by us at a smaller scale.

    RAG — written by hand

    This is the piece Spring AI's VectorStore normally does. We embed the question, compare it to every stored review with cosine similarity, and keep the best few.

    question→ embed it→ cosine similarity vs every review→ top 5→ build prompt→ answer
    Where this approach stops working

    We load every review into memory and compare them one by one. That is fine for a few thousand reviews. At a million it is too slow and uses too much memory, and you would move to pgvector so PostgreSQL does the search with a proper index.

    Worth saying out loud in an interview: "I did it in Java to keep the maths visible, but for real scale I would use pgvector."

    Which should you actually use?

    Use Spring AI for a new project on a current Spring Boot version. It is less code, fewer bugs, and provider switching is genuinely one line.

    Do it manually when you are on an old Spring Boot, when your company routes AI calls through an internal gateway with a custom API, or when you need a brand-new provider feature the abstraction has not caught up with yet.

    Either way, having written it once means you know what the abstraction is hiding — which is exactly what an interviewer is checking when they ask "how does Spring AI work underneath?"

    What I would add next

    • pgvector instead of comparing in Java, once the review count grows.
    • Cache the summary in the product_summaries table and only regenerate when new reviews arrive — right now we pay for the same summary every time.
    • Token budget per user, counting tokensUsed into Redis so one user cannot spend the whole monthly budget.
    • Async embedding — creating the embedding on the request thread makes posting a review slower than it needs to be. A queue would fix that.
    • Tests with WireMock standing in for the OpenAI API, so tests do not cost money.
