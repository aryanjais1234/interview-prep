01 String Constant Pool (SCP)

What is SCP? String Constant Pool is a special memory area inside the Heap where Java stores String literals to save memory and reuse immutable String objects.

String s1 = "Hello";
String s2 = "Hello";

What happens? Only ONE object is created in SCP. Both references point to the same object.

SCP:
[ "Hello" ]
   ↑     ↑
   s1    s2

How JVM decides:

Does this literal already exist in SCP?
   YES → reuse existing object
   NO  → create new object
System.out.println(s1 == s2);   // true  (same SCP reference)

02 new String() Behaviour

String s1 = new String("Hello");

Step 1: Literal "Hello" gets stored in SCP.
Step 2: new String("Hello") creates a separate Heap object.

SCP:  [ "Hello" ]
Heap: [ new String("Hello") ]  ← s1 points here
⚠️ new String() always creates a new Heap object even if the same content already exists in SCP.
String s1 = new String("Hello");  // 2 objects: 1 SCP + 1 Heap
String s2 = "Hello";               // 0 new objects (reused from SCP)
// Grand Total = 2

03 How Many Objects? – Classic Interview Trap

String s1 = new String("Java");  // 1 Heap + 1 SCP = 2
String s2 = "Java";               // "Java" already in SCP → 0 new
// Total = 2

04 == vs equals()

==equals()
ComparesReference / Memory AddressContent / Value

System.out.println(s1 == s2);       // false → different Heap objects

05 intern() Method

Purpose: Returns the pooled reference from SCP.

String s1 = new String("Hello");   // s1 → Heap
String s2 = "Hello";               // s2 → SCP

System.out.println(s1 == s2);              // false (Heap vs SCP)
System.out.println(s1.intern() == s2);     // true  (both SCP now)
System.out.println(s1.intern());           // "Hello"
s1          → Heap object
s1.intern() → SCP object (same content)
s2          → SCP object

s1.intern() == s2 → true ✅

Proving SCP reuse with hashCode:

String s1 = new String("Java");
String s2 = "Java";

System.out.println(s1.intern().hashCode() == s2.hashCode()); // true
// Both resolve to same SCP object → same hashCode
💡 intern() is used to get reference from SCP. Key term for interviews.

06 String Immutability

Immutable = once created, the value cannot be changed (unmodifiable / unchangeable).

String s = "Java";
s.concat("Tech");          // creates a NEW object – does NOT modify s
System.out.println(s);    // Output: Java  (original unchanged)

What happens internally:

Before:   SCP → [ "Java" ]  ← s
After:    SCP → [ "Java" ]  ← s (still pointing here)
                [ "JavaTech" ]  ← new object, not assigned to s

Correct way to capture the result:

s = s.concat("Tech");      // reassign reference
System.out.println(s);    // JavaTech

Reference independence:

String s = "Hello";
String a = s;

s = s.concat(" World");

System.out.println(s);   // Hello World
System.out.println(a);   // Hello  ← a still points to original
🔑 Key Rule: Strings never change. Only references change.

07 Why is String Immutable? – 5 Reasons

Reason 1: Security

// If String were mutable:
String password = "secret123";
// 5 references point to this password
// One modifies it → ALL 5 get corrupted → Security breach!
// Immutability ensures no shared reference can be altered

Reason 2: String Pool Possible ONLY because of Immutability

// If strings were mutable, reusing from SCP would be dangerous
String a = "Java";
String b = "Java";
// Both safely share one SCP object → memory saved ✅

Reason 3: Thread Safety

// Immutable objects are inherently thread-safe
// Multiple threads can read the same String without synchronization
// No thread can modify it → no race condition

Reason 4: HashCode Caching → Faster HashMap

// hashCode is computed ONCE at creation time and cached
Map<String, Integer> map = new HashMap<>();
map.put("Java", 1);
map.get("Java");   // hashCode already cached → O(1) faster lookup

Reason 5: Class Loading Safety

JVM uses String to load class names. If String were mutable, a class name could be altered mid-loading → security vulnerability.

09 Compile-Time vs Runtime Concatenation

Compile-Time (optimized by compiler)

String s1 = "Hello";
String s2 = "Hel" + "lo";       // compiler merges → "Hello" at compile time

System.out.println(s1 == s2);   // true → same SCP object

Runtime (creates new Heap object)

String a  = "Hel";              // non-final variable
String s1 = "Hello";
String s2 = a + "lo";           // runtime: JVM uses StringBuilder internally

System.out.println(s1 == s2);   // false → s1 in SCP, s2 in Heap

Internally, JVM converts runtime + to:

new StringBuilder().append(a).append("lo").toString();
// → creates new Heap object

10 final Variable Optimization

final String a = "Hel";         // compile-time constant
String s1 = "Hello";
String s2 = a + "lo";           // compiler optimizes → "Hello" at compile time

System.out.println(s1 == s2);   // true → same SCP object
✅ Key Rule: final String literals become compile-time constants. Compiler optimizes concatenation before runtime.

Real-time Usage – StringBuilder in DAO Layer

public String buildQuery(String table, List<String> columns) {
    StringBuilder query = new StringBuilder("SELECT ");
    for (String col : columns) {
        query.append(col).append(", ");  // same object modified in-place
    }
    query.append("FROM ").append(table);
    return query.toString();
}

❌ BAD vs ✅ GOOD Pattern

// ❌ BAD – new object created on every iteration
String query = "";
for (String col : columns) {
    query += col + ", ";   // wasteful!
}

// ✅ GOOD – single object modified in-place
StringBuilder query = new StringBuilder();
for (String col : columns) {
    query.append(col).append(", ");
}

12 hashCode() in String

Internal formula:

hash = hash * 31 + currentCharacter

Why 31? It is a prime number — reduces collision probability and is efficient for bit-shifting optimization.

String s1 = "FB";
String s2 = "Ea";

System.out.println(s1.hashCode());  // 2236
System.out.println(s2.hashCode());  // 2236
"FB":  F=70,  B=66  →  70*31 + 66 = 2236
"Ea":  E=69,  a=97  →  69*31 + 97 = 2236
⚠️ Same hashCode does NOT mean objects are equal!

13 Collision

Definition: Collision occurs when two unequal objects generate the same hashCode.

System.out.println("FB".hashCode());          // 2236
System.out.println("Ea".hashCode());          // 2236
System.out.println("FB".equals("Ea"));        // false → COLLISION
The Contract:
  Equal objects   MUST have same hashCode.       (equals true  → hashCode same)
  Same hashCode   does NOT mean equal objects.   (hashCode same → equals may be false)

14 HashSet Internal Working

HashSet internally uses HashMap.

Duplicate Check – 2 Steps:

Step 1: Check hashCode()
          │
          ├── hashCode different? → Store (different bucket)
          │
          └── hashCode same? → Go to Step 2
                    │
                    ├── equals() true?  → DUPLICATE → Rejected
                    └── equals() false? → COLLISION  → Both stored
HashSet<String> set = new HashSet<>();
set.add("FB");
set.add("Ea");
// Same hashCode but equals() → false → COLLISION → both stored
System.out.println(set.size());  // 2

15 equals() and hashCode() – Override Contract

The Problem – only equals() overridden

class Employee {
    int id;
    Employee(int id) { this.id = id; }

    @Override
    public boolean equals(Object o) {
        Employee e = (Employee) o;
        return this.id == e.id;
    }
    // hashCode NOT overridden!
}

HashSet<Employee> set = new HashSet<>();
set.add(new Employee(1));
set.add(new Employee(1));

System.out.println(set.size());  // 2 ❌ (expected 1)
✅ Rule: Whenever equals() is overridden, ALWAYS override hashCode() too.

Correct Implementation

class Employee {
    int id;
    String name;
    int salary;

    public Employee(int id, String name, int salary) {
        this.id = id; this.name = name; this.salary = salary;
    }

    @Override
    public boolean equals(Object o) {
        Employee e = (Employee) o;
        return id == e.id && Objects.equals(name, e.name);
        // salary intentionally excluded
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, name);  // same fields as equals()
    }
}

Employee e1 = new Employee(101, "Aryan", 550);
Employee e2 = new Employee(101, "Aryan", 600);  // different salary

HashSet<Employee> set = new HashSet<>();
set.add(e1); set.add(e2);
System.out.println(set.size());  // 1 ✅ (treated as duplicate)
💡 HashSet does NOT merge objects. It either stores or rejects. Salary difference is ignored here.

16 Mutable Key Problem in HashMap

Employee e = new Employee(1);

HashMap<Employee, String> map = new HashMap<>();
map.put(e, "Aryan");         // stored in bucket: hashCode = 1

e.id = 2;                    // key mutated! hashCode now = 2

System.out.println(map.get(e));  // null ❌
put()  → bucket for hashCode 1
e.id = 2 → hashCode now 2
get()  → looks in bucket for hashCode 2 → not found → null
🔑 Key Rule: HashMap keys should always be immutable. This is why String is the ideal key.

18 Writing a Custom Immutable Class

Rules to follow (5):

  1. Declare class as final → prevents subclassing
  2. Declare all fields as private and final → no reassignment
  3. No setter methods → write only getters
  4. Initialize all fields via constructor only
  5. For mutable fields (List, Date) → return a deep copy in getter
public final class Employee {   // Rule 1: final class

    private final int         id;       // Rule 2: private + final
    private final String      name;
    private final List<String> skills;  // mutable – needs defensive copy

    // Rule 4: Constructor only
    public Employee(int id, String name, List<String> skills) {
        this.id     = id;
        this.name   = name;
        this.skills = new ArrayList<>(skills);  // defensive copy on input
    }

    // Rule 3: Only getters – no setters
    public int    getId()   { return id; }
    public String getName() { return name; }

    // Rule 5: Return copy of mutable field
    public List<String> getSkills() {
        return new ArrayList<>(skills);   // defensive copy on output
    }
}
// Testing immutability
Employee emp = new Employee(1, "Alice", Arrays.asList("Java", "Spring"));

emp.getSkills().add("Python");            // modifies only the copy
System.out.println(emp.getSkills());      // [Java, Spring] ← original safe!

Q&A Interview Questions – Complete Set

Q1 What is String Constant Pool (SCP)?

SCP is a special memory region inside the Heap where Java stores string literals. JVM checks SCP first; if the same value exists, it reuses the reference — saving Heap memory.

Q2 How many objects are created: new String("Java") and "Java"?

2 objects total. Statement 1 → 1 Heap + 1 SCP = 2. Statement 2 → "Java" already in SCP → reused, 0 new.

Q3 What is the difference between == and equals()?
==equals()
ComparesReferenceContent
String s1 = new String("Hello");
String s2 = new String("Hello");
System.out.println(s1 == s2);       // false
System.out.println(s1.equals(s2));  // true
Q4 What is intern() and when is it used?

Returns the SCP reference of a string. If already present, that reference is returned; otherwise the string is added to SCP first.

String s1 = new String("Java");
String s2 = "Java";
System.out.println(s1 == s2);           // false
System.out.println(s1.intern() == s2);  // true
Q5 Why is String immutable in Java? (5 reasons)
  1. Security – passwords/DB URLs; immutability prevents alteration
  2. String Pool – SCP reuse is only safe because values never change
  3. Thread Safety – no synchronization needed; safe across threads
  4. HashCode Caching – computed once; ideal HashMap key
  5. Class Loading Safety – JVM uses String for class names
Q6 Output: String s1 = "Hel" + "lo"; String s2 = "Hello"; s1 == s2?

true – Compiler optimizes "Hel" + "lo" to "Hello" at compile time. Both use same SCP object.

Q7 Output: String a = "Hel"; String s2 = a + "lo"; s1 == s2?

false – a is non-final → concatenation at runtime via StringBuilder → new Heap object.

Q8 What if a is declared final?

true – final makes a a compile-time constant; compiler optimizes to "Hello" → same SCP object.

Q9 Can two unequal objects have the same hashCode?

Yes. This is called a collision.

System.out.println("FB".hashCode());   // 2236
System.out.println("Ea".hashCode());   // 2236
System.out.println("FB".equals("Ea")); // false → collision
Q10 Can equal objects have different hashCodes?

No. Equal objects must have the same hashCode. The reverse is not guaranteed.

Q11 Problem if only equals() is overridden but not hashCode()?

JVM uses default hashCode (memory address) → different buckets → equals() never called → duplicates not detected.

HashSet<Employee> set = new HashSet<>();
set.add(new Employee(1));
set.add(new Employee(1));
System.out.println(set.size());  // 2 ❌
Q12 What happens when a HashMap key is mutated after insertion?

hashCode changes → get() looks in wrong bucket → returns null.

Employee e = new Employee(1);
map.put(e, "Aryan");
e.id = 2;
System.out.println(map.get(e));  // null
Q13 How does HashMap handle collisions internally?
  • Java 7: LinkedList chaining → O(n) worst case
  • Java 8+: If bucket entries > 8 → Red-Black Tree → O(log n)

Q15 Where did you use StringBuilder in your project?

In the DAO layer for building dynamic SQL queries. Each append() modifies the same object — no new objects created, making it memory-efficient.

Q16 How to write a custom immutable class?
  1. final class
  2. private final fields
  3. No setters
  4. Constructor-only initialization
  5. Defensive copy for mutable fields
Q17 Why is String the best HashMap key?
  • Immutable → hashCode never changes after insertion
  • HashCode cached → no recomputation → faster lookups
  • Stable and Secure
