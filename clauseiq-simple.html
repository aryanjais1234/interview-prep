    ClauseIQ — AI Contract Analysis

    A microservices project that reads a contract, breaks it into clauses, and uses AI to score the risk of each clause against the customer's own rules. Same architecture as before, written in a plain and straightforward way.

    Java 21Spring Boot 3.5 Spring AIKafka RedisPostgreSQL + pgvector 5 modules
    00

    What the project does

    The idea

    Companies sign a lot of contracts. Somebody has to read each one and check whether the terms are acceptable. ClauseIQ does the first pass of that reading with AI.

    Each customer of ClauseIQ is called a tenant. A tenant does two things:

    1. Uploads a playbook once. This is a document with their own rules, like "liability must be capped at 12 months of fees".
    2. Uploads contracts. For each contract we split it into clauses, and for every clause we ask the AI: what kind of clause is this, how risky is it, and does it break any of this tenant's rules?

    Why the request is asynchronous

    A 40 page contract becomes around 40 to 60 clauses. Every clause needs its own AI call, and each call takes a few seconds. So one contract takes several minutes.

    The main reason for this design

    We cannot make the user wait several minutes on one HTTP request — it will time out. And if ten users upload contracts at the same time, we would suddenly send hundreds of requests to OpenAI and hit their rate limit.

    So instead: the API accepts the request, saves it, and puts a message on Kafka. Worker services read from Kafka at their own speed. The user gets a job id and checks the status later. Kafka acts as a waiting queue between the fast API and the slow AI work.

    The flow

    Client
    Browser / Postman
    Uploads a contract, asks for an analysis, then polls for the result or opens a stream to watch the progress.
    │
    API Gateway
    Login check, tenant, rate limit
    Reads the JWT token, takes the tenant id out of it, and puts it into a header. Also counts requests in Redis so one customer cannot send too many.
    │
    Controller
    contract-service
    Saves a job row with status QUEUED and returns 202 Accepted straight away with the job id.
    │
    Kafka
    Producer → topic → consumers
    The job is sent to the topic analysis-requested. This is the buffer. If 100 jobs arrive at once they just wait in the topic.
    │
    AI Worker
    Redis + RAG + Spring AI
    For each clause: check Redis cache first, then search the tenant's playbook in pgvector, then call the AI and get back a proper Java object.
    │
    Result store
    PostgreSQL + Redis
    Findings are saved as rows in Postgres. The current job status is also kept in Redis so polling is fast.
    │
    Client
    Poll or stream
    GET /analysis/{jobId} to check status, or GET /analysis/{jobId}/stream to receive live updates using SSE.

    Docker Compose

    Three things we need running: PostgreSQL (with the pgvector extension so it can also store embeddings), Redis, and Kafka.

    Why pgvector and not a separate vector database

    We already need PostgreSQL for the job and finding tables. The pgvector extension lets the same database also store embeddings, so we only have one database to run and back up.

    Careful with the vector size

    The number 1536 must match the embedding model. We use text-embedding-3-small which gives 1536 numbers. If you change the model to a bigger one you must also change this column and upload all documents again.

    05

    api-gateway — setup

    The gateway is the front door. All requests come here first, and it forwards them to the right service. It also does the login check and the rate limiting so the other services do not have to.

    06

    Checking the token and finding the tenant

    The token contains the tenant id inside it. We read it once here and put it in a header. After that, every other service can simply read X-Tenant-Id from the request.

    Important security point

    We always set the tenant header with .header(...) from the token. If we only added it when it was missing, a user could send X-Tenant-Id: some-other-company themselves and read another customer's contracts.

    07

    Rate limiting with Redis

    AI calls cost money, so we limit how many requests each customer can send per minute. The limit depends on their plan.

    The idea is simple: we keep a counter in Redis. The key contains the current minute, so when the minute changes the key changes too and the count starts from zero again. We also set an expiry so old keys are deleted automatically.

    Why Redis and not a variable in the class

    If we counted requests in a normal Java variable, and we run two copies of the gateway, each copy would have its own count and a customer could send double the limit. Redis is shared by all copies, so the count is correct no matter how many gateways are running.

    12

    ingestion-service — reading files into the vector database

    Before we can analyse anything, the PDF has to be split into pieces and saved as embeddings. Spring AI calls this an ETL pipeline: read the file, split it into chunks, save it to the vector store.

    PDF file→ PagePdfDocumentReader→ TokenTextSplitter→ add tenantId→ vectorStore.add()
    Why we save the tenantId in the metadata

    All customers share the same vector_store table. The only thing that keeps their data separate is this tenantId in the metadata, which we use as a filter when we search. If we forget to add it, the search would return other customers' documents.

    13

    ai-worker — setup

    This service has no controller. It only reads messages from Kafka and does the AI work. If we need to go faster we start more copies of it.

    The setting that caused a bug for me

    max.poll.interval.ms. With the default of 5 minutes, long contracts made Kafka think the worker had crashed. It gave the same message to another worker, so two workers analysed the same contract and I paid twice. Setting it to 15 minutes fixed it.

    What the cache saved me

    Standard clauses repeat a lot between contracts. In my testing about a third of the clauses were already in the cache, which means a third fewer AI calls. It is the easiest way to reduce the cost.

    What happens when something breaks

    ProblemWhat happens
    OpenAI is down The listener throws an exception, so Kafka retries the message after 5s, then 10s, then 20s. If it still fails it goes to the DLT and the job is marked FAILED.
    The worker restarts in the middle Kafka sends the message again. We check the job status first, and the cache means the clauses we already did are almost free the second time.
    Redis is down The cache returns null every time so we call the AI more often. Slower and more expensive, but the job still works.
    Kafka is down The job row is saved with status QUEUED but the message is not sent. The user sees QUEUED forever. A scheduled job that re-sends old QUEUED jobs would fix this.

    Things I would add next

    • An Idempotency-Key header so that if the user clicks the button twice we do not create two jobs.
    • A scheduled task that finds jobs stuck in QUEUED and sends them to Kafka again.
    • Unit tests for the analysis service using a mock ChatClient.
    • A circuit breaker on the AI call, so when OpenAI is down we stop trying immediately instead of waiting for a timeout every time.
