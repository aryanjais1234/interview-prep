    Core Java

    Strings, memory, equality, immutability, Java 8 features and the JVM basics that come up in almost every interview.

    01

    What is the difference between == and equals()?

    == compares references — are these two variables pointing at the same object in memory. equals() compares content, if the class has overridden it.

    Follow-up they always ask

    "What if you don't override equals()?" Then it falls back to Object.equals(), which is just ==. That is why two identical-looking objects of your own class come out as not equal.

    02

    Why must you override hashCode() when you override equals()?

    Because HashMap and HashSet find the bucket using hashCode() first, and only then compare with equals(). If two equal objects give different hash codes they land in different buckets and the map never even compares them.

    The contract is: equal objects must have equal hash codes. The reverse is not required — two different objects can share a hash code, that is just a collision.

    In practice: use String for normal values, StringBuilder when you are building a string in a loop, and StringBuffer almost never — if multiple threads are building one string, your design usually has a bigger problem.

    04

    Why is String immutable in Java?

    Four reasons, and interviewers usually want at least two:

    • String pool — strings are shared. If one variable could change the value, every other variable pointing at it would change too.
    • Security — file paths, URLs and DB connection strings are Strings. If they were mutable, code could change a path after a security check had passed.
    • Thread safety — immutable objects need no synchronisation.
    • Caching the hash — String caches its hashCode, which makes it a fast HashMap key.
    05

    What is the String pool?

    A special area in the heap where Java keeps one copy of each string literal. When you write String s = "hello", Java checks the pool first and reuses the existing object.

    Using new String("hello") skips the pool and forces a new object — which is why you almost never write that.

    07

    How does garbage collection work?

    The GC finds objects that are no longer reachable from any live reference and frees their memory. The heap is split into generations because most objects die young:

    • Young generation (Eden + two Survivor spaces) — new objects. Cleaned often, quickly.
    • Old generation — objects that survived several young collections. Cleaned rarely, and it is more expensive.

    An object becomes eligible when nothing references it. You cannot force collection — System.gc() is only a suggestion and is usually a code smell.

    09

    What is a memory leak in Java, if the GC handles memory?

    The GC only frees objects that nothing references. A leak in Java means you are still holding a reference to something you no longer need.

    Common causes I have actually seen:

    • A static Map used as a cache with nothing ever removed.
    • Listeners registered and never unregistered.
    • ThreadLocal not cleared on a pooled thread — the thread lives forever, so the value does too.
    • Unclosed streams and connections.
    10

    What is the transient keyword?

    It tells Java not to serialise this field. When the object is written to a stream the field is skipped, and when it is read back it gets the default value (null, 0, false).

    Use it for passwords, tokens, open connections, and anything you can recalculate.

    11

    What is serialVersionUID and why does it matter?

    It is a version number for a serialisable class. When Java reads a serialised object it compares the stored ID with the class's current ID. If they differ you get an InvalidClassException.

    If you do not declare it, Java generates one from the class structure — so adding a single field silently breaks deserialisation of old data. Declaring it explicitly keeps you in control.

    12

    Shallow copy vs deep copy?

    Shallow copies the fields, so object references are shared — change the nested object through one copy and the other sees it. Deep copies the nested objects too, so they are fully independent.

    13

    What is the volatile keyword?

    It guarantees visibility. Each CPU core can cache a variable; volatile forces reads and writes to go to main memory so every thread sees the latest value.

    Important limitation

    Volatile does not make operations atomic. count++ on a volatile field is still broken with multiple threads, because it is read-modify-write. For that you need AtomicInteger or synchronized.

    Sequential vs parallel streams — when would you use parallel?

    parallelStream() splits the work across the common ForkJoinPool. It only helps when the dataset is large and the operation is CPU-heavy and independent.

    When NOT to use it — worth saying

    What is Optional and why was it introduced?

    A container that may or may not hold a value. It was added to make "this might be absent" part of the method signature instead of a surprise NullPointerException.

    Use it as a return type. Do not use it for fields or method parameters — it was never designed for that.

    Only two things skip finally: System.exit() and the JVM crashing.

    If a class has two private and two public fields with getters and setters, is it still encapsulated?

    No. Encapsulation means the internal state is controlled. The moment a field is public, anyone can read and write it directly, bypassing any validation you put in the setter.

    Also worth adding

    Getters and setters alone are not real encapsulation either. If every field has a public getter and setter, you have just made the fields public with extra steps. Real encapsulation exposes behaviour: employee.giveRaise(10) rather than setSalary().

    What is an immutable class and how do you create one?

    An object whose state cannot change after construction. Five rules:

    1. Make the class final so nobody can subclass and break it.
    2. Make all fields private final.
    3. No setters.
    4. Set everything in the constructor.
    5. Defensive copy any mutable field, both in and out.
    The step people forget

    Point 5. Without the defensive copies, the caller keeps a reference to your internal Date or List and can modify it from outside. The class looks immutable but is not.

    Collections Framework

    HashMap internals, List and Set implementations, iterators, and the questions that separate people who have read about it from people who have debugged it.

    49

    Explain the Collection hierarchy.

    The catch question

    "Is Map part of the Collection interface?" No. Map stores key-value pairs, not single elements, so it sits outside the hierarchy. That trips up a lot of candidates.

    50

    How does HashMap work internally?

    This is asked in almost every interview. The flow for put(key, value):

    1. Call key.hashCode().
    2. Apply an internal hash spreading function (XOR the high bits into the low bits) so poor hash codes still spread out.
    3. Find the bucket: index = (n - 1) & hash, where n is the array length.
    4. If the bucket is empty, insert.
    5. If not, walk the chain comparing with equals(). Same key means replace the value, otherwise append.

    Internally it is an array of Node objects, each holding hash, key, value and next.

    51

    How does HashMap handle collisions?

    Two keys landing in the same bucket are chained together.

    • Before Java 8 — always a linked list. Worst case lookup was O(n).
    • Java 8 and later — when a bucket has more than 8 entries and the table is at least 64 slots, that bucket becomes a red-black tree, so worst case is O(log n).
    • If it shrinks back below 6, it converts back to a list.
    Why 8 and 6, not 8 and 7?

    The gap prevents thrashing. If both thresholds were the same, a bucket hovering at the boundary would convert back and forth on every insert and remove.

    52

    What is load factor and why is it 0.75?

    The load factor decides when the map resizes. At 0.75 with a default capacity of 16, the map doubles to 32 once it holds 12 entries.

    It is a trade-off:

    • Lower (say 0.5) — fewer collisions, faster lookups, but wastes memory and resizes more often.
    • Higher (say 1.0) — better memory use, but more collisions and slower lookups.

    0.75 was chosen as the sweet spot, and it also plays well with the maths behind Poisson distribution of collisions. If you know how many entries you will hold, size it upfront — new HashMap<>(1000) avoids several expensive rehashes.

    53

    What happens during HashMap resize?

    A new array is created at double the size, and every entry is rehashed into the new array. This is an O(n) operation, which is why sizing correctly upfront matters.

    Java 8 improved it: because capacity is always a power of two, an entry either stays at the same index or moves to index + oldCapacity. So it splits each chain into two without recomputing the hash.

    Classic follow-up

    "What happened before Java 8 with concurrent resize?" Two threads resizing at once could create a circular linked list, and a later get() would loop forever, pinning a CPU at 100%. Java 8's split approach fixed that — but HashMap is still not thread safe.

    54

    Can you use a custom class as a HashMap key? What is required?

    Yes, but you must override hashCode() and equals(), and ideally make the class immutable.

    Why immutable matters

    If a field used in hashCode() changes after the object is put in the map, the hash changes, so the map looks in a different bucket and can never find the entry again. The value is stuck in the map, unreachable.

    55

    HashMap vs Hashtable vs ConcurrentHashMap?

    HashMapHashtableConcurrentHashMap
    Thread safeNoYesYes
    LockingNoneWhole mapPer bucket / CAS
    Null keyOne allowedNot allowedNot allowed
    PerformanceFastestSlowestFast under concurrency

    Hashtable locks the entire map for every operation, so with ten threads nine are always waiting. ConcurrentHashMap only locks the bucket being touched, so different threads working on different keys never block each other.

    56

    Why does ConcurrentHashMap not allow null keys or values?

    Because of ambiguity in a concurrent world. If map.get(key) returns null, you cannot tell whether the key is absent or the value really is null.

    In a single-threaded HashMap you can just call containsKey() to find out. In a concurrent map, another thread could change things between the two calls, so that check is not reliable. Rather than leave an unsafe API, the designers banned nulls outright.

    57

    How does ConcurrentHashMap achieve thread safety?

    • Java 7 — segment locking. The map was split into 16 segments, each with its own lock, so 16 threads could write at once.
    • Java 8+ — segments removed. It uses CAS (compare-and-swap) for the common case of inserting into an empty bucket, and synchronized on the first node of a bucket only when there is a collision.

    Reads are completely lock-free — the nodes' val and next fields are volatile.

    77

    Explain the thread lifecycle.

    StateMeans
    NEWObject created, start() not called yet

    BLOCKEDWaiting to acquire a monitor lock
    WAITINGwait(), join() with no timeout

    The NEW vs RUNNABLE question

    Java has no separate "RUNNING" state. Once you call start() the thread is RUNNABLE, whether the OS has actually given it CPU time or not. That distinction is exactly what interviewers are probing for.

    78

    Difference between start() and run()?

    start() creates a new thread and the JVM calls run() on it. Calling run() directly is just a normal method call on the current thread — no new thread at all.

    Also: calling start() twice throws IllegalThreadStateException. A thread cannot be restarted once it has terminated.

    79

    Thread vs Runnable — which do you prefer?

    Runnable, almost always. Java allows only one parent class, so extending Thread uses up your one inheritance slot for no benefit. Runnable also separates the task from the thread that runs it, which is what lets you hand it to an executor.

    80

    What does the synchronized keyword do internally?

    Every Java object has a monitor. synchronized makes a thread acquire that monitor before entering, and release it on exit — including when an exception is thrown.

    At bytecode level it becomes monitorenter and monitorexit. It gives you two guarantees: mutual exclusion (one thread at a time) and visibility (changes made inside are visible to the next thread that acquires the lock).

    Common mistake

    An instance method and a static method synchronize on different locks, so they do not exclude each other. People assume they do and get race conditions.

    82

    What is a deadlock and how do you prevent it?

    Two threads each holding a lock the other one needs, so neither can move.

    Four conditions must all hold: mutual exclusion, hold-and-wait, no preemption, circular wait. Break any one and there is no deadlock.

    How I prevent it in practice:

    • Lock ordering — always acquire locks in the same global order. This is the main fix.
    • Timeouts — tryLock(timeout) so a thread gives up rather than waiting forever.
    • Hold fewer locks — keep the synchronized block as small as possible.

    How do you detect a deadlock in a running application?

    Take a thread dump and look for "Found one Java-level deadlock".

    The dump names both threads, the locks they hold and the locks they want. Tools like JConsole, VisualVM and JMC show it visually. In production, an APM tool usually flags the stuck threads first.

    84

    What is a race condition?

    When the result depends on the timing of threads. The classic example is count++, which looks like one operation but is actually three: read, add, write.

    85

    Explain the Java Memory Model.

    The JMM defines when a write by one thread becomes visible to another. Two problems it addresses:

    • Visibility — each core caches values, so a write may not be seen by another thread.
    • Reordering — the compiler and CPU may reorder instructions for speed, which is safe for one thread but visible to another.

    It defines happens-before relationships. If A happens-before B, then B sees everything A did. Key ones:

    • Unlocking a monitor happens-before any later lock of it.
    • Writing a volatile happens-before any later read of it.
    • Thread.start() happens-before anything in that thread.
    • Everything in a thread happens-before another thread's join() returns.

    volatilesynchronizedAtomicInteger

    Rule of thumb: a boolean flag that one thread sets and others read → volatile. A counter → AtomicInteger. Several fields that must change together → synchronized.

    87

    How do Atomic classes work without locks?

    They use CAS — compare-and-swap, a single CPU instruction: "if this memory location still holds the value I expect, replace it; otherwise tell me you failed."

    Under low contention this is much faster than locking because no thread ever sleeps. Under very high contention the retry loop can spin a lot — that is why Java 8 added LongAdder, which keeps per-thread cells and sums them only when you read.

    Why is Executors.newFixedThreadPool() considered risky in production?

    Because its queue is unbounded. If tasks arrive faster than they complete, the queue grows until you get an OutOfMemoryError. The same applies to newCachedThreadPool(), which can create unlimited threads.

    CallerRunsPolicy is a neat trick: when the queue is full, the submitting thread runs the task itself, which naturally slows down whoever is producing the work.

    93

    notify() vs notifyAll()?

    notify() wakes one arbitrary waiting thread. notifyAll() wakes all of them, and they compete for the lock.

    Prefer notifyAll(). With notify(), if the woken thread is not the one whose condition became true, it goes back to waiting — and the thread that could have made progress is never woken. That is a "lost wakeup" and the app just hangs.

    In modern code I would use BlockingQueue or a Condition instead of writing wait/notify at all.

    94

    What is ThreadLocal and where is it used?

    It gives each thread its own independent copy of a variable — no sharing, so no synchronization needed.

    Spring uses it heavily: the security context, the current transaction and the request attributes are all stored per thread.

    The memory leak

    On a pooled thread the thread never dies, so the ThreadLocal value never gets collected. In any web app or executor you must call remove() in a finally block, or you leak on every request.

    What is the producer-consumer problem and how do you solve it?

    Producers add items, consumers take them, and you need to handle "queue full" and "queue empty" without busy-waiting. The clean answer is BlockingQueue — it handles all the waiting internally.

    The bounded size is the point: it gives you backpressure, so a fast producer cannot exhaust memory.

    97

    What is a Semaphore?

    A counter that limits how many threads can access something at once. A lock allows one; a semaphore allows N.

    Real use: protecting a downstream service that cannot handle your full concurrency, or limiting how many threads hit a connection pool.

    98

    What are virtual threads (Java 21)?

    Lightweight threads managed by the JVM instead of the OS. A platform thread costs about 1MB of stack, so you can run a few thousand. Virtual threads cost a few hundred bytes, so you can run millions.

    The key idea: when a virtual thread blocks on I/O, the JVM unmounts it from the carrier thread, so the OS thread is free. That means simple blocking code scales like reactive code, without the reactive complexity. It helps I/O-bound work, not CPU-bound work.

    99

    How do you make a class thread safe?

    In order of preference:

    1. Make it immutable — no shared mutable state means no problem at all.
    2. Avoid sharing — use local variables or ThreadLocal.
    3. Use concurrent collections — ConcurrentHashMap, AtomicInteger.
    4. Synchronize — the last resort, and keep the block as small as possible.
    Spring angle they often follow up with

    Spring beans are singletons, so they are shared by all request threads. That is fine as long as the bean is stateless. The moment you add a mutable instance field to a @Service, you have created a race condition across requests.

    100

    What is the difference between concurrency and parallelism?

    Concurrency is dealing with many things at once — tasks make progress by interleaving, even on one core. Parallelism is doing many things at once — genuinely simultaneous, requires multiple cores.

    The analogy I like: one barista serving several customers by switching between them is concurrency. Three baristas each serving a customer is parallelism.

    How would you design a rate limiter allowing 5 requests per user per minute?

    This is a very common design question. I would say the choice depends on whether the app runs on one instance or many.

    What they want you to mention

    The trade-off between a fixed window (simple, but allows a burst of 10 across the boundary of two minutes) and a sliding window or token bucket (accurate, more state). And the fact that in-memory breaks the moment you scale to two instances.

    Explain the JVM architecture.

    How does class loading work?

    Three phases:

    1. Loading — read the .class file and create a Class object.
    2. Linking — verify the bytecode is safe, prepare static fields with default values, resolve symbolic references.
    3. Initialization — run static blocks and assign static field values.

    LoaderLoads

    106

    What is the parent delegation model?

    When a class loader is asked for a class, it first asks its parent. Only if the parent cannot find it does the child try to load it itself.

    The reason is security and consistency. If you write your own java.lang.String, delegation means the real one is always found first, so you cannot replace core classes and break the JVM.

    Where it gets broken deliberately

    Application servers like Tomcat invert this — they check the webapp's own WEB-INF/lib first, so two applications can use different versions of the same library. That is one of the few legitimate reasons to break delegation.

    107

    What is the JIT compiler?

    Just-In-Time compiler. The JVM starts by interpreting bytecode, which is slow but starts instantly. It counts how often each method runs, and once a method becomes "hot" the JIT compiles it to native machine code.

    So Java gets the best of both: fast startup from the interpreter, near-native speed for the code that actually matters.

    Why this matters in practice

    It is why benchmarks need a warmup. The first thousand calls run interpreted and look slow; after JIT kicks in the same code can be 10–100x faster. Benchmarking without warmup gives meaningless numbers.

    What optimizations does the JIT actually perform?

    OptimizationWhat it does

    Escape analysisIf an object never leaves the method, it can be allocated on the stack or removed entirely

    Escape analysis is the interesting one to mention: it means a short-lived object inside a method may never touch the heap at all, so the GC never sees it.

    109

    What are GC roots?

    The starting points the GC uses to decide what is still alive. Anything reachable from a root survives; everything else is garbage.

    The main roots are:

    • Local variables and parameters on any thread's stack
    • Static fields of loaded classes
    • Active threads themselves
    • JNI references from native code
    • Objects used as monitors (currently synchronized on)
    Why this explains memory leaks

    A static Map used as a cache is a GC root. Everything in it is permanently reachable, so the GC can never collect it — no matter how big it gets. That single fact explains most Java "memory leaks".

    How would you debug an OutOfMemoryError in production?

    My actual process:

    1. Make sure a heap dump is captured — this flag should already be on in production:
    1. Read the exact message — heap, Metaspace and thread OOMs have different causes.
    2. Check GC logs — is memory growing steadily and never coming back down after a full GC? That is a leak. If it is just spiky, the heap may simply be too small.
    3. Open the dump in Eclipse MAT and run the Leak Suspects report. It usually names the culprit directly.
    4. Follow the "path to GC root" for the biggest retained object — that shows you exactly what is holding the reference.

    In my experience the answer is nearly always a cache with no eviction, or a ThreadLocal never cleared on a pooled thread.

    TypeCleansCost
    MinorYoung generation onlyFast, milliseconds

    116

    What does "stop-the-world" mean?

    A pause where the JVM stops all application threads so the GC can work safely — otherwise objects would move while your code was using them.

    Every collector has stop-the-world pauses; they differ in how long. A full GC on a large heap with the old collectors could pause for seconds, which shows up as a latency spike in your API metrics that has no matching slow query.

    Modern collectors attack exactly this: G1 targets a pause budget you set with MaxGCPauseMillis, and ZGC/Shenandoah do most of their work concurrently, keeping pauses under about 10ms even on very large heaps.

    Why is this API call wrapped with a timeout?

    Why do you use a connection pool instead of opening connections manually?

    Opening a database connection is expensive — TCP handshake, authentication, session setup, often 50–100ms. Doing that per request would dominate your response time.

    A pool creates connections once and hands them out. It also bounds the number of connections, which protects the database — 200 app threads each opening a connection would exhaust the database's own limit and take down every other service using it.

    What are the rules for designing a good REST API?

    How does @RequestBody work internally?

    Step by step:

    1. The request hits DispatcherServlet.
    2. HandlerMapping finds the controller method.
    3. RequestResponseBodyMethodProcessor sees the @RequestBody parameter.
    4. It looks at the Content-Type header and picks a matching HttpMessageConverter — for JSON that is MappingJackson2HttpMessageConverter.
    5. Jackson's ObjectMapper reads the body stream and binds it to your class, matching JSON field names to setters or fields.
    6. If @Valid is present, bean validation runs, and a failure throws MethodArgumentNotValidException.
    Common failures

    No default constructor, wrong Content-Type (form data instead of application/json), or field names not matching. Use @JsonProperty("user_name") when the JSON uses snake_case.

    What is a POJO, and how is it different from a JavaBean?

    A POJO is Plain Old Java Object — an ordinary class with no framework requirements, no mandatory superclass, no special interfaces.

    A JavaBean is a POJO that follows stricter conventions:

    • A public no-argument constructor
    • Private fields with public getters and setters
    • Implements Serializable

    The reason it matters: Jackson, Hibernate and Spring all rely on the JavaBean conventions to bind data reflectively. That is why a missing no-arg constructor breaks deserialisation.

    Why does this endpoint return DTOs instead of entities?

    This is a very common "why did you choose" question. Five solid reasons:

    • Security — an entity may hold a password hash, internal flags or audit columns. Return it and you leak them.
    • Decoupling — renaming a database column should not break every API client.
    • No lazy loading surprises — serialising an entity outside a transaction triggers LazyInitializationException, or silently fires dozens of queries.
    • Shape control — the API can flatten, rename and combine fields from several entities.
    • No infinite recursion — a bidirectional relationship serialises forever without @JsonIgnore.

    What does it mean for an API to be idempotent, and why does it matter?

    Calling it once and calling it ten times leaves the system in the same state.

    MethodIdempotent
    GET, PUT, DELETE, HEADYes
    POST, PATCHNo (by default)

    It matters because networks retry. A client times out, retries, and now you have charged the card twice. Anything that moves money or creates records needs protection.

    Backing it with a unique constraint on the key column is what makes it safe under concurrent duplicate requests — two threads race, one insert wins, the other gets a constraint violation and reads the existing row.

    180

    Why is this API designed to be safe for retries?

    Because in a distributed system, retries are guaranteed — by the client, the gateway, the service mesh, or an impatient user clicking twice.

    What I do:

    • Idempotency-Key header on every state-changing POST.
    • A unique constraint in the database as the real guarantee, not just an application check.
    • Return the same response for a repeated key, not a 409 — the client should not have to care that it was a retry.
    • Make the retryable operation atomic, so a half-finished retry cannot corrupt state.
    Nice point to add

    "I also make sure a failed request is safe to retry. If a POST creates a row and then calls a payment gateway, a retry after a gateway timeout must not create a second row. So I write the row first with a PENDING status keyed by the idempotency key, then attempt the charge."

    Why do you disable CSRF for a JWT API?

    CSRF attacks work because browsers automatically attach cookies to any request to your domain, including one triggered from a malicious site.

    A JWT in an Authorization header is not sent automatically — the client's JavaScript has to add it deliberately. So the attack vector does not exist and the CSRF token is pure overhead.

    The important exception

    If you store the JWT in a cookie, CSRF is back on the table, because now the browser does send it automatically. In that case keep CSRF protection on, or use SameSite=Strict cookies.

    JWT vs OAuth2 — are they the same thing?

    What is CORS and why does it block your requests?

    Cross-Origin Resource Sharing. Browsers enforce the same-origin policy — JavaScript on app.com cannot read a response from api.com unless that server explicitly allows it.

    For anything other than a simple GET, the browser sends a preflight OPTIONS request first, asking whether the real request is allowed.

    Two things worth adding: CORS is a browser restriction — curl and Postman ignore it entirely — and it is not a security feature protecting your server, it protects the user from a malicious site reading their data.

    215

    How do you prevent SQL injection?

    The rule: parameters are data, never SQL. A prepared statement sends the query and the values separately, so the value can never be interpreted as code.

    Extra layers: validate input, use a database account with least privilege, and never expose raw database errors to the caller.

    216

    How do you handle role-based vs permission-based authorization?

    Roles are coarse (ADMIN, USER). Permissions are fine-grained (ORDER_DELETE, REPORT_VIEW). Roles are collections of permissions.

    The practical difference: with roles, giving a "Support Lead" the ability to delete orders means editing code and redeploying. With permissions, you just add ORDER_DELETE to that role in the database.

    The naming trap

    hasRole('ADMIN') looks for the authority ROLE_ADMIN — Spring adds the prefix for you. hasAuthority('ADMIN') looks for exactly ADMIN. Mixing these up is a very common bug.

    How do you handle authentication for service-to-service calls?

    There is no user, so you cannot forward a user token. Options:

    ApproachNotes
    OAuth2 client credentialsEach service has its own client id and secret and gets a token. The standard answer
    mTLSMutual TLS — both sides present certificates. Common with a service mesh
    Token propagationPass the user's token downstream. Simple, but every service sees the user token
    API keySimplest, weakest. Fine for internal, low-risk calls
    Good nuance

    Token propagation is easy but couples services to the user's token lifetime — if it expires mid-chain, a downstream call fails for no obvious reason. Client credentials avoids that because each service manages its own token.

    What is the Bulkhead pattern?

    Named after ship compartments — isolate resources so a flood in one section does not sink the ship. In practice: give each downstream dependency its own thread pool or concurrency limit.

    The scenario it prevents: the payment API slows to 30 seconds per call. Without a bulkhead, all 200 of your threads end up waiting on payments, so the completely healthy product-search endpoint also stops responding. With one, only 10 threads can be stuck there.

    226

    What is the Retry pattern and when is it dangerous?

    When it is dangerous:

    • Non-idempotent operations — retrying a payment charges twice.
    • Retry storms — a struggling service gets 3x the traffic, which finishes it off.
    • No jitter — every client retries at exactly the same moment, creating a thundering herd.
    • Retrying 4xx — a 400 or 401 will fail identically every time.

    Retry should always be paired with a circuit breaker, so repeated failures eventually stop the calls altogether.

    227

    How do you handle distributed transactions?

    You do not use two-phase commit — it does not scale and it locks resources across services. Instead you use the Saga pattern: a sequence of local transactions, each with a compensating action if a later step fails.

    ChoreographyOrchestration
    ControlEach service reacts to eventsA central orchestrator directs
    CouplingLooseTighter to the orchestrator
    VisibilityHard to see the whole flowThe flow is in one place
    Good forSimple flows, few stepsComplex flows with branching

    The key trade-off to state: you give up atomicity and get eventual consistency, and there is a window where the system is in an intermediate state.

    228

    What is eventual consistency and how do you explain it to a business stakeholder?

    The system will become consistent, but not instantly. For a short window different services may see different states.

    The explanation that lands: "when you place an order, the confirmation appears immediately, but the inventory count on the product page might take two seconds to update. It always catches up — we trade instant consistency for the system staying available even when one part is slow."

    How I design for it:

    • Make operations idempotent so replays are safe.
    • Design the UI to show a pending state rather than pretending it is done.
    • Use the outbox pattern so an event is never lost between the DB write and the publish.
    • Add reconciliation jobs to catch anything that fell through.
    229

    What is the Outbox pattern and what problem does it solve?

    It solves the dual-write problem: you need to save to the database and publish an event, but you cannot do both atomically.

    Now either both writes happen or neither does. A relay process (or Debezium reading the transaction log) publishes the events, so delivery is at-least-once — which is why consumers must be idempotent.

    What is the database-per-service pattern, and how do you query across services?

    Each service owns its data, and no other service touches its tables directly. That is what makes independent deployment possible — you can change your schema without coordinating with four other teams.

    But it means you cannot JOIN across services. Options:

    ApproachHowTrade-off
    API compositionCall each service and join in memorySimple, but N calls and no DB-side filtering
    CQRS read modelBuild a denormalised view from eventsFast reads, eventual consistency
    Data duplicationStore the few fields you need locallyFast, must keep it in sync via events
    Practical example

    An order needs the customer's name. Rather than calling customer-service on every read, I store customerName on the order at creation time. It is a snapshot of the name at purchase — which is arguably more correct anyway, since an invoice should not change when someone updates their profile.

    231

    What is CQRS?

    Command Query Responsibility Segregation — separate the write model from the read model.

    You use it when reads and writes have genuinely different needs — for example a heavily normalised write model for correctness, and a flat, pre-joined view for a dashboard that would otherwise need a seven-table join.

    Be balanced

    "CQRS adds real complexity — two models, synchronisation, eventual consistency. I would only reach for it when reads massively outnumber writes and the query shape is genuinely different, not as a default architecture."

    233

    How do you guarantee message ordering in Kafka?

    Kafka guarantees order within a partition, not across a topic. So you control ordering through the message key.

    The trade-off

    More partitions means more parallelism but less ordering. Choosing the key is really choosing your unit of ordering. Keying by orderId gives per-order ordering with full parallelism across different orders — that is almost always what you actually want.

    Also worth mentioning: set max.in.flight.requests.per.connection=1 or enable idempotence, otherwise a retry can reorder messages within the producer itself.

    234

    What is a consumer group and consumer lag?

    A consumer group is a set of consumers sharing the work of a topic. Each partition is assigned to exactly one consumer in the group, so adding consumers scales you out — up to the partition count.

    Consumer lag is how far behind the consumers are: latest offset minus committed offset.

    Lag is the single most useful metric to alert on. Steadily rising lag means consumers cannot keep up — either scale out, or the processing is too slow. Lag that spikes and recovers is normal traffic variation.

    Key limit

    You cannot have more useful consumers than partitions. 3 partitions and 10 consumers means 7 sit completely idle. Partition count is a capacity decision you should make early, because increasing it later changes key-to-partition mapping.

    235

    What is a Dead Letter Queue?

    A separate topic or queue where messages go after they have failed all retries. Without one, a poison message either blocks the partition forever or gets silently dropped.

    Operationally: alert when DLT depth is greater than zero. A message in the DLT means work that will never happen unless a human looks at it.

    236

    What is distributed tracing and why do you need it?

    When one user request touches six services, a stack trace in one service tells you almost nothing. Tracing stitches the whole journey together.

    • Trace ID — one per user request, passed to every service.
    • Span ID — one per operation, with a parent span, forming a tree.

    The payoff: a waterfall view showing that a 3-second request spent 2.8s inside inventory-service waiting on a database call. You cannot get that from logs alone.

    Log the trace id in every log line too, so you can jump from a trace to the exact logs.

    How do you implement centralised logging?

    Services write structured JSON to stdout; a collector ships it to a searchable store.

    The two things that make it useful: structured fields (so you can filter by orderId, not grep a string) and the trace id (so you can pull every log line across all services for one request).

    What does an idempotent API mean in a microservices context?

    The same request processed multiple times has the same effect as processing it once. In microservices this is not optional, because at-least-once delivery is the norm — Kafka will redeliver, clients will retry, gateways will retry.

    The unique constraint on event_id is the real guarantee — if two consumers race, one insert fails and that message is skipped.

    What is the Strangler Fig pattern?

    How you migrate a monolith to microservices without a big-bang rewrite. You put a proxy in front, then move one feature at a time, routing that path to the new service. The monolith shrinks until it can be switched off.

    Why it beats a rewrite: you deliver value continuously, you can roll back a single route, and you are never in a 12-month window where nothing ships. Big-bang rewrites famously fail.

    How do you version microservice APIs without breaking consumers?

    • Additive changes only — adding an optional field is backward compatible. Removing or renaming one is not.
    • Run versions side by side — /v1 and /v2 both live until consumers migrate.
    • Deprecate with a timeline — announce, add a Deprecation header, monitor who is still calling it.
    • Consumer-driven contract tests — Pact or Spring Cloud Contract, so CI tells you when you break a consumer before you deploy.
    • Tolerant reader — consumers ignore unknown fields (@JsonIgnoreProperties(ignoreUnknown = true)), so producers can add fields freely.

    The tolerant reader point is the practical one — it is what makes additive change actually safe.

    How do you decide the boundaries of a microservice?

    The most common failure in microservices is getting boundaries wrong, so I would answer carefully:

    • Business capability, not technical layer. "Orders", not "the database service".
    • Domain-Driven Design bounded contexts — where the language changes, there is probably a boundary. "Customer" means something different to Sales and to Support.
    • Data ownership — a service should own its data completely. If two services constantly need the same table, they might be one service.
    • Rate of change — things that change together belong together.
    • Team structure — a service should be ownable by one team.
    Warning sign to mention

    "If a single feature change requires deploying three services in a specific order, the boundaries are wrong — that is a distributed monolith, which has all the costs of microservices and none of the benefits."

    What is the CAP theorem and how does it apply?

    In a distributed system you can guarantee only two of: Consistency, Availability, Partition tolerance.

    Since network partitions will happen, P is not optional. So the real choice is between C and A during a partition:

    ChoiceBehaviour during a partitionExample
    CPRefuse requests rather than serve stale dataBanking, inventory
    APStay up, accept temporary inconsistencySocial feed, product catalogue

    Worth adding: it is not one decision for the whole system. In an e-commerce app the payment service should be CP, while the product recommendations can happily be AP.

    259

    Order service calls Payment service. Payment is down. What happens and what do you do?

    What happens without protection: the call hangs until the socket timeout. Threads pile up waiting. Eventually the Tomcat thread pool is exhausted and order-service stops responding — including endpoints that have nothing to do with payments. One dead service has taken down two.

    What I would put in place:

    1. Timeout — 3s connect, 5s read. Fail fast instead of hanging.
    2. Circuit breaker — after a failure threshold, stop calling at all for 30s.
    3. Fallback — do not just error. Save the order as PAYMENT_PENDING and return 202.
    4. Queue it — publish a PaymentRequested event so it is retried automatically when payment recovers.
    5. Bulkhead — cap payment calls at 10 concurrent threads so the rest of the service stays healthy.

    The point to make: degrade a feature, do not fail the request. The customer's order is captured; the charge happens minutes later.

    A user was charged twice for one order. How did it happen and how do you fix it?

    Most likely cause: the client timed out and retried, or a Kafka consumer redelivered the message after a rebalance. The payment API was not idempotent, so both attempts charged.

    Immediate fix: refund the duplicate, then find every other affected order by looking for two payments with the same order id in a short window.

    Permanent fix:

    The unique constraint on the key column is the real guarantee. The application check alone loses the race between two concurrent requests.

    An API that took 200ms now takes 5 seconds. How do you investigate?

    I would work outside-in, narrowing down before changing anything:

    1. When did it start? Correlate with a deploy, a config change or a traffic increase. That alone often gives you the answer.
    2. Is it all requests or some? Check p50 vs p99. If only p99 moved, it is likely a specific data case or lock contention.
    3. Look at a trace. The waterfall shows which span grew — my service, a downstream call, or the database.
    4. If it is the database — check slow query logs, run EXPLAIN, look for a missing index or a new N+1.
    5. If it is my service — check GC logs for long pauses, thread dump for lock contention, and connection pool metrics for waiting threads.
    6. If it is downstream — the problem is in their service, but I still need a timeout so it does not become my outage.
    What impresses

    Saying "I would check whether the data volume changed" — a query with no index is fine at 10,000 rows and terrible at 10 million. The code did not change; the data did. That is the most commonly missed cause.

    A Kafka consumer is falling behind and lag keeps growing. What do you do?

    1. Is processing slow? Time the listener. If each message takes 2s and 100/s arrive, no amount of scaling fixes a fundamentally slow consumer.
    2. Are we at the partition limit? With 3 partitions you cannot use more than 3 consumers — extra ones sit idle.
    3. Is it a poison message? One message failing and retrying forever blocks its partition.

    Not enough partitionsIncrease partitions (plan for it — it changes key mapping)
    Poison messageRetry topics + DLT so it stops blocking
    Traffic genuinely doubledScale, and check whether the producer should batch

    A downstream service is slow, and now your service is timing out too. Explain and fix.

    This is cascading failure. Your threads are all blocked waiting on the slow service, so requests that do not even touch it start queuing and timing out.

    Fixes, in order of importance:

    1. Bulkhead — cap inventory calls at 10 concurrent. The other 190 threads stay free.
    2. Aggressive timeout — 2s, not 30s. Fail fast.
    3. Circuit breaker — stop calling entirely once it is clearly broken.
    4. Fallback — serve cached stock levels with a "may be out of date" flag.
    5. Make it async if the answer is not needed immediately.

    The mindset to convey: my service's availability should not equal the product of every dependency's availability.

    266

    How would you design a URL shortener?

    A classic design question. I would cover these points:

    API: POST /shorten returns a short code; GET /{code} returns a 301/302 redirect.

    Generating the code:

    • Counter + Base62 — a distributed counter (Redis INCR or a DB sequence range) encoded to Base62. Short, no collisions, but sequential and guessable.
    • Hash + collision check — MD5 of the URL, take 7 characters, retry on collision.
    • Pre-generated pool — generate codes in advance so the write path never blocks.

    Scale considerations:

    • Reads massively outnumber writes, so cache aggressively in Redis — a hot link should never touch the database.
    • 7 Base62 characters gives 62⁷ ≈ 3.5 trillion combinations, which is plenty.
    • 301 is cached by browsers forever (great for load, terrible for analytics). Use 302 if you need click tracking.
    • Store an expiry and a click count; delete expired rows with a batch job.

    How would you design a notification service (email, SMS, push)?

    Core decision: it must be asynchronous. No business flow should fail because an SMS provider is slow.

    Design points I would raise:

    • Strategy pattern per channel, so adding WhatsApp is a new class, not an if-else chain.
    • Templates stored in the database or a template engine, not hardcoded — marketing changes copy without a deploy.
    • Idempotency keyed on a notification id, so a redelivery does not send twice.
    • User preferences — check opt-outs and quiet hours before sending.
    • Rate limiting per user so a bug cannot send 500 emails to one person.
    • Retry with backoff, then DLT. A hard bounce should not be retried at all.
    • Status tracking — QUEUED, SENT, DELIVERED, FAILED, plus provider webhooks.
    268

    10,000 users try to buy the last 100 concert tickets at once. How do you handle it?

    The classic oversell problem. Layered answer:

    1. Do not let 10,000 requests reach the database. Use Redis as the front line — an atomic DECR on the stock counter. Anything below zero is rejected immediately without touching Postgres.
    2. Atomic database update as the source of truth, so Redis being wrong cannot oversell:
    1. Queue the actual purchase — reserve the ticket, return "processing", complete payment asynchronously. This flattens the spike.
    2. Reservation with a TTL — hold the seat for 10 minutes while the user pays, release it automatically if they abandon.
    3. A virtual waiting room for very large events, admitting users in batches.
    What they are checking

    That you do not write if (stock > 0) { stock--; } in Java. Between the read and the write, a hundred other threads have done the same check. The atomicity has to live in the database or in Redis, not in application code.

    269

    Your database is the bottleneck. What are your options?

    In the order I would actually try them, cheapest first:

    1. Fix the queries. Run EXPLAIN, add missing indexes, remove SELECT *, kill N+1s. This solves it more often than anything else and costs nothing.
    2. Cache. Redis in front of hot reads. If 80% of reads are the same 100 rows, this removes most of the load.
    3. Connection pool tuning. Sometimes the pool is too small — or too large and thrashing the database.
    4. Read replicas. Route reads to replicas, writes to the primary. Good when the workload is read-heavy, but you must handle replication lag.
    5. Archive old data. A table with 500 million rows where only the last 90 days are queried should be partitioned or archived.
    6. Vertical scaling. More RAM and IOPS. Buys time, not a solution.
    7. Sharding. Last resort — it is a large, hard change that complicates every query.
    Good closing line

    "I would resist sharding until I had exhausted indexing and caching. Most 'we need to shard' situations turn out to be three missing indexes and an N+1."

    270

    How do you optimise a slow SQL query?

    1. EXPLAIN / EXPLAIN ANALYZE — look for a full table scan where you expect an index seek, and check whether estimated rows match actual rows.
    2. Index the WHERE, JOIN and ORDER BY columns. A composite index's column order matters — most selective first, and it only helps if the query uses a leading prefix.
    3. Remove SELECT * — fetching only what you need can turn a lookup into a covering index scan that never touches the table.
    4. Avoid functions on indexed columns — WHERE YEAR(created_at) = 2024 cannot use the index; a range condition can.
    5. Replace correlated subqueries with joins where the planner handles them better.
    6. Watch OFFSET on deep pages — use keyset pagination instead.

    I would also mention: measure with production-like data volume. Everything is fast on 100 rows.

    271

    Users report data is "sometimes stale". How do you debug it?

    Almost always caching or replication. I would check in this order:

    1. Is there a cache? Check whether the write path evicts it. A very common bug is @Cacheable on the read with no @CacheEvict on the update.
    2. Cache key mismatch — the read caches under user:123 but the evict uses users:123, so nothing is ever invalidated.
    3. Multiple instances with local caches — instance A updates and evicts locally, instance B still serves the old value. Fix by moving to a shared cache.
    4. Read replica lag — the write went to the primary, the read came from a replica that is 200ms behind. Route read-after-write to the primary.
    5. Eventual consistency by design — if an event updates a read model, there is a window. That may be correct, and the fix is in the UI, not the backend.
    Mitigation worth mentioning

    "Even with correct eviction, I set a TTL on every cache entry. That way a missed invalidation means data is stale for two minutes, not forever."

    272

    A deployment broke production. Walk me through what you do.

    Restore service first, investigate second. That order matters and they are listening for it.

    1. Roll back immediately. Do not debug in production while users are affected. If it is a canary, shift traffic back to the old version.
    2. Confirm recovery — error rate and latency back to normal.
    3. Communicate — tell stakeholders and update the status page.
    4. Then investigate — diff the release, check logs from the failure window, reproduce in a lower environment.
    5. Fix forward with a test that would have caught it.
    6. Blameless postmortem — why did CI not catch this? Should there have been a canary, a feature flag, a contract test?
    The database caveat

    "If the release included a schema migration, rollback is not always safe — a dropped column cannot be un-dropped. That is exactly why I use expand-contract migrations, so the previous version still works against the new schema."

    How do you migrate a monolith to microservices without downtime?

    Incrementally, using the Strangler Fig pattern.

    1. Put a gateway in front of the monolith first, routing everything to it. Nothing changes functionally, but now you have a place to redirect from.
    2. Pick the first service carefully — something with clear boundaries, low coupling and real business value. Notifications or reporting are good first candidates; the core order flow is not.
    3. Extract the code, keep the database shared at first if you must.
    4. Route that path to the new service at the gateway. Canary it — 5%, then 50%, then 100%.
    5. Split the data — this is the hard part. Sync both ways temporarily, then cut over.
    6. Repeat, and delete the code from the monolith as you go.
    What experienced people say

    "The database is always harder than the code. I would extract the service first and share the database temporarily, then separate the data as a second step. Trying to do both at once is where these migrations fail."

    275

    How would you implement a "forgot password" flow securely?

    1. User submits their email.
    2. Always return the same response — "if that email exists, we have sent a link". Saying "email not found" tells an attacker which accounts exist.
    3. Generate a cryptographically random token (not a UUID from a predictable source), store a hash of it with a short expiry (15–30 minutes) and single-use flag.
    4. Email the link. Never include the new password in an email.
    5. On reset: verify the token hash, check expiry and unused flag, apply password rules, hash with BCrypt, mark the token used.
    6. Invalidate all existing sessions and refresh tokens — if the account was compromised, the attacker should be logged out.
    7. Send a "your password was changed" notification to the old email.
    Details that show security awareness

    Storing the token hashed (so a database leak does not hand over live reset links), rate limiting the request endpoint, and revoking sessions after the reset. Most candidates miss all three.

    How would you design a file upload service for large files?

    Do not proxy the bytes through your service. That is the key insight.

    Why: streaming 500MB through your service ties up a thread and memory for minutes, and one concurrent upload per thread does not scale at all.

    Other points I would raise:

    • Multipart upload for very large files, so a failure resumes rather than restarting.
    • Validate on the server — never trust the client's stated content type; check the magic bytes.
    • Virus scan asynchronously before making the file available.
    • Short-lived presigned URLs (a few minutes) so a leaked URL is not a permanent hole.
    • Quotas per user to prevent abuse.

    Memory usage climbs steadily until the pod is OOM-killed every few days. How do you find it?

    A steady climb that never recovers after a full GC is a classic leak.

    1. Confirm from GC logs — if the post-full-GC heap keeps rising, it is a leak, not just an undersized heap.
    2. Get a heap dump — -XX:+HeapDumpOnOutOfMemoryError, or jmap before it dies.
    3. Eclipse MAT → Leak Suspects. It usually names the class directly.
    4. Follow "path to GC root" on the biggest retained object to see what is holding it.

    The usual culprits, and I would check these first:

    • A static Map cache with no eviction and no TTL.
    • ThreadLocal never removed on a pooled thread.
    • Listeners or callbacks registered and never removed.
    • An unbounded queue in an executor, growing because consumers are slower than producers.
    • Unclosed streams or connections.
    Practical tip

    "If I cannot reproduce it locally, I take two heap dumps an hour apart in production and compare them. The class whose instance count grew is the leak — that comparison is usually faster than staring at a single dump."

    How would you add a new field to an API used by 20 client teams?

    Adding an optional field is backward compatible, so no new version is needed — provided consumers are tolerant readers.

    • Add the field as optional with a sensible default. Never make it required.
    • Confirm consumers use @JsonIgnoreProperties(ignoreUnknown = true). If any client fails on unknown fields, that is the real problem to fix.
    • Announce it and update the OpenAPI spec.
    • Run contract tests in CI so a breaking change fails before deployment.

    If it were a breaking change instead — renaming or removing a field:

    1. Add the new field alongside the old one, populate both.
    2. Mark the old one deprecated with a removal date; add a Deprecation header.
    3. Monitor usage of the old field to see who is still on it.
    4. Chase the remaining consumers, then remove it.

    The point to land: expand-contract works for APIs exactly as it does for database schemas.

    An external API you depend on has a rate limit of 100 requests/minute. How do you respect it?

    1. Client-side rate limiter — Resilience4j's RateLimiter or a Redis token bucket shared across instances. With three pods you must share the budget, or you will send 300/min.
    2. Queue the work — do not call the API on the request thread. Push to a queue and let a worker drain it at a controlled rate.
    3. Cache responses — the cheapest request is the one you never make. If 60% of lookups repeat, you have effectively raised your limit.
    4. Batch if the API supports it — one call for 50 ids instead of 50 calls.
    5. Handle 429 properly — respect the Retry-After header rather than retrying immediately and making it worse.

    Leaving headroom is a small detail worth mentioning — running at exactly the limit means any clock skew or burst tips you over.

    282

    How do you handle a poison message that keeps failing and blocking your consumer?

    A message that always throws will be retried forever, blocking its partition. Everything behind it stops.

    Key points:

    • Retry topics, not in-process sleep — the main partition keeps flowing while the failed message backs off separately.
    • Distinguish retryable from permanent. A deserialization error or a validation failure will never succeed; retrying it three times is pure waste.
    • Alert on DLT depth. A message there is work that will never happen.
    • Have a replay path — after fixing the bug, you need to reprocess the DLT.

    Your team wants to add a cache. What questions would you ask first?

    Caching is often reached for too early, so I would push back with questions before agreeing:

    • What is the actual problem? If a query is slow because of a missing index, caching hides a bug instead of fixing it.
    • What is the read/write ratio? Caching only pays off when reads dominate.
    • How stale can this data be? Product descriptions — minutes are fine. Account balance — not at all.
    • What is the invalidation strategy? If we cannot answer this cleanly, we will ship stale-data bugs.
    • Local or distributed? Local is faster but inconsistent across instances.
    • What happens on a cache miss storm? If a hot key expires and 500 threads all recompute it at once, the database gets hit harder than with no cache at all.
    • What if Redis is down? The app must degrade to hitting the database, not fail.
    Good closing statement

    "I always set a TTL even when I have explicit eviction, so a missed invalidation is a two-minute problem rather than a permanent one. And I measure the hit rate afterwards — a cache with a 5% hit rate is just added complexity."

    What is an index and how does it improve performance?

    A separate structure (usually a B-tree) that lets the database find rows without scanning the whole table. Like the index at the back of a book.

    The cost, which candidates often forget to mention:

    • Every INSERT, UPDATE and DELETE must also update the index — writes get slower.
    • Indexes take disk space and memory.
    • Too many indexes can confuse the query planner.

    So index what you filter, join and sort on — not every column.

    What is normalisation, and when would you denormalise?

    FormRule
    1NFAtomic values, no repeating groups
    2NF1NF + no partial dependency on part of a composite key
    3NF2NF + no transitive dependency between non-key columns

    Normalisation removes redundancy, which prevents update anomalies — a customer's address stored in 500 order rows means 500 places to update.

    When I would denormalise:

    • Read-heavy reporting where a 6-table join is too slow.
    • Storing a value that must be a historical snapshot — the price at the time of purchase should not change when the product price changes.

    What is a deadlock in a database and how do you avoid it?

    Same idea as in Java: two transactions each hold a lock the other needs.

    Most databases detect this and kill one transaction with a deadlock error.

    How to avoid it:

    • Consistent lock order — always update the lower account id first. This is the main fix.
    • Keep transactions short — never do an HTTP call inside one.
    • Use the lowest workable isolation level.
    • Retry on deadlock — it is a transient error, so catching it and retrying once is legitimate.

    How do you find and fix a slow query in production?

    1. Find it — the slow query log, pg_stat_statements, or your APM's database view. Sort by total time, not just average — a 50ms query run a million times matters more than a 2s query run twice.
    2. EXPLAIN ANALYZE it — look for sequential scans on large tables, and compare estimated vs actual row counts. A big mismatch means stale statistics.
    3. Fix the common causes — missing index, function on an indexed column, SELECT *, implicit type conversion, or an OR that prevents index use.
    4. Verify — re-run EXPLAIN and confirm the plan actually changed. Adding an index does not guarantee the planner will use it.

    How do you handle database migrations in a Spring Boot project?

    The rules I follow:

    • Never use ddl-auto: update in production. It is unpredictable, it never drops anything, and you have no record of what it did.
    • Migrations are immutable. Once applied, never edit a file — write a new one. Flyway checksums them and will fail if one changes.
    • Migrations live with the code and go through the same review.
    • Backward compatible using expand-contract, so a rolling deploy where old and new pods run together does not break.
