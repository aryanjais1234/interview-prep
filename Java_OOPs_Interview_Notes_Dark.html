01 The Four Pillars of OOPs

🔒
Encapsulation
Binding data and methods into a single unit with controlled access via private fields + public getters/setters.
🧬
Inheritance
Reusing properties/methods of a parent class in a child class using extends or implements.
🔀
Polymorphism
One name, multiple behaviours — achieved through overloading (compile-time) and overriding (runtime).
🎭
Abstraction
Hiding implementation details; exposing only functionality to the end user via interfaces or abstract classes.

02 Encapsulation

Rules to achieve encapsulation:

  • Declare all fields as private
  • Provide public getter and setter methods
// Entity / DTO class – classic encapsulation example
public class Item {

    private int    id;
    private String name;
    private String color;
    private double price;

    // Getters
    public int    getId()    { return id; }
    public String getName()  { return name; }
    public String getColor() { return color; }
    public double getPrice() { return price; }

    // Setters
    public void setId(int id)          { this.id = id; }
    public void setName(String name)   { this.name = name; }
    public void setColor(String color) { this.color = color; }
    public void setPrice(double price) { this.price = price; }
}
💡 Real-time usage: Every @Entity or DTO class in a Spring Boot project follows encapsulation.

03 Inheritance

Keywords:

  • Same type (class → class, interface → interface) → extends
  • Different type (class → interface) → implements
// Parent interface
public interface InventoryService {
    void addItem(Item item);
    void addItem(List<Item> items);   // overloaded
    void removeItem(Item item);
    void removeItem(int itemId);      // overloaded
}

// Child / Implementation class
public class InventoryServiceImpl implements InventoryService {

    @Override
    public void addItem(Item item) {
        System.out.println("Adding single item: " + item.getName());
    }

    @Override
    public void addItem(List<Item> items) {
        System.out.println("Adding " + items.size() + " items");
    }

    @Override
    public void removeItem(Item item) {
        System.out.println("Removing item: " + item.getName());
    }

    @Override
    public void removeItem(int itemId) {
        System.out.println("Removing item with ID: " + itemId);
    }
}

04 Polymorphism

4a. Method Overloading – Compile-time / Static Polymorphism

Same method name, different parameters.

public class InventoryService {

    // Search by name only
    public Item searchItem(String name) { ... }

    // Search by name + color
    public Item searchItem(String name, String color) { ... }

    // Search by name + color + price
    public Item searchItem(String name, String color, double price) { ... }

    // Remove by object
    public void removeItem(Item item) { ... }

    // Remove by ID
    public void removeItem(int itemId) { ... }
}

4b. Method Overriding – Runtime / Dynamic Polymorphism

Same signature in parent and child; child provides its own implementation.

// Interface (Parent)
public interface InventoryService {
    void addItem(Item item);
}

// Implementation (Child)
public class InventoryServiceImpl implements InventoryService {

    @Override                         // same signature – overriding
    public void addItem(Item item) {
        System.out.println("Item saved: " + item.getName());
    }
}

4c. Runtime Polymorphism in Real Projects

// Controller injects the INTERFACE, not the implementation
@RestController
public class InventoryController {

    // Spring injects whichever implementation is active at runtime
    private final InventoryService inventoryService;

    public InventoryController(InventoryService inventoryService) {
        this.inventoryService = inventoryService;
    }
}
💡 This is dynamic / runtime polymorphism – the actual implementation is resolved at runtime by Spring.

05 Abstraction

  • Abstract class – partial implementation; use abstract keyword.
  • Interface – 100% abstraction (before Java 8). Exposes only what the user needs.
public interface PaymentService {
    void doTransaction(double amount);  // abstract – must implement
}

public class GooglePay implements PaymentService {
    @Override
    public void doTransaction(double amount) {
        System.out.println("Google Pay: Processing ₹" + amount);
    }
}

GoalHide implementationHide data

Default Method – Purpose & Example

Purpose: NOT force all implementation classes to override every method.

public interface Payment {

    void doTransaction(double amount);   // abstract – must override

    // Default – implementations are NOT forced to override this
    default void addCoupon(String code) {
        System.out.println("Default 5% cashback applied.");
    }

    // Static – common utility for ALL implementations
    static void generateTransactionReport(String txnId) {
        System.out.println("Transaction Report for: " + txnId);
    }
}

public class GooglePay implements Payment {
    @Override
    public void doTransaction(double amount) { System.out.println("GPay ₹" + amount); }

    @Override
    public void addCoupon(String code) {
        System.out.println("GPay: 10% cashback for code " + code);
    }
}

public class PhonePe implements Payment {
    @Override
    public void doTransaction(double amount) { System.out.println("PhonePe ₹" + amount); }
    // addCoupon NOT overridden → uses default 5% cashback
}
✅ Static method in interface = common utility shared by all implementations. No need for a separate Util class.

07 Exception Hierarchy in Overriding

Case 1: Parent throws → Child declaration is OPTIONAL

class Parent {
    void m1() throws Exception {   // parent throws
        System.out.println("Parent m1");
    }
}

class Child extends Parent {
    @Override
    void m1() {               // No throws – perfectly valid ✅
        System.out.println("Child m1");
    }
}

Case 2: Child throws → Parent MUST declare it

class Parent2 {
    void m1() { }             // parent does NOT throw
}

class Child2 extends Parent2 {
    @Override
    // void m1() throws Exception { }  // ❌ Compilation error!
    // Child CANNOT throw checked exception if parent doesn't
    void m1() { System.out.println("Child2 m1"); }
}
🔑 Rule: If parent throws → child throw is optional. If child throws → parent must declare the same (or broader) checked exception.

08 Static & Private Methods – Cannot be Overridden

class Parent {

    static void staticMethod() {       // Method hiding, NOT overriding
        System.out.println("Parent static");
    }

    private void privateMethod() {     // Not visible to child at all
        System.out.println("Parent private");
    }
}

class Child extends Parent {

    // @Override  ← compile error for static methods
    static void staticMethod() {
        System.out.println("Child static");
    }

    // privateMethod cannot even be seen here
}

// Calling static methods – use class name, NOT object
Parent.staticMethod();   // → Parent static
Child.staticMethod();    // → Child static  (method hiding)

Runtime Polymorphism Demo

class Parent {
    void m1() { System.out.println("Parent m1"); }
}
class Child extends Parent {
    @Override
    void m1() { System.out.println("Child m1"); }
}

Parent p = new Child();   // reference = Parent, object = Child
p.m1();                    // Output: Child m1  ← JVM uses actual object type
💡 JVM resolves overridden methods at runtime based on the actual object type, not the reference type.

09 Covariant Return Type in Overriding (Tricky)

When overriding, the child method can return a subtype of the return type declared in the parent.

interface A { }
class B implements A { }

interface InventoryService {
    A getData();           // returns parent type A
}

class InventoryServiceImpl implements InventoryService {
    @Override
    public B getData() {   // ✅ returning child type B – valid (covariant)
        return new B();
    }
}
⚠️ Interviewers use this to confuse candidates. Remember: child method CAN return a subtype of the parent's declared return type.

Q&A Interview Questions – Complete Set

Q1 What are the 4 pillars of OOPs?
  1. Encapsulation – private fields + public getters/setters
  2. Inheritance – extends / implements for code reuse
  3. Polymorphism – overloading (compile-time) + overriding (runtime)
  4. Abstraction – hide implementation, expose only interface
Q2 Where did you use Encapsulation in your project?

In every @Entity and DTO class. All fields are private; access is only through getters and setters, protecting data integrity.

Q3 What is the difference between Overloading and Overriding?

Also calledCompile-time polymorphismRuntime polymorphism
Method nameSameSame
ParametersDifferentSame

Return typeCan differSame (or covariant)
@OverrideNot usedUsed
Q4 Can we override static or private methods?

No.

  • Static methods → it becomes method hiding. The method called depends on the reference type, not the object.
  • Private methods → not visible to child class; cannot be overridden.
Q5 Parent p = new Child(); p.m1() — which m1() is called?
class Parent {
    void m1() { System.out.println("Parent m1"); }
}
class Child extends Parent {
    @Override
    void m1() { System.out.println("Child m1"); }
}

Parent p = new Child();
p.m1();   // Output: Child m1

Even though reference type is Parent, actual object is Child. JVM resolves at runtime based on object type → runtime/dynamic polymorphism.

Q6 Where did you use Runtime Polymorphism in your project?

In Spring Boot controllers, we inject the interface (InventoryService), not the concrete class (InventoryServiceImpl). At runtime, Spring resolves the actual bean — allowing multiple implementations to be swapped without changing the controller.

Q7 What is the rule for exceptions in overriding?
  • Parent throws → child declaration is optional
  • Child throws checked exception → parent must also declare it
Q8 What is the difference between Java 7 and Java 8 interfaces?
  • Java 7: interfaces can only have abstract methods.
  • Java 8: interfaces can also have default methods (with body) and static methods.
  • default methods avoid forcing all implementing classes to override a new method.
Q9 What is a Covariant Return Type?

When overriding, the child method can return a subtype of the return type declared in the parent.

// Parent returns A; child can return B (where B implements A)
interface Service { A getData(); }
class ServiceImpl implements Service {
    @Override
    public B getData() { return new B(); }  // ✅ valid
}
